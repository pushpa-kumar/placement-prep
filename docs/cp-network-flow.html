Network Flow & Matching

Network flow turns problems about moving resources through a capacitated directed graph into a single well-understood algorithmic primitive: repeatedly push flow along augmenting paths until none remain. From this one idea fall out three of the most reusable tools in competitive programming: computing the maximum throughput between two nodes, computing the minimum-capacity set of edges that separates them (its exact dual, by the max-flow min-cut theorem), and computing the largest matching in a bipartite graph (a special case of max flow with unit capacities). Recognizing when a problem secretly IS one of these three, and building the right graph to feed into a standard implementation, is the real skill being tested. Once max-flow is established, attaching a per-unit cost to each edge (min-cost max-flow) or specializing to complete bipartite matching with a cost matrix (the Hungarian algorithm) unlocks a large family of assignment and scheduling problems that plain max-flow cannot express.

Maximum Flow (Edmonds-Karp)

2 worked examples

A flow network is a directed graph where every edge (u, v) has a nonnegative capacity cap(u, v). A flow is an assignment of a value f(u, v) to every edge satisfying two constraints: capacity (0 <= f(u, v) <= cap(u, v)) and conservation (for every vertex other than the source s and sink t, total flow in equals total flow out). The value of the flow is the net amount leaving s (equivalently, the net amount arriving at t). The maximum flow problem asks for the largest achievable flow value from s to t.

The Ford-Fulkerson method solves this by repeatedly finding an 'augmenting path' -- a path from s to t along which more flow can still be pushed -- in the residual graph, and pushing the bottleneck capacity along it. The residual graph contains, for every edge (u, v) with remaining capacity cap(u, v) - f(u, v) > 0, a forward residual edge, and for every edge (u, v) carrying positive flow, a backward residual edge (v, u) with residual capacity f(u, v) that lets a later augmentation 'undo' a previously bad routing decision. Edmonds-Karp is the specific, easy-to-get-right version of this method that always picks the augmenting path with the FEWEST EDGES, found via a plain BFS on the residual graph rather than an arbitrary DFS. This single choice is what gives it a clean polynomial bound: it can be shown the shortest augmenting-path length never decreases across iterations and each edge can be the 'bottleneck' edge of a shortest path only O(V) times, giving O(VE) total augmentations, each found in O(E) via BFS.

The algorithm terminates when BFS from s in the residual graph can no longer reach t -- at that point, by the max-flow min-cut theorem, the flow found is provably maximum (see the Minimum Cut subtopic for why). Implementation-wise, the standard trick is to store the graph as an adjacency list of edge structs, adding both a forward edge with the given capacity and a paired backward edge with capacity 0, and recording each edge's index of its 'reverse twin' so that augmenting a path can update both sides of every edge in O(1) per edge. Always use a signed 64-bit type for capacities/flow to avoid overflow when capacities are summed.

Edmonds-Karp's O(VE^2) worst case is noticeably slower than Dinic's algorithm (O(V^2E), and much faster in practice, especially O(E*sqrt(V)) on unit-capacity graphs such as bipartite matching instances), which builds level graphs with BFS and then finds a blocking flow with DFS per phase. Dinic's is what you should reach for once graph sizes exceed a few thousand vertices/edges; Edmonds-Karp is preferred here purely because its correctness is much easier to verify by hand and it is very hard to get subtly wrong.

Recognize it by

Look for a directed (or undirected, modeled as two opposite directed edges) graph with explicit edge capacities and a question about the maximum amount of 'flow' -- data rate, goods, people, water -- that can be pushed from one designated source node to one designated sink node. Also recognize disguised versions: 'maximum number of edge-disjoint paths' (unit-capacity max flow), 'can we route X units simultaneously' (max flow >= X feasibility check), and problems with multiple sources/sinks (add a super-source/super-sink connected to each with infinite or given capacity).

Complexity

Edmonds-Karp: O(V * E^2) time (O(VE) augmenting paths, each found by an O(E) BFS), O(V + E) space. Dinic's algorithm improves this to O(V^2 * E) in general and O(E * sqrt(V)) on unit-capacity graphs.

Basic Max Flow Between Two Nodes

Problem

A directed network has n computers numbered 1..n connected by m directed cables, each with an integer bandwidth capacity. Computer 1 wants to send data to computer n. Find the maximum total data rate that can be sustained from computer 1 to computer n.

Input: the first line has two integers n and m (1 <= n <= 10, 0 <= m <= 20). Each of the next m lines has three integers u, v, c describing a directed cable from u to v with capacity c (1 <= u, v <= n, 1 <= c <= 100). Output the single integer maximum flow value from node 1 to node n.

Concrete instance: 4 nodes, 5 cables: 1->2 (cap 3), 1->3 (cap 2), 2->3 (cap 1), 2->4 (cap 2), 3->4 (cap 3).

Approach

1. Build a residual graph with each cable as a forward edge of its given capacity plus a paired reverse edge of capacity 0.
2. Repeat: BFS from node 1 in the residual graph to find any path to node n using only edges of positive residual capacity.
3. If no such path exists, stop -- the current total is the answer.
4. Otherwise find the bottleneck (minimum residual capacity) along the found path, add it to the answer, and subtract it from every forward edge on the path while adding it to every corresponding reverse edge.
5. By hand: augment 1->2->4 by min(3,2)=2 (running total 2), then 1->3->4 by min(2,3)=2 (running total 4), then the only remaining path 1->2->3->4 has bottleneck min(1,1,1)=1 (running total 5); after that node 4 is unreachable from node 1 in the residual graph, so the answer is 5. This matches the min cut {1,2,3} vs {4} of capacity 2 + 3 = 5.

Solution
#include <bits/stdc++.h>
using namespace std;

struct MaxFlow {
    struct Edge { int to; long long cap; int rev; };
    vector<vector<Edge>> graph;
    int n;
    MaxFlow(int n): n(n), graph(n) {}
    void addEdge(int u, int v, long long cap) {
        graph[u].push_back({v, cap, (int)graph[v].size()});
        graph[v].push_back({u, 0, (int)graph[u].size() - 1});
    }
    bool bfs(int s, int t, vector<int>& prevv, vector<int>& preve) {
        vector<bool> visited(n, false);
        queue<int> q;
        q.push(s);
        visited[s] = true;
        prevv.assign(n, -1);
        preve.assign(n, -1);
        while (!q.empty()) {
            int u = q.front(); q.pop();
            if (u == t) break;
            for (int i = 0; i < (int)graph[u].size(); i++) {
                Edge& e = graph[u][i];
                if (!visited[e.to] && e.cap > 0) {
                    visited[e.to] = true;
                    prevv[e.to] = u;
                    preve[e.to] = i;
                    q.push(e.to);
                }
            }
        }
        return visited[t];
    }
    long long maxflow(int s, int t) {
        long long flow = 0;
        vector<int> prevv, preve;
        while (bfs(s, t, prevv, preve)) {
            long long d = LLONG_MAX;
            for (int v = t; v != s; v = prevv[v])
                d = min(d, graph[prevv[v]][preve[v]].cap);
            for (int v = t; v != s; v = prevv[v]) {
                graph[prevv[v]][preve[v]].cap -= d;
                int rev = graph[prevv[v]][preve[v]].rev;
                graph[v][rev].cap += d;
            }
            flow += d;
        }
        return flow;
    }
};

int main() {
    int n, m;
    cin >> n >> m;
    MaxFlow mf(n + 1);
    for (int i = 0; i < m; i++) {
        int u, v; long long c;
        cin >> u >> v >> c;
        mf.addEdge(u, v, c);
    }
    cout << mf.maxflow(1, n) << endl;
    return 0;
}

Max Flow Requiring Several Augmenting Paths

Problem

Same setup and input/output format as above (max flow from node 1 to node n over a small capacitated directed graph, n <= 10, m <= 20), but on a network with a detour edge that lets flow reroute around a partially used bottleneck.

Concrete instance: 5 nodes, 7 cables: 1->2 (cap 4), 1->3 (cap 3), 2->3 (cap 2), 2->4 (cap 3), 4->3 (cap 1), 3->5 (cap 2), 4->5 (cap 5).

Approach

1. Same Edmonds-Karp loop as example 1: repeatedly BFS for a shortest augmenting path in the residual graph and push the bottleneck amount.
2. Notice the only way flow reaches the sink (node 5) is through node 3 (capacity 2 on edge 3->5) or node 4 (capacity 5 on edge 4->5), and the only way into node 4 is edge 2->4 (capacity 3). So the cut {1,2,3} vs {4,5} is NOT the tightest; check the cut {1,2,3} vs {4,5}: crossing edges 2->4 (3) + nothing else since 3->5's other endpoint 5 is outside and 4->3 goes into the set -- crossing capacity is 3 (from 2->4) + 2 (from 3->5) = 5.
3. Running the algorithm confirms this: total achievable flow is 5, split for example as 2 units via 1->2->4->5, 2 units via 1->2->3->5, and 1 unit via 1->3->... -- the exact path decomposition depends on BFS tie-breaking, but the final VALUE is always 5 regardless of which shortest paths are chosen, because it is pinned down by the minimum cut.

Minimum Cut (Max-Flow Min-Cut Theorem)

2 worked examples

An s-t cut of a flow network is a partition of the vertices into two sets S and T = V \ S with s in S and t in T. The capacity of the cut is the sum of capacities of edges that go FROM S TO T only (edges going from T back into S do not count, since they do not limit flow out of S). For ANY valid flow and ANY valid s-t cut, the flow's value can never exceed that cut's capacity -- every unit of flow leaving S toward t must eventually cross one of the S-to-T edges, so the cut capacity upper-bounds every achievable flow value (this direction, weak duality, is easy to see directly).

The max-flow min-cut theorem states this bound is always achieved with equality: the maximum flow value from s to t exactly equals the minimum capacity over all s-t cuts. The proof falls directly out of the Edmonds-Karp/Ford-Fulkerson termination condition: when no augmenting path exists, let S be the set of vertices still reachable from s in the final residual graph, and T everything else (t in T, since it is unreachable by assumption). Every original edge from S to T must be fully saturated (otherwise it would still have residual capacity and S could be extended across it), and every original edge from T to S must carry zero flow (otherwise its residual back-edge from S to T would let S be extended). So the net flow crossing (S, T) equals exactly the sum of capacities of the saturated S-to-T edges -- i.e. the flow value equals this particular cut's capacity, proving both that this cut is a minimum cut and that the flow is a maximum flow, simultaneously.

This gives a completely mechanical recipe: run any correct max-flow algorithm (Edmonds-Karp, Dinic's, ...) to completion, then do ONE more BFS or DFS from s in the final residual graph. Every vertex reached is on the source side S of a minimum cut; the minimum cut's capacity is simply the max flow value already computed, and if the problem asks for the actual edges to cut, they are exactly the original (not residual) edges (u, v) with u in S and v not in S.

A large family of optimization problems that look nothing like flow at first are min-cut in disguise, most famously the maximum-weight closure / project-selection problem: given items with profits and prerequisite dependencies (or, symmetrically, a penalty for touching certain 'shared' resources), build a graph with a source edge for profitable choices, a sink edge for costs, and infinite-capacity edges encoding dependencies, then the answer is (total profit) - (min cut).

Recognize it by

Phrases like 'minimum number/total weight of edges to remove to disconnect node A from node B', 'minimum edges to destroy all paths from s to t', or 'minimum vertices to delete to separate two regions' (vertex version: split each vertex into an in-node and out-node joined by an edge of capacity 1, or the vertex's weight, to cap how much can pass through it). Also recognize optimization problems phrased as 'choose a subset to maximize total profit minus some interacting penalty cost' -- these are frequently project-selection / closure problems solvable by constructing a graph and computing a min cut.

Complexity

Identical to whatever max-flow algorithm computes it -- O(V * E^2) with Edmonds-Karp -- since the minimum cut's capacity is read off directly as the max flow value, plus one extra O(V + E) BFS/DFS pass over the final residual graph to recover the actual source-side vertex set / cut edges.

Minimum Edge Cut on a Small Diamond Graph

Problem

A directed graph has n nodes and m directed edges, all of capacity 1 (i.e. this asks for the minimum number of edges whose removal disconnects node 1 from node n -- the edge connectivity from 1 to n). Compute this minimum, and also output the set of vertices reachable from node 1 in the residual graph after computing a maximum flow (one valid source side of a minimum cut), in increasing order.

Input: first line n and m (1 <= n <= 10, 0 <= m <= 20); each of the next m lines has u, v, c (here c is always 1). Output: first line is the minimum cut value; second line is the space-separated sorted list of vertices on node 1's side of that cut.

Concrete instance: 4 nodes forming a 'diamond' -- two vertex-disjoint paths from node 1 to node 4: 1->2, 1->3, 2->4, 3->4, each with capacity 1.

Approach

1. Run Edmonds-Karp max flow from 1 to 4: augment along 1->2->4 (bottleneck 1), then along 1->3->4 (bottleneck 1). Total flow = 2, and no further augmenting path exists (both edges out of node 1 are now saturated).
2. By the max-flow min-cut theorem, the minimum cut capacity equals this flow value, 2 -- you must remove both edges 1->2 and 1->3 (or equivalently both paths' worth of capacity) to fully disconnect node 1 from node 4, and no single edge removal suffices since the two paths are vertex-disjoint.
3. Do one more BFS from node 1 in the final residual graph: both 1->2 and 1->3 are fully saturated (0 residual capacity), so no further vertex is reachable -- the source side of the minimum cut is just {1}.

Solution
#include <bits/stdc++.h>
using namespace std;

struct MaxFlow {
    struct Edge { int to; long long cap; int rev; };
    vector<vector<Edge>> graph;
    int n;
    MaxFlow(int n): n(n), graph(n) {}
    void addEdge(int u, int v, long long cap) {
        graph[u].push_back({v, cap, (int)graph[v].size()});
        graph[v].push_back({u, 0, (int)graph[u].size() - 1});
    }
    bool bfs(int s, int t, vector<int>& prevv, vector<int>& preve) {
        vector<bool> visited(n, false);
        queue<int> q;
        q.push(s);
        visited[s] = true;
        prevv.assign(n, -1);
        preve.assign(n, -1);
        while (!q.empty()) {
            int u = q.front(); q.pop();
            if (u == t) break;
            for (int i = 0; i < (int)graph[u].size(); i++) {
                Edge& e = graph[u][i];
                if (!visited[e.to] && e.cap > 0) {
                    visited[e.to] = true;
                    prevv[e.to] = u;
                    preve[e.to] = i;
                    q.push(e.to);
                }
            }
        }
        return visited[t];
    }
    long long maxflow(int s, int t) {
        long long flow = 0;
        vector<int> prevv, preve;
        while (bfs(s, t, prevv, preve)) {
            long long d = LLONG_MAX;
            for (int v = t; v != s; v = prevv[v])
                d = min(d, graph[prevv[v]][preve[v]].cap);
            for (int v = t; v != s; v = prevv[v]) {
                graph[prevv[v]][preve[v]].cap -= d;
                int rev = graph[prevv[v]][preve[v]].rev;
                graph[v][rev].cap += d;
            }
            flow += d;
        }
        return flow;
    }
    // vertices reachable from s in the final residual graph (the source side of the min cut)
    vector<int> reachableFromSource(int s) {
        vector<bool> visited(n, false);
        queue<int> q;
        q.push(s);
        visited[s] = true;
        vector<int> order;
        while (!q.empty()) {
            int u = q.front(); q.pop();
            order.push_back(u);
            for (auto& e : graph[u]) {
                if (!visited[e.to] && e.cap > 0) {
                    visited[e.to] = true;
                    q.push(e.to);
                }
            }
        }
        sort(order.begin(), order.end());
        return order;
    }
};

int main() {
    int n, m;
    cin >> n >> m;
    MaxFlow mf(n + 1);
    for (int i = 0; i < m; i++) {
        int u, v; long long c;
        cin >> u >> v >> c;
        mf.addEdge(u, v, c);
    }
    long long cut = mf.maxflow(1, n);
    cout << cut << "\n";
    vector<int> side = mf.reachableFromSource(1);
    for (int i = 0; i < (int)side.size(); i++) {
        cout << side[i] << (i + 1 < (int)side.size() ? ' ' : '\n');
    }
    return 0;
}

Weighted Minimum Cut with a Non-Trivial Source Side

Problem

Same input/output format as above, but with general (non-unit) capacities, illustrating that the minimum cut does not always sit right next to the source.

Concrete instance: 4 nodes, 5 edges: 1->2 (cap 5), 1->3 (cap 5), 2->3 (cap 10), 2->4 (cap 3), 3->4 (cap 3).

Approach

1. Run Edmonds-Karp: augment 1->2->4 by min(5,3)=3 (total 3), then 1->3->4 by min(5,3)=3 (total 6). Now edges 2->4 and 3->4 are both fully saturated (0 residual capacity), while 1->2 and 1->3 still each have 2 units of residual capacity left, and 2->3 (capacity 10) is completely unused.
2. Check for another augmenting path: from node 1 you can still reach node 2 (residual 2) and node 3 (residual 2, or via 2->3 which still has capacity 10), but from either node 2 or node 3 there is no more residual capacity into node 4 (both are saturated). So node 4 is unreachable and the algorithm terminates at flow value 6.
3. The final BFS from node 1 in the residual graph reaches nodes 1, 2, AND 3 (since 1->2, 1->3, and 2->3 all still have spare residual capacity), but not node 4. So the minimum cut's source side is {1, 2, 3}, and its capacity is the sum of ORIGINAL capacities of edges leaving this set: 2->4 (3) + 3->4 (3) = 6, matching the flow value exactly -- note this cut does NOT simply cut every edge out of the source, demonstrating that the bottleneck can be 'deeper' in the network.

Bipartite Matching (Kuhn's Algorithm)

2 worked examples

Given a bipartite graph with left vertices L and right vertices R connected by edges only between the two sides, a matching is a set of edges no two of which share an endpoint. The maximum bipartite matching problem asks for the largest such set. Kuhn's algorithm (the bipartite specialization of the general augmenting-path idea, sometimes called the Hungarian algorithm in the unweighted case) builds the matching one left vertex at a time: for each unmatched left vertex u, it performs a DFS along 'alternating' edges -- first an unmatched edge to some right vertex v, and if v is already matched to some other left vertex u', it recursively tries to re-match u' to a DIFFERENT right vertex, freeing up v for u. If this DFS reaches any currently-unmatched right vertex, the entire alternating path is flipped (previously matched edges become unmatched and vice versa), increasing the total matching size by exactly one.

This is not a coincidence or a separate technique -- it is exactly the max-flow augmenting-path idea specialized to the graph formed by adding a super-source connected to every left vertex with capacity 1, a super-sink connected from every right vertex with capacity 1, and capacity-1 edges for every original left-right edge. Because every capacity is 1, the maximum flow in this network is always an integer equal to the maximum matching size, and each Kuhn's-algorithm DFS is precisely one Edmonds-Karp-style augmentation (here found by DFS rather than BFS, which is fine since all path lengths from source to sink are equal at 3 edges, so BFS vs DFS makes no complexity difference here).

Complexity: each left vertex triggers at most one DFS that visits each edge at most once, giving O(V * E) total in the worst case -- fine for V, E up to a few thousand. When graphs get larger (V, E up to ~1e5), switch to Hopcroft-Karp, which finds a maximal set of vertex-disjoint SHORTEST augmenting paths per phase via one BFS + multiple DFS's, achieving O(E * sqrt(V)) and O(sqrt(V)) phases.

Beyond directly asking for a maximum matching, bipartite matching is used as a FEASIBILITY test via Hall's marriage theorem (a perfect matching saturating one side exists if and only if every subset of that side has a neighborhood at least as large as itself), commonly wrapped in a binary search: 'find the minimum X such that a matching of size >= K exists once only edges satisfying some threshold-X condition are allowed'.

Recognize it by

Two clearly distinguishable groups (people/jobs, boys/girls, tasks/workers, rows/columns) with a compatibility relation, and a question asking for the maximum number of one-to-one pairings possible, or whether a pairing saturating one side exists. Also recognize it hiding inside a binary search: 'minimum threshold so that at least K pairs / a full assignment is achievable' almost always means 'binary search + bipartite matching feasibility check' via Hall's theorem.

Complexity

O(V * E) with a plain Kuhn's algorithm (one DFS of cost O(E) per left vertex); O(E * sqrt(V)) with Hopcroft-Karp for larger instances.

Maximum Matching Size

Problem

There are L people on the left and R people on the right (1 <= L, R <= 10), and m compatible pairs (u, v) meaning left-person u is willing to be paired with right-person v (1 <= u <= L, 1 <= v <= R, 0 <= m <= 50). Find the size of the maximum matching (the largest number of pairs that can be formed so that every person appears in at most one pair).

Input: first line L, R, m; each of the next m lines has u, v. Output: a single integer, the maximum matching size.

Concrete instance: L = R = 4, with compatible pairs (1,1), (1,2), (2,1), (3,2), (3,3), (4,3), (4,4).

Approach

1. Process left vertices in order 1..4, running a DFS-based augmenting search for each.
2. Left 1: tries right 1 (free) -> match (1,1).
3. Left 2: tries right 1 (taken by 1) -> try to re-match left 1 elsewhere: left 1's only other option is right 2, which is free -> re-match (1,2), freeing right 1 for left 2 -> match (2,1).
4. Left 3: tries right 2 (taken by 1) -> try to re-match left 1: its only options are right 1 (taken by 2, and left 2 has no other option, so this fails) -> right 2 augmentation fails -> try right 3 (free) -> match (3,3).
5. Left 4: tries right 3 (taken by 3) -> try to re-match left 3: its only other option is right 2 (taken by 1, whose only other option right 1 is taken by 2 with no alternative -- fails) -> right 3 augmentation fails -> try right 4 (free) -> match (4,4).
6. Every one of the 4 left vertices got matched, so the maximum matching size is 4.

Solution
#include <bits/stdc++.h>
using namespace std;

int L, R, m;
vector<vector<int>> adj; // adjacency list for left vertices (1-indexed)
vector<int> matchR;      // matchR[r] = l matched to r, or -1
vector<bool> visited;

bool tryKuhn(int u) {
    for (int v : adj[u]) {
        if (visited[v]) continue;
        visited[v] = true;
        if (matchR[v] == -1 || tryKuhn(matchR[v])) {
            matchR[v] = u;
            return true;
        }
    }
    return false;
}

int main() {
    cin >> L >> R >> m;
    adj.assign(L + 1, {});
    matchR.assign(R + 1, -1);
    for (int i = 0; i < m; i++) {
        int u, v;
        cin >> u >> v;
        adj[u].push_back(v);
    }
    int result = 0;
    for (int u = 1; u <= L; u++) {
        visited.assign(R + 1, false);
        if (tryKuhn(u)) result++;
    }
    cout << result << endl;
    return 0;
}

Recovering the Matched Pairs

Problem

Same setup as above (L, R, m then m compatible pairs), but now also print the matched pairs themselves, sorted by left vertex.

Input: first line L, R, m; each of the next m lines has u, v. Output: first line is the maximum matching size; each following line has one matched pair 'u v', sorted by u ascending.

Min-Cost Max-Flow (MCMF)

2 worked examples

Min-cost max-flow generalizes ordinary max-flow by giving every edge a per-unit COST in addition to its capacity, and asking for the maximum flow that also has the smallest possible total cost (sum over edges of flow(e) * cost(e)), or, in a common variant, the smallest cost to push some REQUIRED amount of flow (not necessarily the maximum). The standard algorithm is successive shortest augmenting paths (SSP): repeatedly find the CHEAPEST path from source to sink in the residual graph (using shortest-path search, since a cheapest path is exactly a shortest path when edge weights are the costs), push as much flow as the path's bottleneck capacity allows, and repeat until either no augmenting path remains (max-flow case) or the required flow amount has been shipped (required-flow case). Crucially, when you push flow along an edge, you must add a REVERSE residual edge with the NEGATED cost (mirroring how max-flow adds reverse edges with negated... well, zero-cost residual capacity, but here also negative cost) — this reverse edge lets a later augmenting path 'undo' part of an earlier, now-suboptimal, flow assignment, which is essential for overall optimality. Because of these negative-cost reverse edges, Dijkstra cannot be used directly on the raw graph; the two standard fixes are (a) SPFA / Bellman-Ford-with-a-queue, which tolerates negative edges directly at the cost of a worse worst-case complexity, or (b) Johnson's-algorithm-style potentials, which maintain a running set of vertex potentials that make all reduced edge costs non-negative, allowing Dijkstra (with a priority queue) after the very first SPFA/Bellman-Ford pass — the potentials approach is asymptotically much faster on graphs with many augmenting iterations and is the standard choice in production MCMF libraries, though a straightforward SPFA-based implementation is simpler to get right under contest time pressure and is what is shown below.

A critical correctness property of SSP is that shortest-path DISTANCES to the sink are non-decreasing across successive iterations, as long as the very first iteration's shortest paths are computed correctly (this is what justifies using Dijkstra-with-potentials after the first Bellman-Ford pass, and it is also why greedily always taking the cheapest available path, one at a time, produces a GLOBALLY minimum-cost solution rather than merely a locally greedy one — this is the deep reason SSP is provably optimal and not just a heuristic).

The hard part of most MCMF problems in practice is not the algorithm itself (a well-tested MCMF template is typically copy-pasted) but recognizing and constructing the FLOW NETWORK from a combinatorial problem statement that does not superficially mention flow at all: assignment problems where the same unit can be routed through different 'paths' at different costs, budgeted resource allocation with per-source or per-destination caps (modeled as edge capacities) and per-unit prices (modeled as edge costs), and coloring/labeling problems with per-vertex balance constraints (modeled by splitting each vertex into an in-node and out-node connected by a capacity-and-cost-carrying edge, the classic 'node splitting' trick). Recognizing when a problem is really an assignment/transportation problem in disguise, and correctly setting up capacities (which encode 'how much', e.g. a budget or a supply limit) versus costs (which encode 'how expensive per unit', e.g. a price or a penalty) is the single most important skill this subtopic tests.

Recognize it by

The problem involves assigning, routing, or matching UNITS of something (goods, characters, tasks, time slots) through multiple possible channels/pairings, each channel has both a CAPACITY (how much can flow through it) and a PER-UNIT COST, and you need either (a) the minimum cost to achieve the maximum possible throughput, or (b) the minimum cost to achieve some specific REQUIRED throughput (with -1 or 'impossible' if that throughput cannot be reached at all).

Complexity

O(F * E log V) with Dijkstra + potentials, or O(F * V * E) with plain SPFA/Bellman-Ford augmenting paths, where F is the total flow pushed (bounded by the max-flow value or the required flow amount), V and E are the network's vertex and edge counts.

Maximum Flow at Minimum Cost on a Small Network

Problem

You are given a directed flow network with n nodes (0-indexed), a designated source s and sink t, and m directed edges, each with a capacity and a per-unit cost. Compute the value of the maximum flow from s to t, and, among all flows achieving that maximum value, the minimum possible total cost.

Input: n, m, s, t on the first line; then m lines each with u, v, cap, cost describing a directed edge from u to v.
Output: two integers, the maximum flow value and its minimum total cost, separated by a space.

Approach

Build the flow network with a standard adjacency-list MCMF structure: each added edge also creates a reverse residual edge with capacity 0 and NEGATED cost. Repeatedly run SPFA (Bellman-Ford with a FIFO queue, needed because reverse residual edges carry negative costs) from s to find the CHEAPEST path to every reachable node; if the sink is unreachable, stop. Otherwise, find the bottleneck capacity along the cheapest s-to-t path (the minimum residual capacity of any edge on that path), push that much flow along it (decreasing forward capacities and increasing the corresponding reverse capacities), and add (bottleneck * path cost) to the running total cost. Repeat until no augmenting path remains; the accumulated flow is the max-flow value and the accumulated cost is the minimum cost for that flow.

This was hand-verified on the given 4-node network: source 0, sink 3, edges 0->1 (cap 2, cost 2), 0->2 (cap 1, cost 3), 1->3 (cap 1, cost 1), 1->2 (cap 1, cost 1), 2->3 (cap 2, cost 1). The bottleneck at every source/sink edge forces a unique maximum flow of exactly 3 units that saturates EVERY edge in the network simultaneously (0->1 fully used at 2, 0->2 fully used at 1, 1->3 fully used at 1, 1->2 fully used at 1, 2->3 fully used at 2) — since this is the only possible flow of value 3, its cost is forced: 2*2 + 1*3 + 1*1 + 1*1 + 2*1 = 4+3+1+1+2 = 11, matching the program's output exactly.

Solution
#include <bits/stdc++.h>
using namespace std;
typedef long long ll;
const ll INF = LLONG_MAX / 2;

struct MCMF {
    struct Edge { int to; ll cap, cost; int rev; };
    int n;
    vector<vector<Edge>> graph;
    MCMF(int n) : n(n), graph(n) {}
    void addEdge(int from, int to, ll cap, ll cost) {
        graph[from].push_back({to, cap, cost, (int)graph[to].size()});
        graph[to].push_back({from, 0, -cost, (int)graph[from].size()-1});
    }
    // returns {maxflow, mincost} using successive shortest augmenting paths (SPFA, handles negative edges)
    pair<ll,ll> run(int s, int t) {
        ll totalFlow = 0, totalCost = 0;
        while (true) {
            vector<ll> dist(n, INF);
            vector<int> prevv(n, -1), preve(n, -1);
            vector<bool> inq(n, false);
            dist[s] = 0;
            deque<int> q;
            q.push_back(s);
            inq[s] = true;
            while (!q.empty()) {
                int u = q.front(); q.pop_front();
                inq[u] = false;
                for (int i = 0; i < (int)graph[u].size(); i++) {
                    Edge &e = graph[u][i];
                    if (e.cap > 0 && dist[u] + e.cost < dist[e.to]) {
                        dist[e.to] = dist[u] + e.cost;
                        prevv[e.to] = u;
                        preve[e.to] = i;
                        if (!inq[e.to]) {
                            inq[e.to] = true;
                            q.push_back(e.to);
                        }
                    }
                }
            }
            if (dist[t] == INF) break; // no more augmenting paths
            // find bottleneck capacity along the path
            ll d = INF;
            for (int v = t; v != s; v = prevv[v]) {
                d = min(d, graph[prevv[v]][preve[v]].cap);
            }
            for (int v = t; v != s; v = prevv[v]) {
                graph[prevv[v]][preve[v]].cap -= d;
                Edge &back = graph[v][graph[prevv[v]][preve[v]].rev];
                back.cap += d;
            }
            totalFlow += d;
            totalCost += d * dist[t];
        }
        return {totalFlow, totalCost};
    }
};

int main(){
    int n, m, s, t;
    cin >> n >> m >> s >> t;
    MCMF mcmf(n);
    for (int i = 0; i < m; i++) {
        int u, v; ll cap, cost;
        cin >> u >> v >> cap >> cost;
        mcmf.addEdge(u, v, cap, cost);
    }
    auto [flow, cost] = mcmf.run(s, t);
    cout << flow << " " << cost << endl;
}

Shipping a Required Amount at Minimum Cost (or Determining Impossibility)

Problem

You must ship exactly D units of cargo from source node s to sink node t through a directed flow network with n nodes and m edges (each with a capacity and a per-unit cost), minimizing total shipping cost. If it is impossible to ship D units through the network at all (even ignoring cost), print -1.

Input: n, m, s, t, D on the first line; then m lines each with u, v, cap, cost.
Output: the minimum cost to ship exactly D units, or -1 if D units cannot be shipped.

Approach

This is the 'required flow' variant of MCMF: instead of running successive shortest augmenting paths until NO path remains (which finds the true max-flow), stop as soon as the accumulated flow reaches exactly D, capping the amount pushed along the final augmenting path so the total does not overshoot D. If the loop runs out of augmenting paths (sink becomes unreachable) before reaching D units shipped, D units are infeasible and the answer is -1. Because SSP always selects the CHEAPEST available path first, and cheapest-path costs are non-decreasing across iterations, capping the flow at D automatically yields the minimum cost for shipping exactly D units, not just A valid way to ship D units.

Verified on a 5-node network (source 0, sink 4) with edges 0->1 (cap 4, cost 2), 0->2 (cap 2, cost 2), 1->3 (cap 2, cost 1), 1->4 (cap 3, cost 6), 2->3 (cap 2, cost 1), 3->4 (cap 4, cost 2): the two cheapest paths, 0-1-3-4 (cost 2+1+2=5 per unit, capacity-limited to 2 units by edge 1->3) and 0-2-3-4 (cost 2+1+2=5 per unit, capacity-limited to 2 units by edge 0->2), together supply exactly the required D=4 units at the shared cheapest rate of 5 per unit, for a total cost of 4*5=20 — matching the program's output. Separately verified that requesting D=8 (exceeding the network's true max-flow of 6) correctly yields -1.

Solution
#include <bits/stdc++.h>

    }
    // Ships up to `need` units of flow at minimum cost, one shortest augmenting path at a time.
    // Returns {flowShipped, cost}. If flowShipped < need, it was impossible to ship `need` units.
    pair<ll,ll> run(int s, int t, ll need) {
        ll totalFlow = 0, totalCost = 0;
        while (totalFlow < need) {
            vector<ll> dist(n, INF);
            vector<int> prevv(n, -1), preve(n, -1);
            vector<bool> inq(n, false);
            dist[s] = 0;
            deque<int> q;
            q.push_back(s);
            inq[s] = true;
            while (!q.empty()) {
                int u = q.front(); q.pop_front();
                inq[u] = false;
                for (int i = 0; i < (int)graph[u].size(); i++) {
                    Edge &e = graph[u][i];
                    if (e.cap > 0 && dist[u] + e.cost < dist[e.to]) {
                        dist[e.to] = dist[u] + e.cost;
                        prevv[e.to] = u;
                        preve[e.to] = i;
                        if (!inq[e.to]) {
                            inq[e.to] = true;
                            q.push_back(e.to);
                        }
                    }
                }
            }
            if (dist[t] == INF) break; // no more augmenting paths at all
            ll d = need - totalFlow;
            for (int v = t; v != s; v = prevv[v]) {
                d = min(d, graph[prevv[v]][preve[v]].cap);
            }
            for (int v = t; v != s; v = prevv[v]) {
                graph[prevv[v]][preve[v]].cap -= d;
                Edge &back = graph[v][graph[prevv[v]][preve[v]].rev];
                back.cap += d;
            }
            totalFlow += d;
            totalCost += d * dist[t];
        }
        return {totalFlow, totalCost};
    }
};

        cin >> u >> v >> cap >> cost;
        mcmf.addEdge(u, v, cap, cost);
    }

Hungarian Algorithm (Assignment Problem)

2 worked examples

The assignment problem asks: given n 'workers' and n 'jobs' and an n x n cost matrix cost[i][j] (the cost of assigning worker i to job j), find a PERFECT matching (a bijection between workers and jobs, i.e. each worker gets exactly one job and vice versa) that minimizes (or, with negated costs, maximizes) the total cost. This is exactly a special case of min-cost max-flow — build a bipartite network with a source connected to every worker (capacity 1 each), every worker connected to every job with the given cost (capacity 1), and every job connected to the sink (capacity 1 each) — but the Hungarian algorithm (also called the Kuhn-Munkres algorithm, in its modern potential-based form sometimes attributed to Jonker-Volgenant) solves it directly in O(n^3) without any explicit flow-network machinery, which is both asymptotically better than a generic MCMF implementation on this special structure and simpler to reason about once the potential-update invariants are internalized.

The algorithm maintains a potential u_i for every worker and v_j for every job, satisfying the invariant cost[i][j] - u_i - v_j >= 0 for all i, j (with equality along 'tight' edges that are candidates for the eventual matching), and incrementally grows an augmenting structure one worker at a time: for each new worker, it runs a Dijkstra-like shortest-augmenting-path search over the REDUCED costs (cost[i][j] - u_i - v_j) to find an augmenting path from that worker to some free job through the existing partial matching, updates potentials along the way to maintain the invariant, and then flips the matching along the found path. After all n workers have been processed this way, the resulting perfect matching is provably optimal, and the total minimum cost equals -v_0 (or can simply be read off by summing cost[i][match(i)] over the final matching, which is what most implementations do directly for clarity). To solve a MAXIMIZATION version (maximize total profit rather than minimize total cost), simply negate every entry of the profit matrix and run the same minimization algorithm; the optimal assignment is unchanged and the true maximum profit is the negation of the reported minimum cost.

Beyond the literal 'n workers, n jobs, minimize total cost' framing, the Hungarian algorithm's structure applies whenever a problem reduces to choosing a BIJECTION between two equal-size finite sets to optimize a sum of pairwise costs/profits: assigning distinct completion times to tasks to minimize total tardiness penalty, choosing an order to activate a fixed set of time-dependent financial offers to maximize eventual payoff, or any 'match every item on the left to a distinct item on the right' scenario where the pairwise cost/profit matrix is given explicitly or can be computed in O(n^2) total. When n is large (thousands) and the cost structure has extra exploitable regularity (e.g. costs depending only on |i - j| or on a 1-D coordinate difference), a smarter O(n log n) greedy or DP often exists and outperforms the generic O(n^3) Hungarian algorithm — but the Hungarian algorithm remains the fully general fallback whenever the cost matrix has no such special structure.

Recognize it by

You must pair up every element of one set with a distinct element of another set of the SAME size (a bijection / perfect matching), an explicit or implicitly-computable cost (or profit) is associated with each possible pairing, and you need the minimum total cost (or maximum total profit) over all such bijections. n is usually small-to-moderate (up to several hundred to ~1000, since the algorithm is O(n^3)).

Complexity

O(n^3) time for an n x n cost matrix, O(n^2) space.

Minimum-Cost Task Assignment

Problem

There are n employees and n tasks (1 <= n <= 300 in the general version; kept small here for hand verification). You are given an n x n cost matrix where cost[i][j] is the cost of assigning employee i to task j. Assign every employee exactly one distinct task (a perfect matching between employees and tasks) to minimize the total cost. Output the minimum total cost, and one valid assignment (for each employee 1..n, the task assigned to it).

Input: n, then n rows of n integers each (the cost matrix, 1-indexed conceptually).
Output: the minimum total cost on the first line; then n integers on the second line, where the i-th integer is the task assigned to employee i.

Approach

Direct application of the O(n^3) Hungarian algorithm with worker/job potentials (u_i, v_j) and per-worker shortest-augmenting-path search over reduced costs, as described in the theory. Each new worker i is temporarily attached to a virtual 'unassigned' job (column 0 in the 1-indexed internal formulation), and the algorithm grows a shortest-path tree from that worker through the existing partial matching until it reaches a genuinely free job, then flips the matching along that path and updates potentials so the non-negativity invariant is preserved for the next worker.

Hand-verified on the 3x3 cost matrix [[4,1,3],[2,0,5],[3,2,2]]: brute-forcing all 3! = 6 possible assignments gives costs 6, 11, 5, 9, 10, 6 for the six permutations, so the true minimum is 5, achieved uniquely by employee1->task2 (cost 1), employee2->task1 (cost 2), employee3->task3 (cost 2), summing to 5 — exactly matching the program's output of total cost 5 and assignment (2, 1, 3).

Solution
#include <bits/stdc++.h>
using namespace std;
typedef long long ll;
const ll INF = LLONG_MAX / 2;

// Jonker-Volgenant / Kuhn-Munkres O(n^3) Hungarian algorithm for the square
// assignment problem: minimize sum of cost[i][match(i)] over a perfect matching.
// 1-indexed internally (standard formulation with potentials u,v).
int n;
vector<vector<ll>> cost; // 1-indexed n x n

pair<ll, vector<int>> hungarianMin() {
    vector<ll> u(n+1, 0), v(n+1, 0);
    vector<int> p(n+1, 0), way(n+1, 0); // p[j] = row assigned to column j
    for (int i = 1; i <= n; i++) {
        p[0] = i;
        int j0 = 0;
        vector<ll> minv(n+1, INF);
        vector<bool> used(n+1, false);
        do {
            used[j0] = true;
            int i0 = p[j0], j1 = -1;
            ll delta = INF;
            for (int j = 1; j <= n; j++) {
                if (!used[j]) {
                    ll cur = cost[i0][j] - u[i0] - v[j];
                    if (cur < minv[j]) { minv[j] = cur; way[j] = j0; }
                    if (minv[j] < delta) { delta = minv[j]; j1 = j; }
                }
            }
            for (int j = 0; j <= n; j++) {
                if (used[j]) { u[p[j]] += delta; v[j] -= delta; }
                else minv[j] -= delta;
            }
            j0 = j1;
        } while (p[j0] != 0);
        do {
            int j1 = way[j0];
            p[j0] = p[j1];
            j0 = j1;
        } while (j0 != 0);
    }
    vector<int> rowToCol(n+1, 0);
    for (int j = 1; j <= n; j++) rowToCol[p[j]] = j;
    ll total = 0;
    for (int i = 1; i <= n; i++) total += cost[i][rowToCol[i]];
    return {total, rowToCol};

Maximum-Profit Assignment

Problem

There are n agents and n contracts. You are given an n x n profit matrix where profit[i][j] is the profit earned if agent i is assigned contract j. Assign every agent exactly one distinct contract to MAXIMIZE total profit. Output the maximum total profit and one optimal assignment.

Input: n, then n rows of n integers each (the profit matrix).
Output: the maximum total profit on the first line; then n integers on the second line, the contract assigned to each agent.

Approach

Negate every entry of the profit matrix to obtain a cost matrix (cost[i][j] = -profit[i][j]), then run the exact same O(n^3) minimum-cost Hungarian algorithm on this negated matrix. Minimizing total negated-profit is equivalent to maximizing total profit, and the optimal assignment (the bijection itself) is identical either way — only the reported total needs to be negated back at the end.

Hand-verified on the 3x3 profit matrix [[5,9,4],[2,6,8],[7,3,1]]: brute-forcing all 6 permutations gives totals 12, 16, 12, 24, 9, 17, so the true maximum is 24, achieved uniquely by agent1->contract2 (profit 9), agent2->contract3 (profit 8), agent3->contract1 (profit 7), summing to 24 — exactly matching the program's output of total profit 24 and assignment (2, 3, 1). Note this optimum is NOT the trivial diagonal assignment, confirming the algorithm is doing genuine combinatorial work rather than defaulting to an identity matching.

Solution
#include <bits/stdc++.h>
using namespace std;
typedef long long ll;
const ll INF = LLONG_MAX / 2;

int n;
vector<vector<ll>> cost; // 1-indexed n x n, holds NEGATED profit so min-cost Hungarian maximizes profit

pair<ll, vector<int>> hungarianMin() {
    vector<ll> u(n+1, 0), v(n+1, 0);
    vector<int> p(n+1, 0), way(n+1, 0);
    for (int i = 1; i <= n; i++) {
        p[0] = i;
        int j0 = 0;
        vector<ll> minv(n+1, INF);
        vector<bool> used(n+1, false);
        do {
            used[j0] = true;
            int i0 = p[j0], j1 = -1;
            ll delta = INF;
            for (int j = 1; j <= n; j++) {
                if (!used[j]) {
                    ll cur = cost[i0][j] - u[i0] - v[j];
                    if (cur < minv[j]) { minv[j] = cur; way[j] = j0; }
                    if (minv[j] < delta) { delta = minv[j]; j1 = j; }
                }
            }
            for (int j = 0; j <= n; j++) {
                if (used[j]) { u[p[j]] += delta; v[j] -= delta; }
                else minv[j] -= delta;
            }
            j0 = j1;
        } while (p[j0] != 0);
        do {
            int j1 = way[j0];
            p[j0] = p[j1];
            j0 = j1;
        } while (j0 != 0);
    }
    vector<int> rowToCol(n+1, 0);
    for (int j = 1; j <= n; j++) rowToCol[p[j]] = j;
    ll total = 0;
    for (int i = 1; i <= n; i++) total += cost[i][rowToCol[i]];
    return {total, rowToCol};
}

int main(){
    cin >> n;
    vector<vector<ll>> profit(n+1, vector<ll>(n+1));
    cost.assign(n+1, vector<ll>(n+1));
    for (int i = 1; i <= n; i++)
        for (int j = 1; j <= n; j++) {
            cin >> profit[i][j];
            cost[i][j] = -profit[i][j]; // maximize profit == minimize negated profit
        }
    auto [totalNeg, rowToCol] = hungarianMin();
    cout << (-totalNeg) << "\n";
    for (int i = 1; i <= n; i++) cout << rowToCol[i] << " \n"[i==n];
}
