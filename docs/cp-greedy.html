Greedy Algorithms

An algorithm is 'greedy' when it builds a solution by repeatedly committing to the locally best-looking choice and never reconsidering it, without ever backtracking or exploring alternatives. This is dangerous: greedy is only as good as its proof, and unlike DP or flow (whose correctness is structural by construction), a greedy rule that merely 'sounds reasonable' is very often wrong on some input you haven't thought of. That is why proving correctness -- almost always via an exchange argument (show any optimal solution can be transformed into the greedy one without making it worse) or by recognizing an underlying matroid (show the greedy-by-weight rule is optimal because feasible sets form a matroid) -- is the actual content of a greedy problem; the algorithm itself is often three lines. Building on straightforward greedy exchange arguments, these two subtopics sharpen the central judgment call of greedy algorithm design: Huffman coding and optimal-merge show a provably correct greedy merge order and exactly where an adjacency constraint breaks it, while fractional-vs-0/1 recognition trains the instinct for telling a genuinely greedy problem apart from one that only looks like it until you try a concrete counterexample.

Interval Scheduling and Its Generalizations

2 worked examples

The base case is activity selection: given intervals, select the maximum number that pairwise don't overlap. The greedy rule is to sort by right endpoint ascending and repeatedly take the next interval whose start is at or after the end of the last taken one. The exchange argument: let G be the greedy selection and O be any optimal selection, both sorted by start time. Compare their first picks -- greedy's first interval ends no later than O's first interval (by choice of sort key), so swapping O's first pick for greedy's first pick cannot cause any conflict with the rest of O's picks (they all start after O's original first pick ends, hence after greedy's earlier-ending pick too), and the swap doesn't reduce the count. Repeating this argument down the list shows greedy's count is never less than optimal's, so greedy is optimal.

The technique generalizes past a single resource. With k identical resources (e.g. k people who can each watch one movie at a time), still sort by end time, but now maintain a multiset of each resource's current 'free time'. For each interval, among all resources free at or before its start, assign it to the one with the LARGEST such free time (i.e. the one that just barely became free), not an arbitrary one. The exchange argument here is subtler: assigning to the 'just barely free' resource strictly maximizes the free time left on every OTHER resource, which is a Pareto-dominant state -- any assignment achievable from a worse choice is still achievable from this one, so it can never be strictly worse for future intervals, and by induction the total count is maximized.

A further generalization drops 'select a subset of intervals' in favor of 'choose points so every interval contains enough of them' (the dual, or 'stabbing', formulation). For 'every interval must contain at least two chosen points', sort by right endpoint again, and when an interval is under-covered, add new points as far RIGHT as possible (at the interval's own right endpoint, and the position just before it if two points are needed at once). The proof that 'rightmost is safe' is again an exchange argument: any valid solution can have its points shifted rightward, one at a time, up to the boundary imposed by the current interval's right endpoint, without ever removing coverage of intervals already processed (since those all end at or before the current right endpoint) and only helping with intervals still to come (which end even further right). This is considerably subtler than plain stabbing because a single new point can satisfy many future intervals at once, so being greedy about WHERE exactly to place it matters much more than in the one-point-per-interval case.

Recognize it by

Look for the words 'maximum number of non-overlapping', 'minimum points/resources to cover/hit all intervals', or 'schedule as many as possible given start/end times' -- these are almost always solved by sorting on one endpoint. The danger sign is when intervals carry an extra VALUE or WEIGHT and the goal is to maximize total value rather than total count: plain earliest-end-time greedy provably fails there (a short, low-value interval can block a long, high-value one), and you need weighted interval scheduling (DP with binary search) instead. Another danger sign is heterogeneous resources (e.g. k machines with different speeds, or intervals that can only be served by some subset of resources) -- the 'assign to the resource that frees up latest but still in time' trick assumes resources are interchangeable, and breaks without that assumption.

Complexity

O(n log n) for sorting plus O(log n) per greedy step if a heap/multiset/BIT is needed (k-resource and stabbing variants); O(n) once sorted for the plain single-resource case.

Movie Festival with k Club Members

Problem

A festival shows n movies; movie i runs on the half-open interval [s_i, e_i) (a member can start a new movie exactly when their previous one ends). A club has k members who can each watch at most one movie at a time, but different members may watch different movies simultaneously. No movie may be watched by more than one member (watching it twice doesn't count twice). Maximize the total number of movie-viewings (i.e. the number of movies that get watched by at least one member). Input: first line 'n k', then n lines each 's e'. Output: the maximum number of movies watched.

Approach

Sort movies by end time ascending (ties by start time). Maintain a multiset of the k members' current free times, initialized to 0. For each movie (s, e) in sorted order, look for a member whose free time is <= s; among all such members, pick the one with the LARGEST free time (found via upper_bound(s) then stepping back one position in the multiset). If such a member exists, assign the movie to them (remove their old free time, insert e) and count it; otherwise skip the movie. Correctness: processing by end time ensures we always resolve the 'tightest' movie first, exactly as in single-resource interval scheduling. Choosing the member who is free LATEST (but still in time) rather than the one free earliest is the key exchange step -- it leaves every other member's free time untouched at its (possibly earlier, more flexible) value, so the resulting configuration of free times is componentwise <= any alternative valid assignment's free times. Since a componentwise-smaller multiset of free times can only make it easier to satisfy every subsequent movie, an induction over the sorted order shows this greedy choice never loses to any other feasible assignment, so the final count is optimal.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; long long k;
    cin >> n >> k;
    vector<pair<int,int>> mv(n);
    for (auto &p : mv) cin >> p.first >> p.second;
    sort(mv.begin(), mv.end(), [](const pair<int,int>&a, const pair<int,int>&b){
        if (a.second != b.second) return a.second < b.second;
        return a.first < b.first;
    });
    multiset<int> freeTimes;
    for (int i = 0; i < k; i++) freeTimes.insert(0);
    int count = 0;
    for (auto &p : mv) {
        int s = p.first, e = p.second;
        auto it = freeTimes.upper_bound(s);
        if (it == freeTimes.begin()) continue;
        --it;
        freeTimes.erase(it);
        freeTimes.insert(e);
        count++;
    }
    cout << count << endl;
}

Covering Every Interval with at Least Two Points

Problem

You are given n closed integer intervals [l_i, r_i] with r_i - l_i >= 1. Find the minimum-size set S of integers such that every interval contains at least 2 elements of S. Input: first line n, then n lines each 'l r'. Output: the minimum size of S.

Approach

Sort intervals by right endpoint ascending (ties by left endpoint ascending). Track only the two largest points chosen so far, p1 <= p2 (initialized to -infinity). For the current interval [l, r]: count how many of {p1, p2} are >= l -- since points are only ever added in non-decreasing order and all previously added points are <= every previously processed r <= current r, p1 and p2 are exactly the relevant candidates already inside [., r]. If both are >= l, the interval is already satisfied. If only p2 >= l, add one more point at r (the rightmost legal position), shifting p1 <- p2, p2 <- r. If neither is >= l, add two new points at r-1 and r. Correctness (exchange argument): whenever a new point must be added to satisfy the current interval, adding it as far RIGHT as legally possible (at r, or at r-1 and r) can only help every future interval, since all future intervals have right endpoint >= r and their left endpoints have not been tested yet. Formally, given any optimal solution, repeatedly shift its rightmost usable point(s) for the current interval to r without ever losing coverage of intervals already finalized (all of which end at or before r); this transforms any optimal solution into one that agrees with this greedy choice at every step, without increasing its size, so the greedy count matches the true minimum.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin >> n;
    vector<pair<int,int>> iv(n);
    for (auto &p : iv) cin >> p.first >> p.second;
    sort(iv.begin(), iv.end(), [](const pair<int,int>&a, const pair<int,int>&b){
        if (a.second != b.second) return a.second < b.second;
        return a.first < b.first;
    });
    long long p1 = LLONG_MIN, p2 = LLONG_MIN;
    long long total = 0;
    for (auto &p : iv) {
        int l = p.first, r = p.second;
        int cnt = (p1 >= l) + (p2 >= l);
        if (cnt == 2) continue;
        else if (cnt == 1) { p1 = p2; p2 = r; total += 1; }
        else { p1 = r - 1; p2 = r; total += 2; }
    }
    cout << total << endl;
}

Exchange-Argument Scheduling Order

3 worked examples

Many problems ask for the best ORDER in which to process a fixed set of items, where the objective is some sum or set of local constraints over the resulting sequence. The standard proof technique is the adjacent-swap exchange argument: assume an optimal order exists; if it ever places two adjacent items in an order that disagrees with the proposed greedy sort key, show that swapping those two adjacent items cannot make the objective worse. Applying this repeatedly (essentially a bubble-sort argument) morphs any optimal order into the fully-sorted greedy order without ever hurting the objective, proving the greedy order is at least as good as any order.

A classic instance: given tasks with durations and deadlines, processed one after another with 'finish time' = cumulative duration so far, and reward = deadline - finish_time summed over all tasks, maximize total reward. Summing the reward formula, total = (sum of all deadlines) - (sum of all finish times); the first term is a CONSTANT independent of order, so maximizing total reward is exactly minimizing the sum of finish times -- and it is a textbook fact (provable by the same adjacent-swap argument) that the sum of completion times over a sequential single-server schedule is minimized by shortest-processing-time-first (SPT) order. The deadlines, despite appearing in the objective, are entirely irrelevant to the optimal ORDER; they only shift every solution's score by the same constant. Missing this and trying to sort by deadline is a natural but incorrect first instinct.

A second flavor concerns simultaneous LOCAL constraints rather than a global sum: e.g., assign each position in a line a value such that any position with a higher priority than a neighbor must get a strictly larger value than that neighbor, minimizing the total. Here a single left-to-right or right-to-left greedy pass provably cannot satisfy both directions of constraint at once (a peak needs to satisfy both its left and right neighbor simultaneously). The trick is to solve each DIRECTION of the constraint independently and optimally with one monotone pass each, then combine the two independently-optimal partial solutions by taking the pointwise maximum. This is valid because each pass's result is a valid lower bound satisfying its own direction of constraints, and pointwise-max of two lower bounds still satisfies both directions simultaneously, while being provably no larger than any valid combined assignment (which must itself dominate both passes' lower bounds pointwise).

A third flavor computes a closed-form MINIMUM by identifying the single hardest structural bottleneck (e.g. the largest single item) plus the trivial aggregate lower bound (e.g. the total workload), and shows the max of these two simple bounds is always achievable by a suitable construction -- turning what looks like a hard bin-balancing / partition problem into an O(n) formula, because the specific combinatorial structure (e.g. 'both workers must eventually do all of the same work, just staggered to avoid a resource clash') rules out the usual NP-hardness of general two-machine partition.

Recognize it by

Recognize this pattern when the objective is a SUM over positions/finish-times (minimize/maximize sum of completion times, weighted completion times, lateness sums) or when there are purely LOCAL pairwise constraints between adjacent elements. The giveaway that greedy-by-obvious-key might be wrong is when the objective is a MAX or BOTTLENECK rather than a SUM -- minimizing maximum lateness needs sorting by deadline (earliest-deadline-first), a completely different rule from minimizing summed lateness, and confusing sum-objectives with max-objectives is the most common way this family of greedy breaks. Always redo the adjacent-swap argument for your exact objective rather than pattern-matching to a memorized sort key.

Complexity

O(n log n) for the sort, O(n) for the pass(es) that follow.

Tasks and Deadlines

Problem

You are given n tasks; task i has duration d_i and deadline t_i. You process all n tasks one at a time, in an order of your choosing, on a single machine with no idle time. If a task finishes at time f (cumulative sum of durations of all tasks processed up to and including it), its reward is t_i - f (rewards may be negative). Maximize the sum of all rewards. Input: first line n, then n lines each 'duration deadline'. Output: the maximum total reward.

Approach

Sort tasks by duration ascending only (the deadlines never affect the ordering decision). Simulate the schedule in that order, tracking a running 'finish' time; for each task add its deadline minus the updated finish time to the total. Correctness: total reward = sum(deadlines) - sum(finish times), and sum(deadlines) is a constant regardless of processing order, so maximizing total reward is equivalent to minimizing sum(finish times). By the adjacent-swap argument, if two adjacent tasks in some order have the earlier one longer than the later one, swapping them decreases both of their finish times' contribution to the sum (and leaves every other task's finish time unchanged), so sorting fully by ascending duration (shortest processing time first, SPT) minimizes the sum of finish times among all orders.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin >> n;
    vector<pair<long long,long long>> t(n);
    for (auto &p : t) cin >> p.first >> p.second;
    sort(t.begin(), t.end());
    long long finish = 0, total = 0;
    for (auto &p : t) {
        finish += p.first;
        total += p.second - finish;
    }
    cout << total << endl;
}

Two Readers, Every Book Read Twice

Problem

There are n books; book i takes t_i time to read. Two people must EACH read every one of the n books (both need to finish all n, not split the set between them), each reading in whatever order they choose, working continuously with no idle time until they personally finish all n books. The only restriction: the same book cannot be read by both people at the same moment (though the two people may read two DIFFERENT books simultaneously). Find the minimum time until both people have finished reading all n books. Input: first line n, second line n integers t_1..t_n. Output: the minimum total time.

Approach

Compute S = sum of all t_i and M = max t_i. The answer is max(2*M, S). Two independent lower bounds force this: (1) each person individually spends S total time reading (they read every book once), so the finish time of either person is at least S; (2) the single longest book, of length M, must be read once by each person, and those two M-length intervals cannot overlap in time (same-book clash), so they occupy two disjoint length-M windows somewhere in the timeline, forcing the timeline to span at least 2*M. A matching construction (e.g., have the two readers proceed through a cyclic rotation of the same reading order, offset so that whenever one of them is on a given book the other is always on a different one, inserting idle time only around the longest book if 2*M > S) achieves exactly max(2*M, S), so this closed form is tight in both directions. Note the edge case n=1: S=M so the formula gives 2*M, correctly capturing that with only one book, the second reader must wait for the first to finish entirely before starting.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin >> n;
    vector<long long> t(n);
    for (auto &x : t) cin >> x;
    long long sum = 0, mx = 0;
    for (auto x : t) { sum += x; mx = max(mx, x); }
    cout << max(2 * mx, sum) << endl;
}

Candy Distribution

Problem

There are n children in a line, each with a rating r_i. Each child must receive at least 1 candy. Any child with a strictly higher rating than an immediate neighbor must receive strictly more candies than that neighbor. Find the minimum total number of candies needed. Input: first line n, second line n integers (ratings). Output: the minimum total candies.

Approach

Do two independent monotone passes. Left pass: left[0]=1; for i from 1 to n-1, left[i] = left[i-1]+1 if r[i] > r[i-1], else 1. This pass alone correctly satisfies every LEFT-neighbor constraint but ignores right-neighbor constraints. Right pass: right[n-1]=1; for i from n-2 down to 0, right[i] = right[i+1]+1 if r[i] > r[i+1], else 1 -- this alone satisfies every RIGHT-neighbor constraint. Take answer[i] = max(left[i], right[i]) for every i and sum. Correctness: any valid assignment must be >= left[i] (because the left-pass recurrence is forced by the left-neighbor constraints alone, taking the minimum candies consistent with them) and simultaneously >= right[i] (same argument for the right side), so answer[i] = max(left[i], right[i]) is a valid lower bound at every position. It is also achievable: one can check that this pointwise maximum still satisfies BOTH constraint directions at every position (an increase relative to one pass's baseline of 1 never breaks that pass's own recurrence, since the recurrence only demands a value strictly greater than the appropriate neighbor's baseline, and taking the max preserves the needed gap), so it is simultaneously a valid assignment and pointwise minimal, hence globally minimal in sum.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin >> n;
    vector<int> r(n);
    for (auto &x : r) cin >> x;
    vector<int> left(n,1), right(n,1);
    for (int i = 1; i < n; i++) if (r[i] > r[i-1]) left[i] = left[i-1] + 1;
    for (int i = n-2; i >= 0; i--) if (r[i] > r[i+1]) right[i] = right[i+1] + 1;
    long long total = 0;
    for (int i = 0; i < n; i++) total += max(left[i], right[i]);
    cout << total << endl;
}

Greedy Combined with a Priority Structure (Heaps and DSU)

2 worked examples

Some greedy problems need to REVISE an earlier commitment once better information arrives, rather than committing once and moving on. The canonical example is stock trading where you may buy or sell exactly one share per day (never short), maximizing total profit: maintain a min-heap of 'prices used as a buy so far'. For each new price p, if p is greater than the heap's minimum, bank the difference as profit, pop that minimum, and then push p back onto the heap as if the share had been re-bought at price p -- in addition to always pushing p itself unconditionally. This lets the SAME transaction slot be revised again later if an even better price shows up, effectively 'undoing' a previous sale-and-rebuy chain. The correctness argument is an accounting/telescoping one: any feasible sequence of at-most-one-operation-per-day buy/sell actions can be decomposed into a multiset of (buy-day, sell-day) pairs with buy price < sell price, and one can show by induction that the heap's running total after processing the first k prices always equals the maximum achievable profit using only those k days -- because the 'resell through the heap' operation is exactly what's needed to convert a locally-optimal decomposition using the first k-1 prices into a locally-optimal decomposition using k prices, without ever needing to look back further than the current heap state.

A second, very different priority-structure greedy solves deadline-constrained scheduling: n jobs each take one unit of time, job i has a deadline d_i (must run in some integer slot from 1 to d_i) and a profit p_i; only one job may run per slot; maximize total profit of scheduled jobs. Sort jobs by profit DESCENDING, and for each job find the LATEST still-free slot at or before its deadline (a Union-Find structure where find(t) returns the latest free slot <= t makes this near O(1) amortized: when a slot is used, union it with the slot one earlier). Placing a job as LATE as possible rather than as early as possible is deliberate: it reserves every earlier slot for jobs with tighter deadlines that we haven't seen yet (since we're iterating by profit, not by deadline). This is a direct instance of the matroid-greedy theorem: the collection of 'schedulable subsets of jobs' (there's an assignment of each job in the subset to a distinct slot at or before its own deadline) forms the independent sets of a transversal matroid, and it is a general fact that scanning elements in decreasing weight order and greedily adding each one whenever it keeps the current set independent produces a maximum-weight independent set -- no case analysis on deadlines is needed beyond verifying the matroid axioms once.

Recognize it by

Look for an explicit 'one operation per unit time' or 'process a stream, react as better options appear' framing -- that is the heap/regret pattern. Look for 'maximize total value, each item needs a slot before some deadline, one item per slot' -- that is the DSU/matroid pattern. Danger sign for the heap-regret trick specifically: it relies on the objective decomposing into pairwise, telescoping differences (buy-then-sell spreads); adding transaction fees, cooldown periods, or a hard cap on the total number of transactions usually breaks the trick and pushes the problem toward DP instead. Danger sign for the DSU/matroid pattern: it assumes each job takes exactly one uniform time unit and any slot works equally well; jobs with different durations turn this into interval/knapsack-scheduling, which the transversal-matroid argument no longer covers.

Complexity

O(n log n) for the heap approach (each price pushed/popped a bounded number of times). O((n + D) alpha(D)) for the DSU job-scheduling approach, where D is the maximum deadline and alpha is the inverse Ackermann function; O(n log n) if a heap of free slots is used instead of DSU.

Buy Low Sell High

Problem

You know the stock price for each of the next n days. On each day you may do at most one of: buy exactly one share, sell exactly one share you currently own, or nothing. You may never sell a share you don't own (no short selling), but you may hold any number of shares simultaneously. Maximize total profit (sum of sell prices minus sum of buy prices) over the n days. Input: first line n, second line n integers (prices). Output: the maximum achievable profit.

Approach

Maintain a min-heap. For each day's price p, if the heap is non-empty and p is greater than the heap's minimum, add (p - heap.top()) to the profit, pop that minimum, and push p (representing 'resold and immediately re-bought at p', keeping this slot available for an even better future price); then, regardless, push p onto the heap unconditionally (representing 'p is also available as a fresh potential buy price'). The running total after processing all n days equals the optimal profit under the one-operation-per-day rule. Intuition/verification for the sample (prices 1, 2, 100): day 1 pushes 1; day 2 sees 2 > 1, banks profit 1, and the heap ends up holding {2,2}; day 3 sees 100 > 2, banks profit 98, total 99 -- matching the manual optimum of buying at 1 and selling at 100 while day 2 is left unused (any alternative use of day 2, such as buying a second share, wastes a transaction since only one share can be sold on day 3).

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin >> n;
    vector<long long> a(n);
    for (auto &x : a) cin >> x;
    priority_queue<long long, vector<long long>, greater<long long>> pq;
    long long profit = 0;
    for (long long p : a) {
        if (!pq.empty() && p > pq.top()) {
            profit += p - pq.top();
            pq.pop();
            pq.push(p);
        }
        pq.push(p);
    }
    cout << profit << endl;
}

Job Sequencing with Deadlines

Problem

There are n jobs; job i has a profit p_i and a deadline d_i (it must be scheduled in some integer time slot from 1 to d_i, inclusive). Every job takes exactly one unit of time, and at most one job may be scheduled in each time slot. Choose a subset of jobs and an assignment of each chosen job to a distinct slot at or before its deadline, to maximize the total profit of scheduled jobs. Input: first line n, then n lines each 'profit deadline'. Output: the maximum achievable total profit.

Approach

Sort jobs by profit descending. Maintain a Union-Find over slots 0..maxDeadline, where find(t) returns the latest free slot <= t (slot 0 is a sentinel meaning 'no slot available'). For each job in profit order, let slot = find(deadline); if slot > 0, take the job (add its profit) and mark that slot used by unioning it to slot-1 (so future queries skip past it). This is the matroid-greedy theorem applied to the transversal matroid of 'sets of jobs schedulable given their deadlines': scanning in decreasing weight order and adding each job whenever doing so keeps the current set independent (i.e., still schedulable, checked here via the DSU slot search) is guaranteed to produce a maximum-weight independent set. Tracing the sample: jobs sorted by profit are (100,d2),(27,d2),(25,d1),(19,d1),(15,d3). Job(100,d2) takes slot 2; job(27,d2) takes slot 1 (slot 2 now taken); job(25,d1) and job(19,d1) find no free slot at or before 1 and are skipped; job(15,d3) takes slot 3. Total profit = 100+27+15 = 142.

Solution
#include <bits/stdc++.h>
using namespace std;
vector<int> parent_;
int find(int x){
    if (parent_[x] == x) return x;
    return parent_[x] = find(parent_[x]);
}
int main(){
    int n; cin >> n;
    vector<pair<int,int>> jobs(n);
    int maxD = 0;
    for (auto &j : jobs) { cin >> j.first >> j.second; maxD = max(maxD, j.second); }
    sort(jobs.begin(), jobs.end(), [](const pair<int,int>&a, const pair<int,int>&b){
        return a.first > b.first;
    });
    parent_.resize(maxD + 1);
    for (int i = 0; i <= maxD; i++) parent_[i] = i;
    long long total = 0;
    for (auto &j : jobs) {
        int profit = j.first, deadline = j.second;
        int slot = find(deadline);
        if (slot > 0) {
            total += profit;
            parent_[slot] = slot - 1;
        }
    }
    cout << total << endl;
}

Reducing to a Minimum Spanning Tree

2 worked examples

Kruskal's and Prim's algorithms are the archetypal matroid greedy: process edges by increasing weight and add an edge whenever it doesn't close a cycle. Correctness follows from two classical facts. The CUT PROPERTY: for any cut (partition of vertices into two nonempty sets), the minimum-weight edge crossing it belongs to SOME minimum spanning tree -- so it is always safe to greedily add the cheapest crossing edge. The CYCLE PROPERTY: the maximum-weight edge on any cycle is never NEEDED in a minimum spanning tree -- so Kruskal's rule of skipping an edge that would close a cycle never discards something essential. Together these show that Kruskal produces a spanning tree whose total weight cannot be beaten by any other spanning tree, i.e. it's minimum; formally this is exactly the greedy-algorithm theorem for the graphic matroid, where independent sets are forests.

What makes some problems 'greedy reductions to MST' is that they don't look like graph problems at all until you find the right transformation. A frequent pattern: each element can either pay a fixed 'go it alone' cost, or pay a pairwise cost to piggyback on some other already-covered element -- and at least one element must ultimately be self-sufficient (directly or transitively). The trick is to introduce one virtual node, connect it to every real node with an edge weighted by that node's stand-alone cost, and connect every pair of real nodes with an edge weighted by their pairwise piggyback cost; a Minimum Spanning Tree of this augmented graph is then EXACTLY the optimal solution -- any spanning tree corresponds to a valid assignment (nodes directly connected to the virtual node build their own facility; every other node is connected via wires, transitively reaching some facility through the tree), and conversely any valid assignment yields a spanning tree of the same total cost. The correctness of Kruskal/Prim on the transformed graph is then inherited for free; all of the actual insight is in justifying that this bijection (or at least cost equivalence) between feasible original-problem solutions and spanning trees holds.

Recognize it by

Watch for a 'take a fixed local action, OR connect to any other element by paying a pairwise cost, and everything must end up connected (directly or transitively) to at least one element that took the local action' structure -- that is exactly the virtual-source-to-MST reduction. This shows up in facility-location-flavored problems ('build your own vs. share a neighbor's'), network design, and clustering problems. Danger sign: the reduction needs symmetric, uncapacitated connections (any node may attach to any other node, and any number of nodes may share one hub); once directed costs, per-hub capacity limits, or flow-style constraints are introduced, the clean equivalence with an unconstrained MST breaks and a different tool (e.g. min-cost flow) is usually required instead.

Complexity

O(E log E) (Kruskal with sorting) or O(E log V) (Prim with a binary heap), where E is the number of edges and V the number of vertices. Virtual-source constructions are often dense (all pairs of n real nodes plus n edges to the virtual node give O(n^2) edges), yielding O(n^2 log n) with Kruskal, improvable to O(n^2) with array-based Prim.

Minimum Cost to Connect All Computers

Problem

There are n computers and m candidate cables; cable j connects computers u_j and v_j at cost w_j (the candidate cables are guaranteed to make the network connectable). Choose a subset of cables of minimum total cost so that every computer is connected to every other computer (directly or through other computers). Input: first line 'n m', then m lines each 'u v w' (1-indexed computers). Output: the minimum total cost.

Approach

This is literally Minimum Spanning Tree: run Kruskal's algorithm -- sort all m candidate cables by weight ascending, use a Union-Find to add each cable only if its two endpoints are currently in different components, and sum the weights of added cables. By the cut property, the cheapest cable crossing any still-disconnected boundary is always safe to add, so this produces the minimum-cost fully-connecting set of cables. On the sample (4 computers; edges of weight 1,2,3,4,5), sorted order 1,2,3 connect all 4 computers first (edges (1,2),(2,3),(3,4)), so the remaining, more expensive edges (weight 4 and 5) are skipped as they would only close cycles; total cost = 1+2+3 = 6.

Solution
#include <bits/stdc++.h>
using namespace std;
int parent_[100005], rnk_[100005];
int find(int x){ return parent_[x] == x ? x : parent_[x] = find(parent_[x]); }
bool unite(int a, int b){
    a = find(a); b = find(b);
    if (a == b) return false;
    if (rnk_[a] < rnk_[b]) swap(a, b);
    parent_[b] = a;
    if (rnk_[a] == rnk_[b]) rnk_[a]++;
    return true;
}
int main(){
    int n, m; cin >> n >> m;
    vector<array<long long,3>> edges(m);
    for (auto &e : edges) {
        long long u, v, w; cin >> u >> v >> w;
        e = {w, u, v};
    }
    sort(edges.begin(), edges.end());
    for (int i = 1; i <= n; i++) { parent_[i] = i; rnk_[i] = 0; }
    long long total = 0;
    for (auto &e : edges) {
        long long w = e[0], u = e[1], v = e[2];
        if (unite((int)u, (int)v)) total += w;
    }
    cout << total << endl;
}

Power Grid: Build a Station or Wire to a Neighbor

Problem

There are n cities on a 2D grid; city i is at (x_i, y_i) and building its own power station there costs c_i. Alternatively, a wire can be built between any two cities i and j at cost k times their Manhattan distance |x_i - x_j| + |y_i - y_j|. Every city must ultimately be powered: either it has its own station, or it is connected (directly or transitively, through wires and other powered cities) to some city that has a station. Find the minimum total cost (stations plus wires) to power every city. Input: first line 'n k', then n lines each 'x y c'. Output: the minimum total cost.

Approach

Introduce a virtual node 0 representing 'the power source'. Add an edge from node 0 to city i with weight c_i (building a station is modeled as 'wiring to the free, always-on virtual source'). Add an edge between every pair of cities i, j with weight k times their Manhattan distance. Run Kruskal/Prim to find the Minimum Spanning Tree of this (n+1)-node graph; its total weight is the minimum total cost. Correctness: any valid station/wire assignment for the original problem corresponds exactly to a spanning tree of the augmented graph rooted at node 0 (edges to node 0 are the stations that get built, all other tree edges are wires), and vice versa -- any spanning tree of the augmented graph gives a valid assignment of the same cost, since every city is reachable from node 0 through some path of real or virtual edges. So the MST of the augmented graph is precisely the optimal answer, and MST correctness (cut/cycle properties) transfers over automatically. On the sample (3 cities at (0,0),(1,0),(2,0), all with station cost 10, k=1): wiring city1-city2 costs 1 and city2-city3 costs 1 (much cheaper than three separate 10-cost stations), then one more edge to node 0 (cost 10, from any of the three cities) connects the whole wired cluster to the source; total = 1+1+10 = 12.

Solution
#include <bits/stdc++.h>
using namespace std;
int parent_[205];
int find(int x){ return parent_[x] == x ? x : parent_[x] = find(parent_[x]); }
bool unite(int a, int b){
    a = find(a); b = find(b);
    if (a == b) return false;
    parent_[a] = b;
    return true;
}
int main(){
    int n; long long k;
    cin >> n >> k;
    vector<long long> x(n+1), y(n+1), c(n+1);
    for (int i = 1; i <= n; i++) cin >> x[i] >> y[i] >> c[i];
    vector<array<long long,3>> edges;
    for (int i = 1; i <= n; i++) edges.push_back({c[i], 0, i});
    for (int i = 1; i <= n; i++)
        for (int j = i+1; j <= n; j++) {
            long long d = llabs(x[i]-x[j]) + llabs(y[i]-y[j]);
            edges.push_back({k*d, i, j});
        }
    sort(edges.begin(), edges.end());
    for (int i = 0; i <= n; i++) parent_[i] = i;
    long long total = 0;
    for (auto &e : edges) {
        if (unite((int)e[1], (int)e[2])) total += e[0];
    }
    cout << total << endl;
}

Huffman Coding & Optimal Merge

2 worked examples

Huffman coding builds an optimal binary prefix-free code for a set of symbol frequencies by repeatedly merging the two SMALLEST remaining weights into one combined weight (paying a cost equal to their sum) and pushing the combined weight back into the pool, until a single weight remains. This greedy rule is provably optimal by an exchange argument: in any optimal Huffman tree, the two least-frequent symbols can always be placed as siblings at the deepest level without increasing the total weighted path length, so merging them first loses nothing and the same argument applies recursively to the resulting smaller instance. A priority queue (min-heap) makes this greedy merge run in O(n log n): pop the two smallest weights, push their sum, and accumulate that sum into a running total cost -- the final total is exactly the minimum possible sum of (frequency * code length) over all valid prefix-free binary codes, which is also exactly the answer to the more general 'optimal merge cost' problem (minimize total cost to combine n items pairwise, where combining two items of weight a and b costs a+b).

The greedy priority-queue approach generalizes cleanly to K-ARY merges (combine the K smallest weights at a time instead of 2) as long as the only constraint is 'pick any K items, of any positions, to merge next' -- this is still solvable by always grabbing the K globally smallest weights from a heap (after padding with zero-weight dummy items if needed so the merge count divides evenly). However, the moment an ADJACENCY constraint is added -- e.g. 'you may only merge K items that are currently CONSECUTIVE in the original row/array' -- the greedy 'always take the smallest' argument breaks completely, because the smallest available weights might not be next to each other, and merging them anyway is simply illegal. This adjacency-constrained version needs INTERVAL DP instead: dp[l][r] tracks the minimum cost to merge the contiguous range [l, r] down to the fewest piles reachable under the K-at-a-time rule (exactly 1 + (r - l) mod (K-1) piles), built by trying every valid split point and, when a full K-way merge of the whole range is legal, adding the range's total sum as the final merge's cost.

Recognizing which regime you are in -- unconstrained 'always merge globally smallest' (greedy, priority queue) versus adjacency-constrained or otherwise structurally restricted merging (interval DP) -- is the single most important skill this subtopic tests, since the two problem statements can look deceptively similar while requiring completely different algorithms.

Recognize it by

The problem asks to combine n items pairwise (or K at a time) into one, where each combination costs the sum of the pieces being combined, and you want to minimize (or the problem directly names) total Huffman/prefix-code length or 'optimal merge cost' -- if merges may pick ANY items regardless of position, it is the classical greedy priority-queue algorithm. The moment the problem restricts merges to CONSECUTIVE/adjacent elements (or adds any other cost term beyond a pure sum, such as a positional penalty), the greedy argument no longer applies and interval DP is required instead.

Complexity

O(n log n) for the greedy priority-queue Huffman/optimal-merge algorithm; O(n^2) to O(n^2 * K) for the adjacency-constrained interval DP variant (K-way merge of contiguous ranges), depending on how the split points are enumerated.

Minimum Total Huffman Code Length

Problem

You are given the frequencies of n distinct symbols (2 <= n <= 10^5, 1 <= frequency <= 10^9). Construct an optimal binary prefix-free (Huffman) code for these symbols and output the minimum possible total encoded length, i.e. the sum over all symbols of (frequency of the symbol) * (length of its assigned binary code).

Input: n, then n integers (the frequencies).
Output: the minimum total encoded length.

Approach

Push all n frequencies into a min-heap. While more than one element remains, pop the two smallest values a and b, add (a+b) to a running total cost, and push (a+b) back into the heap -- this is the classical Huffman merge. The final running total is exactly the minimum total encoded length, because each symbol's frequency gets added into the running total once for every merge along the path from its leaf up to the root of the eventual Huffman tree, which is precisely frequency * (depth in the tree) = frequency * (code length). Verified against the well-known textbook example (frequencies 5, 9, 12, 13, 16, 45), which is documented to have an optimal total encoded length of 224 -- the implementation reproduces this exactly.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin>>n;
    priority_queue<long long, vector<long long>, greater<long long>> pq;
    for(int i=0;i<n;i++){ long long f; cin>>f; pq.push(f); }
    if(n==1){ cout << pq.top() << endl; return 0; }
    long long total = 0;
    while(pq.size()>1){
        long long a = pq.top(); pq.pop();
        long long b = pq.top(); pq.pop();
        long long merged = a+b;
        total += merged;
        pq.push(merged);
    }
    cout << total << endl;
}

Minimum Cost to Merge K Adjacent Piles (where the Huffman greedy fails)

Problem

You are given n piles of stones in a row (1 <= n <= 30), pile i having stones[i] stones (1 <= stones[i] <= 100), and an integer K (2 <= K <= n). In one move you may merge EXACTLY K CONSECUTIVE piles into a single new pile; the cost of that move equals the total number of stones in those K piles, and after the merge those K piles are replaced by the one combined pile (so future merges see the new, shorter row). Find the minimum total cost to merge the entire row down to a single pile, or report -1 if it is impossible.

Input: n and K, then n integers stones[1..n].
Output: the minimum total cost, or -1 if merging down to one pile is impossible.

Approach

First, a merge sequence can only ever reduce the number of piles by (K-1) per move, so reaching exactly 1 pile from n is only possible when (n-1) is divisible by (K-1); otherwise output -1 immediately. Otherwise, this is the adjacency-constrained generalization of Huffman/optimal-merge, and the greedy 'always merge the K globally smallest piles' rule from ordinary Huffman coding does NOT apply, because the K smallest-valued piles are almost never K consecutive piles in the row -- interval DP is required instead.

Let dp[i][j] = the minimum cost to merge the piles in range [i, j] down to the FEWEST piles reachable under the K-at-a-time rule, which is always exactly 1 + ((j-i) mod (K-1)) piles (a consequence of each merge removing exactly K-1 piles). Compute it by increasing range length: dp[i][j] = min over mid stepping by (K-1) from i up to (but not including) j of dp[i][mid] + dp[mid+1][j] (splitting the range into a left part that can be fully reduced to its minimal pile count, and a right remainder). Whenever (j - i) is itself a multiple of (K-1), the range [i, j] can additionally be fully collapsed into exactly ONE final pile with one more K-way merge, so add the full range sum (prefix-sum precomputed) to dp[i][j] in that case. The answer is dp[0][n-1]. Verified against all three official LeetCode 'Minimum Cost to Merge Stones' examples: stones=[3,2,4,1],K=2 -> 20; stones=[3,2,4,1],K=3 -> -1; stones=[3,5,1,2,6],K=3 -> 25 -- all three match exactly.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n, K;
    cin >> n >> K;
    vector<long long> a(n);
    for (auto &x : a) cin >> x;
    if ((n-1) % (K-1) != 0) { cout << -1 << endl; return 0; }
    vector<long long> pre(n+1, 0);
    for (int i = 0; i < n; i++) pre[i+1] = pre[i] + a[i];
    auto rangeSum = [&](int i, int j){ return pre[j+1]-pre[i]; };
    const long long INF = LLONG_MAX/2;
    vector<vector<long long>> dp(n, vector<long long>(n, 0));
    for (int len = 2; len <= n; len++) {
        for (int i = 0; i + len - 1 < n; i++) {
            int j = i + len - 1;
            dp[i][j] = INF;
            for (int mid = i; mid < j; mid += (K-1)) {
                dp[i][j] = min(dp[i][j], dp[i][mid] + dp[mid+1][j]);
            }
            if ((j - i) % (K-1) == 0) {
                dp[i][j] += rangeSum(i, j);
            }
        }
    }
    cout << dp[0][n-1] << endl;
}

Fractional vs. 0/1 Greedy Recognition

2 worked examples

The fractional knapsack theorem states: if items are DIVISIBLE (you may take any fraction of an item's weight and receive that same fraction of its value), then sorting items by value-to-weight ratio (descending) and greedily filling the capacity -- taking each item fully while it fits, and topping off the very last item with whatever fraction of capacity remains -- produces the provably optimal total value. The proof is a clean exchange argument: given any solution that doesn't follow this order, you can always shift an infinitesimal amount of weight from a lower-ratio item to a higher-ratio item without violating the capacity constraint, strictly increasing total value, showing any non-greedy solution cannot be optimal.

The moment items become INDIVISIBLE (0/1 knapsack: take an item entirely or not at all), this exact exchange argument breaks down, because you can no longer 'top off' the last item with an arbitrarily small fraction -- you either take the whole item (possibly overshooting the remaining capacity) or skip it entirely (possibly wasting capacity that a different, lower-ratio combination could have used more fully). A classic concrete counterexample: capacity 50, items (weight=10, value=60), (weight=20, value=100), (weight=30, value=120). Sorted by ratio (6, 5, 4), greedy 0/1 selection takes item 1 (10/60) then item 2 (20/100), filling 30 of the 50 capacity for 160 total value, and cannot fit item 3 -- but the true optimal 0/1 selection is items 2 and 3 together (weight 50 exactly, value 220), which the ratio-greedy never considers because it commits to the top-ratio item early and never revisits that choice. The correct approach for 0/1 knapsack is a DP over remaining capacity: dp[c] = best value achievable with total weight <= c, updated item by item in decreasing order of c (to avoid reusing an item twice within the same pass).

More generally, greedy-by-ratio (or greedy-by-any-local-comparison) tends to be PROVABLY correct exactly when the underlying structure has a matroid-like exchange property (as in fractional knapsack, or Kruskal's MST algorithm, or scheduling problems built from freely swappable atomic units) -- and tends to FAIL exactly when an indivisibility constraint, an exact-size/exact-count constraint, or some other rigid combinatorial restriction prevents the small local exchange step that the greedy's correctness proof relies on. A fast diagnostic: try to construct a small counterexample by hand where greedy's answer differs from a brute-force or DP answer; if you can, greedy is wrong for that variant and you need DP (or a more careful combinatorial argument) instead.

Recognize it by

If the problem explicitly allows taking a FRACTION of an item (or is phrased in terms of continuous quantities, like fluid volumes or divisible resources), ratio-based greedy is very likely correct and provably optimal. If instead items must be taken whole (0/1), or there are hard cardinality constraints (exactly p of one type and s of another, or an exact count limit per category), be suspicious of any greedy-by-ratio or greedy-by-single-criterion approach -- try to construct a counterexample before trusting it, and default to a DP formulation (over remaining capacity, remaining counts, or similar) when in doubt.

Complexity

O(n log n) for the fractional-knapsack greedy (dominated by the sort); O(n * W) for the 0/1 knapsack DP (W = weight capacity), which is pseudo-polynomial and only tractable when W is reasonably small.

Fractional Knapsack (greedy is provably correct)

Problem

You are given n items (1 <= n <= 10^5), item i having weight w[i] and value v[i] (positive real-valued in general; integers here for concreteness), and a knapsack capacity C. You may take any fraction (between 0 and 1) of each item's weight, receiving that same fraction of its value, subject to the total weight taken not exceeding C. Maximize total value.

Input: n and C, then n lines each with w[i] and v[i].
Output: the maximum total value achievable, printed with 2 decimal places.

Approach

Sort item indices by value-to-weight ratio v[i]/w[i] in descending order. Walk through items in that order, maintaining the remaining capacity: if an item's full weight fits within the remaining capacity, take it entirely (add its full value, subtract its weight from remaining capacity); otherwise take exactly the fraction of it that fits (add value * (remaining/weight), set remaining capacity to 0), and stop, since no further capacity remains. This greedy order is optimal by the standard exchange argument for divisible items. On the classic textbook instance (capacity 50, items (10,60), (20,100), (30,120)), the greedy takes item 1 fully (value 60, capacity left 40), item 2 fully (value 100, capacity left 20), and 20/30 of item 3 (value 80), for a total of 240.00, matching the well-known reference answer for this exact instance.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; double cap;
    cin >> n >> cap;
    vector<double> w(n), v(n);
    for(int i=0;i<n;i++) cin >> w[i] >> v[i];
    vector<int> idx(n);
    iota(idx.begin(), idx.end(), 0);
    sort(idx.begin(), idx.end(), [&](int a, int b){
        return v[a]/w[a] > v[b]/w[b];
    });
    double total = 0.0;
    double remaining = cap;
    for(int i : idx){
        if(remaining <= 0) break;
        if(w[i] <= remaining){
            total += v[i];
            remaining -= w[i];
        } else {
            total += v[i] * (remaining / w[i]);
            remaining = 0;
        }
    }
    printf("%.2f\n", total);
}

0/1 Knapsack (same instance, ratio-greedy is provably wrong)

Problem

You are given n items (1 <= n <= 500), item i having integer weight w[i] and integer value v[i] (1 <= w[i], v[i] <= 10^4), and an integer knapsack capacity C (1 <= C <= 10^4). Each item must be taken WHOLE or not at all (0/1, no fractions). Maximize total value subject to total weight <= C.

Input: n and C, then n lines each with w[i] and v[i].
Output: the maximum total value achievable.

Approach

Run the standard 1D 0/1 knapsack DP: dp[c] = best value achievable using total weight exactly <= c, initialized to all 0. For each item, update dp[c] for c from C down to w[i] (descending order is essential so each item is only considered once per pass): dp[c] = max(dp[c], dp[c - w[i]] + v[i]). The final answer is dp[C].

Using the EXACT same numbers as the fractional-knapsack example above (capacity 50, items (10,60), (20,100), (30,120)) deliberately demonstrates why ratio-based greedy fails once items are indivisible: sorting by ratio (6, 5, 4) and greedily taking whole items in that order takes item 1 and item 2 (weight 30, value 160) and then cannot fit item 3 (weight 30 > remaining 20 capacity), for a greedy total of only 160. The DP above finds the true optimum of 220, achieved by taking items 2 and 3 together (weight exactly 50, value 220) and skipping the highest-ratio item 1 entirely -- a combination the greedy never even considers because it commits early to the best-ratio item. This 60-point gap (220 vs. 160) is a concrete, hand-verifiable proof that greedy-by-ratio is not a valid algorithm for the 0/1 variant.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n, cap;
    cin >> n >> cap;
    vector<int> w(n), v(n);
    for(int i=0;i<n;i++) cin >> w[i] >> v[i];
    vector<long long> dp(cap+1, 0);
    for(int i=0;i<n;i++){
        for(int c = cap; c >= w[i]; c--){
            dp[c] = max(dp[c], dp[c-w[i]] + v[i]);
        }
    }
    cout << dp[cap] << endl;
}
