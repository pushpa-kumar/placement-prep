RAII (Resource Acquisition Is Initialization)

RAII binds a resource's lifetime to an object's lifetime: acquire the resource in the constructor, release it in the destructor. Because C++ *guarantees* that destructors run when a scope exits — through normal control flow, an early return, or even an exception unwinding the stack — RAII gives you automatic, exception-safe cleanup without a single explicit try/finally-equivalent block. This one idea underlies std::lock_guard, every smart pointer, std::fstream, std::vector's own memory management, and essentially all correctly-written resource-owning C++ types.

A minimal RAII wrapper around a raw resource
class FileHandle {
    FILE* fp;
public:
    explicit FileHandle(const char* path) : fp(fopen(path, "r")) {
        if (!fp) throw std::runtime_error("failed to open file");
    }
    ~FileHandle() { if (fp) fclose(fp); }

    FileHandle(const FileHandle&) = delete;            // see Rule of Five: don't allow
    FileHandle& operator=(const FileHandle&) = delete;  // an implicit double-close

    FILE* get() const { return fp; }
};

void process() {
    FileHandle f("data.bin");   // acquired
    parseHeader(f.get());       // if this throws...
    parseBody(f.get());
}                                // ...~FileHandle() STILL runs during stack unwinding, closing fp

There is no cleanup code visible anywhere in process() — that's the entire point. Whether the function returns normally or an exception propagates out of parseHeader/parseBody, f's destructor is guaranteed to run as the stack unwinds past it, so the file always gets closed exactly once.

RAII for a mutex — the pattern behind std::lock_guard
class ScopedLock {
    std::mutex& m;
public:
    explicit ScopedLock(std::mutex& m) : m(m) { m.lock(); }
    ~ScopedLock() { m.unlock(); }
    ScopedLock(const ScopedLock&) = delete;
};

void criticalSection(std::mutex& mtx) {
    ScopedLock lock(mtx);
    doWork();  // if doWork() throws, the mutex is STILL released — no deadlock
}

This is literally what std::lock_guard<std::mutex> does internally. Without RAII, you'd need to remember to call mtx.unlock() on every exit path of criticalSection — including exceptional ones — which is exactly the kind of manual bookkeeping RAII eliminates.

Pitfalls

  • Writing an RAII class but forgetting to delete (or properly implement) its copy constructor/assignment — a naive memberwise copy of a resource-owning object (e.g. copying fp in FileHandle above) leads to two objects both believing they own — and will both try to close/free — the same resource.

  • Allocating a resource in a constructor that can partially fail (acquiring resource A, then throwing while acquiring resource B) without unwinding what was already acquired — the destructor never runs for an object whose constructor didn't finish, so any RAII sub-members must each independently be exception-safe.

RAII isn't usually asked about directly by name as often as it's ASSUMED — interviewers expect you to reach for it (smart pointers, lock_guard) automatically when discussing resource management, and will probe if you reach for manual malloc/free or lock/unlock instead.

Rule of Zero / Three / Five

**Rule of Three** (the pre-C++11 guideline): if a class needs a custom destructor, it's almost certainly managing a resource directly — and if so, it needs a custom copy constructor and copy-assignment operator too, because the compiler-generated memberwise versions would copy the raw resource handle, not the resource itself (see RAII pitfalls above). **Rule of Five** extends this for C++11+: add a move constructor and move-assignment operator too, so the resource can be transferred cheaply instead of always being deep-copied. **Rule of Zero** is the modern preferred design: don't write ANY of the five special members by hand at all — instead, compose your class out of members that ALREADY manage their own resources correctly (std::vector, std::string, std::unique_ptr, etc.), so the compiler-generated defaults for all five special members are automatically correct, because they just recursively do the right thing member-by-member.

Rule of Five: a class that legitimately needs all five
class Buffer {
    size_t n; int* data;
public:
    explicit Buffer(size_t n) : n(n), data(new int[n]) {}
    ~Buffer() { delete[] data; }                                     // 1. destructor
    Buffer(const Buffer& o) : n(o.n), data(new int[n]) {              // 2. copy ctor
        std::copy(o.data, o.data + n, data);
    }
    Buffer& operator=(const Buffer& o) {                              // 3. copy assign
        if (this != &o) { int* nd = new int[o.n]; std::copy(o.data, o.data+o.n, nd);
                           delete[] data; data = nd; n = o.n; }
        return *this;
    }
    Buffer(Buffer&& o) noexcept : n(o.n), data(o.data) {               // 4. move ctor
        o.data = nullptr; o.n = 0;
    }
    Buffer& operator=(Buffer&& o) noexcept {                           // 5. move assign
        if (this != &o) { delete[] data; data = o.data; n = o.n; o.data = nullptr; o.n = 0; }
        return *this;
    }
};

Buffer IS the resource-owning primitive here (it directly holds a raw int*), so it must define all five to behave correctly under copying, moving, and destruction — this is exactly the situation where Rule of Five applies.

Rule of Zero: the same functionality, none of the boilerplate
class Buffer {
    std::vector<int> data;  // already manages its own memory correctly
public:
    explicit Buffer(size_t n) : data(n) {}
    // no destructor, no copy ctor/assign, no move ctor/assign written by hand --
    // the compiler-generated versions of all five just call vector's own
    // (already-correct) versions member-by-member, and that's exactly right.
};

By delegating actual ownership to std::vector, Buffer no longer needs to know anything about copying, moving, or freeing memory itself — it inherits correct behavior for free. This is why Rule of Zero is the default modern recommendation: write Rule of Five code only when you're building the resource-owning primitive itself (rare), and Rule of Zero everywhere else (common).

Pitfalls

  • Defining only SOME of the five (e.g. just a destructor, forgetting copy/move) — this is worse than defining none, because it silently disables move operations (the compiler won't generate a move constructor for a class that has a user-declared destructor) and falls back to copying, or worse leaves a raw-resource class with a compiler-generated copy that double-frees.

  • Writing Rule-of-Five boilerplate for a class that doesn't need it — if your class's members are all well-behaved RAII types already, hand-writing the five special members is pure risk (a bug in hand-rolled boilerplate) for zero benefit over Rule of Zero.

Smart pointer ownership models

The three standard smart pointers encode three DIFFERENT ownership philosophies, and picking the wrong one for the situation is a common design-review flag. std::unique_ptr<T> is sole ownership: exactly one owner at a time, move-only (copying is disabled), and — crucially — zero runtime overhead over a raw pointer; the object is destroyed the instant the owning unique_ptr goes out of scope. std::shared_ptr<T> is shared ownership via ATOMIC reference counting: any number of shared_ptrs can co-own the same object, which is destroyed when the last one goes away — but that shared refcount means copying a shared_ptr is not free (an atomic increment/decrement every time). std::weak_ptr<T> observes an object owned by a shared_ptr WITHOUT extending its lifetime or touching the strong refcount — used to break reference cycles and to safely ask "is this thing still alive?" before trying to use it.

All three, and when each is the right call
auto owner = std::make_unique<Order>();      // exactly one owner -- the common case
auto shared = std::make_shared<Book>(bookId); // genuinely shared across multiple subsystems
std::weak_ptr<Book> cache_entry = shared;     // a cache that shouldn't keep Book alive on its own

if (auto locked = cache_entry.lock()) {
    use(*locked);           // safely promoted to a real shared_ptr, only if still alive
} else {
    // the Book was already destroyed elsewhere -- refetch or skip
}

The cache holding a weak_ptr instead of a shared_ptr is the key design decision here: if the cache held a shared_ptr, it would itself keep every cached Book alive forever, defeating the point of a cache. weak_ptr::lock() is the safe way to attempt access without accidentally extending an object's lifetime.

The classic shared_ptr cycle leak
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;  // deliberately weak to break the cycle
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->prev = a;   // if this were ALSO a shared_ptr, a and b would keep each other alive forever
               // -- neither refcount would ever reach zero, even after a and b go out of scope

This is why doubly-linked structures built on shared_ptr deliberately make one direction (commonly "prev"/"parent") a weak_ptr — otherwise the mutual ownership means neither object's reference count ever drops to zero, and both leak silently for the rest of the program's life.

Pitfalls

  • Defaulting to shared_ptr everywhere "to be safe" — this hides ownership intent (who's really responsible for this object?) and pays for atomic refcounting you usually don't need; prefer unique_ptr (or even a plain reference/raw pointer with clear, non-owning semantics) unless shared ownership is a genuine requirement.

  • Creating a reference cycle with shared_ptrs in both directions of a graph/tree-like structure (see example above) — a very common, very real memory leak in production code, not just an academic gotcha.

  • Using shared_ptr on a genuinely latency-sensitive hot path without accounting for the atomic increment/decrement cost on every copy — this is a real, measurable cost interviewers expect you to know about.

Extremely commonly asked, often phrased as "implement a basic shared_ptr" or "what happens if two objects hold shared_ptrs to each other" — both of which test whether you understand the reference-counting mechanism, not just the API.

Allocators & custom allocation

Every STL container is actually a template over an Allocator type (defaulting to one that calls operator new/operator delete), which is the hook that lets you plug in a custom memory strategy — most commonly, a pre-sized arena or pool allocator — instead of the general-purpose heap for every single allocation. This matters a great deal in latency-sensitive code: the default heap allocator is a general-purpose tool that has to handle arbitrary sizes and frees in arbitrary order, which usually means internal locking and bookkeeping with latency that isn't tightly bounded. A pre-allocated arena, sized for a known maximum number of objects up front, can hand out and reclaim fixed-size chunks in O(1) with no lock contention and no unpredictable tail latency.

The shape of a minimal fixed-size pool allocator
template <class T, size_t N>
class PoolAllocator {
    alignas(T) char storage[N * sizeof(T)];
    bool used[N] = {};
public:
    T* allocate() {
        for (size_t i = 0; i < N; ++i)
            if (!used[i]) { used[i] = true; return reinterpret_cast<T*>(storage + i * sizeof(T)); }
        throw std::bad_alloc(); // pool exhausted -- a design decision made explicit, not hidden
    }
    void deallocate(T* p) {
        size_t i = (reinterpret_cast<char*>(p) - storage) / sizeof(T);
        used[i] = false;
    }
};

All the storage for up to N objects is claimed once, up front, as a single contiguous block. allocate()/deallocate() then become simple array-scan/index operations — no syscalls, no general-purpose allocator bookkeeping, no lock — at the cost of a hard, known-in-advance capacity limit.

Why this matters in a trading-system hot path
// Bad on a hot path: every incoming market-data tick allocates a fresh Order
// via the general heap allocator -- unpredictable latency, potential lock contention
// with other threads also calling malloc/new.
std::vector<std::unique_ptr<Order>> book; // default new/delete under the hood

// Better: pre-size a pool for the expected peak order count at startup,
// and hand out/reclaim Order objects from it during the trading session --
// no calls into the general allocator once trading has started.

The core idea is moving all allocation-related uncertainty to STARTUP time (when it doesn't matter), so the actual trading-hours hot path never has to ask the OS/general allocator for memory at all.

Pitfalls

  • Assuming a custom allocator automatically makes code thread-safe — a pool allocator shared across threads still needs its own synchronization (or a per-thread pool) unless it's specifically designed to be lock-free.

  • Over-engineering with a custom allocator before profiling shows the default allocator is actually a bottleneck — this is real complexity/bug-surface you're taking on, and it should be justified by a measured problem, not applied preemptively everywhere.

PImpl idiom (Pointer to Implementation)

A class hides its private implementation details behind a single pointer to a forward-declared struct/class whose full definition lives only in the .cpp file, never the header. The immediate payoff: changing a private member no longer changes the public class's size or forces every translation unit that includes its header to recompile — you're trading one extra heap allocation and one extra pointer indirection per access for dramatically better compile-time isolation (and, as a bonus, a more stable binary interface/ABI, since the public class's memory layout doesn't change when private internals do).

The header — completely decoupled from Widget's real internals
// widget.h
class Widget {
public:
    Widget();
    ~Widget();                      // must be declared here, DEFINED in the .cpp (see pitfall)
    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;
    void doWork();
private:
    struct Impl;                    // forward declaration ONLY -- no definition visible here
    std::unique_ptr<Impl> pImpl;    // the entire real implementation lives behind this one pointer
};

Anyone who includes widget.h sees none of Widget's actual private data members — only a forward-declared Impl and a pointer to it. Adding, removing, or resizing private fields inside Impl never touches this header, so it never forces a rebuild of every file that includes widget.h.

The .cpp — where Impl actually lives
// widget.cpp
struct Widget::Impl {
    std::vector<int> data;
    std::string name;
    // as much private state as needed -- completely invisible to widget.h's includers
};

Widget::Widget() : pImpl(std::make_unique<Impl>()) {}
Widget::~Widget() = default;   // MUST be defined here, where Impl is a complete type
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;
void Widget::doWork() { pImpl->data.push_back(42); }

The destructor (and any special member relying on Impl being complete, like the defaulted move operations) has to be DEFINED in the .cpp file, not just declared in the header — see the pitfall below for why getting this wrong is a classic compile error.

Pitfalls

  • Declaring ~Widget() in the header but letting it be implicitly defined there (or writing = default right in the header) — at that point in the header, Impl is only forward-declared (incomplete), so std::unique_ptr<Impl>'s destructor can't be instantiated; this produces a real, sometimes-confusing compile error about an incomplete type. The fix is always to declare the destructor in the header but DEFINE it (even as = default) in the .cpp, after Impl's full definition is visible.

  • Using PImpl reflexively on every class "for good practice" — it adds a real heap allocation and indirection cost to every object; it's most valuable for classes with either large/frequently-changing private internals or genuine ABI-stability requirements, not as a universal default.

Exception safety guarantees

Three standard levels describe what a piece of code promises will still be true if an exception is thrown partway through it. The **basic guarantee**: no resources leak and the object's invariants still hold, but its exact observable state afterward is unspecified. The **strong guarantee**: the operation either fully succeeds, or has NO visible effect at all — as if it never started (commit-or-rollback semantics) — commonly implemented via the copy-and-swap idiom. The **nothrow (no-throw) guarantee**: the operation is guaranteed to never throw at all, which the standard library actually RELIES on in specific places — most importantly, containers only use a type's move constructor during reallocation if that move constructor is noexcept; otherwise they fall back to copying to preserve their own strong guarantee (see Move semantics).

The strong guarantee via copy-and-swap
class Widget {
    std::vector<int> data;
public:
    Widget& operator=(const Widget& other) {
        Widget tmp(other);              // (1) copy -- if THIS throws, *this is completely untouched
        std::swap(data, tmp.data);      // (2) swap is noexcept -- this step cannot fail
        return *this;
    }                                    // (3) tmp's destructor cleans up the OLD data automatically
};

If step (1)'s copy throws (e.g. out of memory), *this has not been modified at all yet — the strong guarantee holds. Step (2), the only part that actually mutates *this, is a non-throwing swap, so once you reach it, success is guaranteed. This pattern — build the new state fully off to the side, then commit via a non-throwing swap — is the standard recipe for the strong guarantee.

Why noexcept on move operations isn't just documentation
class Buffer {
public:
    Buffer(Buffer&& other) noexcept { /* steal other's resources */ }
};

std::vector<Buffer> v;
// ... v grows past capacity ...
// Because Buffer's move ctor is noexcept, std::vector moves each existing
// Buffer into the new, larger allocation -- O(1) per element.
// If it were NOT noexcept, std::vector would COPY every element instead,
// specifically to preserve ITS OWN strong guarantee: a throwing move mid-reallocation
// could leave the vector in a state where some elements were moved and others weren't,
// with no way to safely roll back -- so the library refuses to risk it.

This is a direct, practical consequence of the nothrow guarantee concept: the standard library's own exception-safety promises are the reason it inspects your type's noexcept-ness before deciding how to treat it internally.

Pitfalls

  • Assuming "basic guarantee" means "nothing bad happens" — it specifically does NOT promise the object's state is predictable afterward, only that it's still valid (destructible, assignable) and nothing leaked. Code relying on a specific post-exception state needs the strong guarantee, not just the basic one.

  • Forgetting that destructors, swap, and move operations are all expected to provide the no-throw guarantee by convention (and are noexcept by default for destructors since C++11) — throwing from any of these is either outright disallowed (destructors during unwinding call std::terminate) or defeats optimizations the standard library specifically makes conditional on noexcept-ness.
