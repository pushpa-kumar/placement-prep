Value categories: lvalue, prvalue, xvalue

Every C++ expression — not just every variable, every *expression* — has a value category, and that category is what overload resolution actually keys off of when deciding whether a copy or a move constructor runs. This trips people up because it feels like it should be about types, but it's about expressions.

An **lvalue** names an object with identity: something you can take the address of, that persists beyond the expression evaluating it. A named variable is the classic example. A **prvalue** ("pure rvalue") is a temporary that *initializes* an object and has no identity of its own — a literal like 42, or the result of a function returning by value before it's bound to anything. An **xvalue** ("eXpiring value") is the interesting middle case: it denotes an object that *does* have identity, but whose resources are about to go away, so it's safe to plunder them — the result of std::move(x), or a function returning T&&.

Two umbrella terms tie these together: a **glvalue** (lvalue or xvalue) is anything with identity; an **rvalue** (prvalue or xvalue) is anything that can be moved from. The whole lattice exists for exactly one reason: to give the compiler a principled way to decide, at every single expression, whether it's looking at something with a name and a future, or something that's either brand new or on its way out.

Identifying the category of each subexpression
int x = 10;        // x is an lvalue (it has identity, you can do &x)
int y = x + 1;      // (x + 1) is a prvalue: a temporary, no identity
int&& r = std::move(x); // std::move(x) is an xvalue: names x, but "expiring"

int* p = &x;   // OK: x is an lvalue
// int* p2 = &(x + 1); // ERROR: can't take the address of a prvalue

&x compiles because x is an lvalue — it lives somewhere with a real address. &(x+1) does not compile, because x+1 is a prvalue: a value that exists only for the duration of the expression, with no address the standard promises you can take.

Why the category — not the type — decides which overload runs
void f(const std::string& s) { std::cout << "lvalue ref overload\n"; }
void f(std::string&& s)      { std::cout << "rvalue ref overload\n"; }

std::string name = "Alice";
f(name);              // name is an lvalue -> calls f(const string&)
f(std::string("Bob")); // a prvalue temporary -> calls f(string&&)
f(std::move(name));    // an xvalue -> calls f(string&&)

Both overloads take a std::string, so the TYPE alone can't distinguish them — it's the value category of the argument expression that overload resolution uses to pick between the lvalue-reference and rvalue-reference overload.

Pitfalls

  • Assuming a named rvalue-reference variable is itself an rvalue: void f(T&& x) { g(x); } — inside f, x is a named variable, so it's an LVALUE even though its declared type is T&&. Passing it on to g without std::move(x) calls g's lvalue overload, silently defeating the move you thought you set up.

  • Trying to take the address of a prvalue (a plain temporary) and being confused when it doesn't compile — remember only glvalues (lvalues/xvalues) have addresses you can rely on.

This is the single most commonly probed C++ fundamentals question at trading firms — usually as "what's the difference between lvalue and rvalue" followed immediately by "so why does calling std::move(x) inside a function and then using x again still compile, and what state is x in?"

Move semantics

Move construction and move assignment let an object TRANSFER ownership of a resource — a heap buffer, a file descriptor, a socket — from a source object to a destination, instead of deep-copying it. The source is left in a valid-but-unspecified state (usually empty/null), and the destination now owns what the source used to own.

What makes this possible is purely a matter of overload resolution: if a class declares an rvalue-reference overload of its constructor/assignment operator (T(T&& other)), and the argument expression is an rvalue (a prvalue temporary or an xvalue from std::move), that overload is selected instead of the copy constructor. The move constructor's body is then free to "steal" the other object's internals — pointer-swap instead of memcpy — because the standard guarantees nobody else cares about the moved-from object's exact value afterward.

The payoff is enormous for anything holding a heap allocation: returning a std::vector or std::string by value, or reallocating a growing vector, becomes a pointer-swap instead of an O(n) copy.

A move constructor and move-assignment operator that actually steal, not copy
class Buffer {
    size_t n;
    int* data;
public:
    Buffer(size_t n) : n(n), data(new int[n]) {}

    // Move constructor: steal the other's pointer, null it out
    Buffer(Buffer&& other) noexcept : n(other.n), data(other.data) {
        other.data = nullptr;
        other.n = 0;
    }

    // Move assignment: release our own resource first, then steal
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data;
            data = other.data;
            n = other.n;
            other.data = nullptr;
            other.n = 0;
        }
        return *this;
    }

    ~Buffer() { delete[] data; }
};

Notice there's no new/copy loop anywhere in the move operations — just pointer reassignment and nulling the source. That's the entire point: O(1) transfer instead of O(n) duplication. The noexcept is not decorative — see the pitfall below.

Why std::vector cares whether your move constructor is noexcept
std::vector<Buffer> v;
v.reserve(2);
v.emplace_back(1000000); // fills capacity
v.emplace_back(1000000); // triggers a reallocation of the vector's storage

When v reallocates, it must move (or copy) every existing Buffer into the new, larger block. If Buffer's move constructor is noexcept, std::vector uses it directly — O(1) per element. If it is NOT noexcept, std::vector conservatively falls back to COPYING every element instead, because a throwing move partway through reallocation could leave the vector in a corrupted state with no way to roll back. Forgetting noexcept silently turns your "optimization" back into the copies you were trying to avoid.

Pitfalls

  • Omitting noexcept on the move constructor/assignment — as shown above, this makes std::vector (and other standard containers) silently prefer copying over moving during reallocation, defeating the entire point.

  • Using a moved-from object as if it still holds its old value. The standard guarantee is only "valid but unspecified state" — you can destroy it or assign a new value to it safely, but reading its old contents is not guaranteed to work.

  • Forgetting to null out the source's pointer in the move constructor — if you copy the pointer but don't clear the source, BOTH objects' destructors will try to free the same memory (double-free).

Move semantics is arguably THE defining feature that separates "modern C++" performance characteristics from C++03 — expect at least one question about it in any serious C++ interview, often phrased as "walk me through what happens when a std::vector reallocates."

std::move vs std::forward

These two are constantly confused because they look similar ("cast something to an rvalue reference-ish thing") but they solve opposite problems. std::move UNCONDITIONALLY casts its argument to an rvalue reference — it doesn't move anything itself, it just makes the argument eligible to be moved from by whatever receives it. std::forward CONDITIONALLY casts: inside a template function taking a forwarding reference, it preserves whatever value category the caller originally used, forwarding an lvalue as an lvalue and an rvalue as an rvalue. This is "perfect forwarding" — passing an argument through a layer of indirection without losing information about how it was passed in.

std::move: turning a named lvalue back into something move-able
std::string s = "hello";
std::string t = std::move(s); // s is an lvalue; std::move casts it to string&&
// t now owns "hello"'s buffer; s is valid-but-unspecified (commonly empty)

Without std::move, t = s would copy (s is a named variable, hence an lvalue). std::move is purely a cast — static_cast<std::string&&>(s) — that makes the move constructor's overload the one selected.

std::forward: preserving the caller's value category through a wrapper
template <class T>
void wrapper(T&& arg) {
    target(std::forward<T>(arg)); // forwards arg AS the caller originally passed it
}

std::string s = "hi";
wrapper(s);                 // T deduced as string&  -> forwards as lvalue -> target copies
wrapper(std::string("hi")); // T deduced as string    -> forwards as rvalue -> target moves

If wrapper used std::move(arg) instead of std::forward<T>(arg), it would ALWAYS move — even when the caller passed an lvalue they still needed afterward. std::forward is what lets a single generic wrapper correctly replicate whatever the caller intended.

Pitfalls

  • Using std::move on a const object: std::move(const_string) still compiles and returns const string&&, but no move constructor will bind to a const rvalue reference — it silently falls back to copying. std::move can't undo const.

  • Using std::forward outside of a template with a genuine forwarding-reference parameter — it only does the right thing when T is actually deduced per-call; using it on a fixed (non-template) T&& parameter is just a confusing way to write std::move.

Universal / forwarding references

A parameter written as T&& is NOT always an rvalue reference — it depends entirely on whether T is a template parameter being deduced right there. When T is deduced (e.g. template<class T> void f(T&& x)), x is a **forwarding reference**: it will bind to both lvalues and rvalues, with T deduced as U& for an lvalue argument (collapsing T&& = U& && = U& via C++'s reference-collapsing rules) and as plain U for an rvalue argument. When T is a fixed, concrete type — void f(Widget&& x) — there is no deduction happening, and x is simply an ordinary rvalue reference that will only bind to rvalues.

Forwarding reference vs. plain rvalue reference, side by side
template <class T>
void forwarding(T&& x) { /* T deduced: forwarding reference */ }

void plainRvalueRef(Widget&& x) { /* Widget is fixed: NOT a forwarding reference */ }

Widget w;
forwarding(w);            // OK: T deduced as Widget&, x binds to the lvalue w
forwarding(Widget());     // OK: T deduced as Widget,  x binds to the rvalue temporary

plainRvalueRef(w);        // ERROR: an lvalue cannot bind to Widget&&
plainRvalueRef(Widget()); // OK: a plain rvalue reference binds to an rvalue

The syntax T&& looks identical in both cases, but only the templated version with a genuinely deducible T gets the special "binds to anything" forwarding-reference behavior.

auto&& is also a forwarding reference
for (auto&& elem : container) {
    // elem is a forwarding reference here too — auto plays the role of T
}

This is exactly why range-based for loops commonly use auto&&: it correctly binds to whatever value category the container's iterator produces (an lvalue reference for most containers, but potentially an rvalue for some proxy-iterator containers), without forcing an unwanted copy or an invalid binding.

Pitfalls

  • Assuming any T&& in a function signature means "this is for rvalues only" — always check whether T is actually being deduced at that call site before concluding it's a forwarding reference vs. a plain rvalue reference.

  • Writing template<class T> void f(std::vector<T>&& x) and thinking this is a forwarding reference — it is NOT, because T is not deduced directly as the parameter's whole type (it's nested inside vector<T>); this is a plain rvalue reference to a vector.

A classic interview trap question: "is T&& always an rvalue reference?" — the expected answer distinguishes forwarding references from plain rvalue references, which is exactly the nuance above.

Copy elision / RVO & NRVO

Return Value Optimization is the compiler constructing a returned object directly in the CALLER's storage, skipping an intermediate copy or move entirely. Since C++17, elision of a prvalue returned directly (return T(args); or return makeT();) is not just an optimization the compiler is ALLOWED to do — it's mandated by the standard; there is no copy/move constructor call at all in that case, and the type doesn't even need to be copyable or movable. Named RVO — returning a named local variable (T t; ... return t;) — is a different, older case: it's still only an optional-but-near-universally-implemented optimization, not guaranteed by the standard, because the compiler has to prove no other code path returns a different named variable.

Guaranteed elision (C++17+) vs. optional NRVO
struct Big {
    Big()               { std::cout << "ctor "; }
    Big(const Big&)      { std::cout << "copy "; }
    Big(Big&&) noexcept  { std::cout << "move "; }
};

Big makeGuaranteed() {
    return Big();      // C++17: MANDATORY elision. Prints only "ctor " — no copy/move at all.
}

Big makeNamed() {
    Big b;
    return b;          // NRVO: an optimization, not guaranteed. In practice, almost every
}                       // modern compiler elides this too, printing just "ctor ".

Both functions typically print just "ctor " on any modern compiler, but only makeGuaranteed's elision is something the STANDARD requires — makeNamed's elision is compiler generosity you can rely on in practice but shouldn't design correctness around.

When NRVO can't happen: multiple different named returns
Big pick(bool cond) {
    Big a, b;
    if (cond) return a;
    else      return b;   // two DIFFERENT named locals returned from two paths
}                          // the compiler generally CANNOT elide here -> falls back to a move

NRVO requires the compiler to be certain, statically, which single local object is being returned so it can construct it directly in the caller's slot from the start. With two different candidate locals on different branches, that certainty is gone, so the compiler instead falls back to moving the chosen object out — still cheap thanks to move semantics, but not free like true elision.

Pitfalls

  • Explicitly writing return std::move(localVar); — this actually DEFEATS NRVO on most compilers, because wrapping the return in std::move turns it into an xvalue expression that the compiler's elision analysis doesn't recognize as "the one guaranteed-unique named local" anymore. Just return localVar; and let the compiler decide is almost always better.

  • Assuming NRVO always happens and therefore skipping the move constructor entirely (making it deleted, or private) — since NRVO isn't guaranteed, this can break on a compiler/optimization-level combination where NRVO doesn't kick in.

Explains why returning large objects by value is often completely free in modern C++, removing the old C++03-era instinct to use output parameters "for performance."
