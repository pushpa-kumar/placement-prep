Sorting & Binary Search

Sorting and binary search are the two workhorse techniques that unlock a huge fraction of competitive-programming and placement-exam problems: sorting imposes structure you can exploit (monotonicity, grouping, order statistics), and binary search exploits that structure to cut search spaces from O(n) to O(log n). The most powerful application, binary search on the answer, generalizes the idea from "find a value in a sorted array" to "find the optimal value of any monotonic feasibility predicate," turning otherwise intractable optimization problems into a handful of feasibility checks. These techniques build directly on Sorting & Binary Search: ternary search is binary search's cousin for unimodal (rather than monotonic) functions, custom comparators generalize 'sort then scan' by engineering the right sort key for a greedy or heap-based argument, and order statistics/quickselect reuse the partition step of quicksort to answer 'what is the k-th element' without fully sorting.

Sorting Algorithm Tradeoffs

2 worked examples

Every comparison-based sort is bounded below by Omega(n log n) comparisons in the worst case, so the interesting differences between quicksort, mergesort, and heapsort are not about their average-case time complexity (all three are O(n log n) on average) but about stability, worst-case guarantees, memory usage, and constant factors. Quicksort (what std::sort typically uses, blended with introsort/heapsort fallback and insertion sort for small partitions) has excellent cache locality and the best practical constant factor, but a naive implementation is O(n^2) worst case on adversarial or already-sorted input; production implementations defend against this with random pivots, median-of-three pivots, or by switching to heapsort after too many recursion levels (introsort, which is what the C++ standard mandates for std::sort's worst-case bound). Quicksort is also NOT stable: equal elements can be reordered relative to each other.

Mergesort is stable (equal elements keep their relative input order) and has a guaranteed O(n log n) worst case, which matters when input can be adversarial or when stability is required (e.g., sorting by a secondary key after already sorting by a primary key). The cost is O(n) auxiliary space for the merge step and generally worse cache behavior / constant factor than quicksort on random data. std::stable_sort is typically an implementation of mergesort for this reason. Heapsort is in-place (O(1) extra space) with a guaranteed O(n log n) worst case, but it is not stable and has poor cache locality because of its access pattern jumping around the heap array, making it slower in practice than quicksort or mergesort despite the same asymptotic complexity; it is mainly useful as the 'safety net' fallback that gives introsort its worst-case guarantee, and as the engine behind priority queues and heap-based algorithms (Dijkstra, k-way merges).

When array elements come from a small, bounded domain (e.g., integers in [0, k) with k = O(n)), non-comparison sorts break the Omega(n log n) lower bound entirely: counting sort runs in O(n + k) and is naturally stable when implemented with a prefix-sum placement pass, and radix sort applies counting sort digit-by-digit to sort O(n) w-bit integers in O(n * w / log n) time. Recognizing that problem constraints put values in a small range (say, sorting 10^6 integers each at most 10^5) is a classic signal to reach for counting sort instead of std::sort, saving a log factor.

In competitive programming you almost never hand-implement quicksort/mergesort/heapsort; the actual skill being tested is (1) choosing stable vs unstable sort correctly when a problem has a hidden secondary ordering requirement, (2) writing correct custom comparators (especially ones that must form a valid strict-weak-ordering, e.g., the 'concatenation' comparator for largest-number problems), and (3) recognizing when bounded-value constraints allow you to drop to a faster non-comparison sort.

Recognize it by

Reach for this topic's ideas when: a problem asks you to arrange/reorder elements under a custom rule that is not plain numeric order (needs a custom comparator, and you must argue it is a valid total order); a problem's correctness depends on ties preserving original order (stability); or the input values are bounded by something small relative to n, hinting that O(n + k) counting/radix sort beats O(n log n) comparison sort. If a solution's correctness argument breaks when two equal elements swap places, you need a stable sort or an explicit tie-breaker (e.g., include the original index as a secondary sort key).

Complexity

Quicksort (introsort/std::sort): O(n log n) average and (with introsort fallback) worst case, O(log n) extra space for recursion, NOT stable. Mergesort/std::stable_sort: O(n log n) worst case guaranteed, O(n) extra space, stable. Heapsort: O(n log n) worst case guaranteed, O(1) extra space, NOT stable. Counting/radix sort: O(n + k) / O(n * w/log n), O(n + k) extra space, stable if implemented via prefix sums.

Largest Number (custom comparator)

Problem

Given n non-negative integers, arrange them (each used exactly once) so that their decimal concatenation forms the largest possible number, and print that number as a string (with no leading zeros, unless the result is exactly "0"). Constraints: 1 <= n <= 10^5, 0 <= a[i] <= 10^9.

Approach

This is not orderable by plain numeric or lexicographic comparison of the numbers themselves (e.g., 9 should come before 30 even though '30' < '9' lexicographically as a prefix issue). Convert every number to its decimal string, then sort the strings with the comparator cmp(a, b) := (a+b) > (b+a) as strings, i.e., a should precede b iff placing a first yields a lexicographically larger concatenation. This comparator is provably a valid strict weak ordering (transitivity follows from comparing digit blocks), so std::sort with it produces a correct total order. After sorting, concatenate all strings; finally, strip leading zeros (but keep a single '0' if every element was zero).

Solution
#include <bits/stdc++.h>
using namespace std;

int main(){
    int n;
    cin >> n;
    vector<string> v(n);
    for (auto &s : v) {
        int x;
        cin >> x;
        s = to_string(x);
    }
    sort(v.begin(), v.end(), [](const string &a, const string &b) {
        return a + b > b + a;
    });
    string res;
    for (auto &s : v) res += s;
    int i = 0;
    while (i + 1 < (int)res.size() && res[i] == '0') i++;
    res = res.substr(i);
    cout << res << endl;
    return 0;
}

Ranking Students (stability matters)

Problem

You are given n students in input order, each with a name and an integer score. Print the students sorted by score in descending order; students with equal scores must keep their original relative (input) order. Constraints: 1 <= n <= 1000, 0 <= score <= 100.

Approach

This is the canonical demonstration of why stability matters: sorting only by 'score descending' does not fully specify the output when scores tie, so the algorithm must preserve input order among equal elements. Using std::sort here is unsafe because it is not guaranteed stable (equal elements may be reordered arbitrarily by its internal introsort). The correct tool is std::stable_sort with the comparator only comparing score (descending); stable_sort guarantees O(n log^2 n) worst case (O(n log n) with enough extra memory, which is the common case) and never disturbs the relative order of elements that compare equal. An equivalent alternative that also works with plain sort is to break ties explicitly by original index.

Solution
#include <bits/stdc++.h>
using namespace std;

struct Student {
    string name;
    int score;
};

int main(){
    int n;
    cin >> n;
    vector<Student> v(n);
    for (int i = 0; i < n; i++) cin >> v[i].name >> v[i].score;
    stable_sort(v.begin(), v.end(), [](const Student &a, const Student &b) {
        return a.score > b.score;
    });
    for (auto &s : v) cout << s.name << " " << s.score << "\n";
    return 0;
}

Binary Search

2 worked examples

Classic binary search finds a target (or a boundary) inside a structure with a monotonic order in O(log n) by repeatedly halving the search interval [lo, hi]. The essential invariant to keep in your head is not 'the array is sorted' but 'the predicate I'm testing at each midpoint is monotonic over the search range' — sortedness is just the most common way that monotonicity arises. At each step you evaluate the predicate at mid = lo + (hi - lo) / 2 (never (lo + hi) / 2, to avoid signed overflow on large indices) and discard the half of the range that cannot contain the answer. The two most common templates are: (1) exact-match search, shrinking until lo > hi or the element is found; and (2) boundary search (as in std::lower_bound / std::upper_bound), which finds the first index where a predicate flips from false to true, using a loop of the form while (lo < hi) { mid = ...; if (pred(mid)) hi = mid; else lo = mid + 1; }.

A large family of 'hard' binary search problems apply the technique to structures that are only piecewise sorted or sorted along a derived quantity rather than the raw array: searching a rotated sorted array (the array is sorted except for one rotation point, and at every step exactly one half of any sub-range is guaranteed properly sorted, which is enough information to decide which half to recurse into), or binary searching over a partition index into two arrays to find a median without merging them. These problems are 'binary search' in the sense that the state space, not necessarily the raw array, is monotonic — the discipline is to precisely state the invariant you're maintaining and prove it holds after each halving step, since off-by-one errors are the single most common source of bugs in this topic.

It's worth internalizing why binary search is provably optimal for plain search in a sorted array: any comparison-based search algorithm needs Omega(log n) comparisons in the worst case (an adversary argument / decision-tree lower bound), and binary search matches that bound exactly.

Recognize it by

Use classic binary search when the data is sorted (or can be sorted up front cheaply) and you need membership, insertion position, or a boundary/count query in O(log n); when the phrase 'find the first/last index such that...' appears; or when a structure is 'almost sorted' in a way that still lets you determine, from O(1) probes at the midpoint, which half must contain the answer (rotated arrays, bitonic arrays, or a derived monotonic quantity like a partition balance in the two-sorted-array median problem).

Complexity

O(log n) time per search, O(1) extra space (iterative) or O(log n) stack space (recursive).

Search in a Rotated Sorted Array

Problem

An array of n distinct integers, originally sorted in ascending order, has been rotated at some unknown pivot (e.g., [0,1,2,4,5,6,7] rotated at index 3 becomes [4,5,6,7,0,1,2]). Given the rotated array and a target value, return the index of the target, or -1 if it is not present. Must run in O(log n) time. Constraints: 1 <= n <= 5000, all elements distinct.

Approach

At any midpoint, even though the whole array isn't sorted, at least one of the two halves [lo, mid] or [mid, hi] IS a contiguous sorted run (rotation can only break sortedness at one point). So at each step: compare a[lo] with a[mid] to determine which half is properly sorted; then check whether the target lies within that sorted half's value range. If it does, recurse into that half; otherwise the target (if present) must be in the other half. This keeps the search space halving every step, giving O(log n).

Solution
#include <bits/stdc++.h>
using namespace std;

int main(){
    int n;
    cin >> n;
    vector<int> a(n);
    for (auto &x : a) cin >> x;
    int target;
    cin >> target;

    int lo = 0, hi = n - 1, ans = -1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == target) { ans = mid; break; }
        if (a[lo] <= a[mid]) {
            // left half [lo, mid] is sorted
            if (a[lo] <= target && target < a[mid]) hi = mid - 1;
            else lo = mid + 1;
        } else {
            // right half [mid, hi] is sorted
            if (a[mid] < target && target <= a[hi]) lo = mid + 1;
            else hi = mid - 1;
        }
    }
    cout << ans << endl;
    return 0;
}

Median of Two Sorted Arrays

Problem

Given two sorted arrays nums1 (size m) and nums2 (size n), find the median of the combined sorted array in O(log(min(m, n))) time (merging, which is O(m+n), is too slow for the intended constraints m, n up to 10^6). Print the median with 5 digits after the decimal point.

Approach

Binary search over a partition index i in the smaller array (WLOG size m <= n). For a given i, the mirrored partition in the other array is forced: j = (m + n + 1) / 2 - i, so that the left side of the combined partition has exactly ceil((m+n)/2) elements. A partition is correct when max(left side of A) <= min(right side of B) AND max(left side of B) <= min(right side of A); if the first condition fails (A's left is too large), shrink i; if the second fails, grow i. When a valid partition is found, the median is either max(leftA, leftB) (odd total length) or the average of max(leftA, leftB) and min(rightA, rightB) (even total length). Sentinels INT_MIN/INT_MAX handle empty partitions cleanly.

Solution
#include <bits/stdc++.h>
using namespace std;

int main(){
    int m;
    cin >> m;
    vector<int> A(m);
    for (auto &x : A) cin >> x;
    int n;
    cin >> n;
    vector<int> B(n);
    for (auto &x : B) cin >> x;

    if (m > n) { swap(A, B); swap(m, n); }

    int lo = 0, hi = m, half = (m + n + 1) / 2;
    double ans = 0;
    while (lo <= hi) {
        int i = lo + (hi - lo) / 2;
        int j = half - i;
        int Aleft  = (i == 0) ? INT_MIN : A[i - 1];
        int Aright = (i == m) ? INT_MAX : A[i];
        int Bleft  = (j == 0) ? INT_MIN : B[j - 1];
        int Bright = (j == n) ? INT_MAX : B[j];

        if (Aleft <= Bright && Bleft <= Aright) {
            if ((m + n) % 2 == 0)
                ans = (max(Aleft, Bleft) + min(Aright, Bright)) / 2.0;
            else
                ans = max(Aleft, Bleft);
            break;
        } else if (Aleft > Bright) {
            hi = i - 1;
        } else {
            lo = i + 1;
        }
    }
    cout << fixed << setprecision(5) << ans << endl;
    return 0;
}

Binary Search on the Answer

3 worked examples

Binary search on the answer (a.k.a. 'binary search over the value space') is used when you cannot compute the optimal answer directly, but you CAN cheaply check, for a fixed candidate answer x, whether x is 'feasible' (e.g., 'can we achieve at least this much', or 'can we finish within this much time/cost'), and feasibility is monotonic in x. If feasible(x) is monotonic — every x' >= x is also feasible whenever x is (or the symmetric case for minimizing) — then the set of feasible x forms a contiguous suffix (or prefix) of the value line, and you can binary search for the boundary between infeasible and feasible exactly like std::lower_bound, except the 'array' is implicit: it's the predicate feasible(mid), evaluated on demand instead of read from memory.

The template for minimizing an answer is: lo = smallest conceivable value, hi = largest conceivable value (a safe upper bound, often derivable from a trivial feasible construction); while (lo < hi) { mid = lo + (hi - lo) / 2; if (feasible(mid)) hi = mid; else lo = mid + 1; }; answer = lo. Maximizing is the mirror image with feasible(mid) shrinking lo upward. The entire complexity of the algorithm collapses into two parts: (1) proving monotonicity (often the 'aha' insight — it is rarely stated in the problem and must be argued informally, e.g. 'if we can pack everything using capacity x, we can certainly pack it using any larger capacity'), and (2) designing an efficient feasibility check, which is frequently a greedy linear scan, a two-pointer count, or a difference-array / prefix-sum computation.

This technique is what separates 'medium' from 'hard' binary search problems: the binary search itself is boilerplate, but recognizing that a problem phrased as 'minimize the maximum X' or 'maximize the minimum Y' or 'find the smallest T such that...' is secretly a monotonic feasibility problem — rather than something requiring direct DP or a closed-form formula — is the actual skill. A huge number of CP problems ('minimize the largest subarray sum when splitting into k pieces', 'maximize the minimum distance between placed items', 'find the k-th smallest pairwise distance') reduce to exactly this pattern.

Recognize it by

Strong signals: the problem says 'minimize the maximum ...' or 'maximize the minimum ...'; it asks for the smallest/largest value of some quantity such that a condition holds, and directly computing that value seems to require trying all possibilities; and you can write (even if slowly) a function feasible(x) that tells you in O(n) or O(n log n) whether a candidate value x works, and you can convince yourself that feasibility only turns on (never off) as x increases (or vice versa).

Complexity

O(log(range) * feasibility-check-cost). Feasibility checks are typically O(n) (greedy scan) or O(n log n) (two-pointer over a sorted array, or a scan needing a sort up front), giving overall O(n log(range)) or O(n log n log(range)).

Factory Machines

Problem

There are k machines producing identical products; machine i needs t_i seconds to make one product, and all machines work in parallel and continuously (machine i can produce floor(T / t_i) products in T seconds). Find the minimum number of seconds T needed so that the machines together have produced at least n products in total. Constraints: 1 <= k <= 2*10^5, 1 <= n <= 10^9, 1 <= t_i <= 10^9. (CSES 1620, Factory Machines.)

Approach

Computing the optimal T directly is hard because production is a sum of floor divisions with different rates. But feasibility is trivial to check and monotonic: for a fixed candidate time T, the total products made is sum(floor(T / t_i)) over all machines, an O(k) computation, and this total is clearly non-decreasing as T grows. So binary search T over [1, huge upper bound] (e.g., up to n * max(t_i), or just a very large constant since t_i, n <= ~10^9), and find the smallest T with total production >= n.

Solution
#include <bits/stdc++.h>
using namespace std;

int main(){
    long long k, n;
    cin >> k >> n;
    vector<long long> t(k);
    for (auto &x : t) cin >> x;

    long long lo = 1, hi = (long long)2e18;
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        long long total = 0;
        for (auto ti : t) {
            total += mid / ti;
            if (total >= n) break;
        }
        if (total >= n) hi = mid;
        else lo = mid + 1;
    }
    cout << lo << endl;
    return 0;
}

Array Division (minimize the maximum subarray sum)

Problem

Given an array of n positive integers, divide it into k contiguous, non-empty subarrays so as to minimize the largest sum among the k subarrays. Print that minimized maximum sum. Constraints: 1 <= k <= n <= 2*10^5, 1 <= a_i <= 10^9. (CSES 1085, Array Division; equivalent to LeetCode's Split Array Largest Sum.)

Approach

Binary search on the candidate maximum sum M. Feasibility check: greedily scan the array left to right, accumulating a running sum for the current subarray; whenever adding the next element would exceed M, start a new subarray there instead. Count how many subarrays this greedy scan needs; if that count is <= k, M is feasible (we can always merge extra small pieces together without exceeding M, or simply use fewer than k cuts). Feasibility is monotonic in M (a larger cap can only need fewer or equal subarrays), so binary search between lo = max single element (a lower bound, since that element alone must fit in some subarray) and hi = total sum (trivially feasible with 1 subarray) finds the minimum feasible M.

Solution
#include <bits/stdc++.h>
using namespace std;

int main(){
    int n, k;
    cin >> n >> k;
    vector<long long> a(n);
    long long lo = 0, hi = 0;
    for (auto &x : a) { cin >> x; hi += x; lo = max(lo, x); }

    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        long long parts = 1, cur = 0;
        for (auto x : a) {
            if (cur + x > mid) { parts++; cur = x; }
            else cur += x;
        }
        if (parts <= k) hi = mid;
        else lo = mid + 1;
    }
    cout << lo << endl;
    return 0;
}

K-th Smallest Pair Distance

Problem

Given an array of n integers, define the distance of a pair (i, j) with i < j as |nums[i] - nums[j]|. Find the k-th smallest such distance among all C(n,2) pairs. Constraints: 2 <= n <= 10^4, 1 <= k <= n*(n-1)/2, 0 <= nums[i] <= 10^6. (LeetCode 719.)

Approach

Sort the array. Binary search on the candidate distance d in [0, max-min]. The feasibility check counts how many pairs have distance <= d: after sorting, use a two-pointer sliding window — for each right endpoint, advance left while a[right]-a[left] > d, then every index between left and right (inclusive on the left side) pairs with right at distance <= d, contributing (right - left) pairs; summing this over all right endpoints is an O(n) pass (each pointer moves forward only). This count is monotonic non-decreasing in d, so binary search for the smallest d with count(d) >= k gives exactly the k-th smallest pair distance.

Solution
#include <bits/stdc++.h>
using namespace std;

int main(){
    int n;
    cin >> n;
    vector<int> a(n);
    for (auto &x : a) cin >> x;
    int k;
    cin >> k;

    sort(a.begin(), a.end());
    int lo = 0, hi = a[n - 1] - a[0];
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        long long count = 0;
        int left = 0;
        for (int right = 0; right < n; right++) {
            while (a[right] - a[left] > mid) left++;
            count += (right - left);
        }
        if (count >= k) hi = mid;
        else lo = mid + 1;
    }
    cout << lo << endl;
    return 0;
}

Ternary Search on Unimodal Functions

2 worked examples

Binary search finds a target in a MONOTONIC function (or array); ternary search is the analogous tool for a UNIMODAL function -- one that strictly increases and then strictly decreases (or vice versa), with a single peak or valley. Given such a function f, pick two interior points m1 < m2 within the current search range [lo, hi] (commonly at the 1/3 and 2/3 marks). If f(m1) < f(m2) (searching for a maximum), the peak cannot lie to the left of m1, because f is still increasing there, so the range can be narrowed to [m1, hi]; symmetrically if f(m1) > f(m2), the peak cannot lie to the right of m2, so the range narrows to [lo, m2]. Each iteration discards roughly one-third of the range, giving O(log(range) / log(3/2)) iterations to converge -- still O(log n) asymptotically, just with a larger constant than binary search.

On a continuous (real-valued) domain, this is implemented with a fixed number of iterations (e.g. 100-200), since 'the range is small enough' has no natural integer stopping point; each iteration roughly multiplies the search interval width by 2/3, so 100 iterations shrink an initial range of 10^6 down to well below any double-precision-meaningful width. On an integer domain, care is needed: naive ternary search can infinite-loop or give an off-by-one wrong answer when the range becomes very small (comparing m1 and m2 might not make progress) or when the function has a PLATEAU (multiple adjacent points sharing the same optimal value) rather than a single strict peak. The standard robust fix is to shrink the search range only down to a small constant width (commonly hi - lo <= 2), using a comparison like 'if f(m1) <= f(m2) then hi = m2 else lo = m1 + 1', and then brute-force check the few remaining candidates directly -- this handles plateaus correctly because convexity still guarantees the true optimum survives every narrowing step, and the final brute-force sweep resolves any remaining ties exactly.

Recognizing unimodality is often the hard part, not implementing the search. Sums of convex functions are convex (and hence unimodal after negation for maximization), so if a cost function is built by summing several convex pieces (e.g. absolute-value costs, or a Kadane-style 'worst subarray sum' as a function of a shift parameter), the whole thing is guaranteed unimodal even without an explicit closed form -- letting you search on it directly without ever deriving a formula for the optimum.

Recognize it by

You need to optimize (minimize or maximize) a real- or integer-valued function of a single parameter, and you can argue (or it is given/provable) that the function first strictly increases then strictly decreases (or the reverse) -- i.e. it is unimodal/convex -- but you cannot easily solve for the optimum in closed form and each function evaluation is itself computable (e.g. via a linear scan or Kadane's algorithm).

Complexity

O(log(range)) evaluations of f for the search itself (each evaluation costing whatever it costs, e.g. O(n) for a Kadane-based check), so O(n log(range)) total for a typical 'search over a parameter, evaluate with a linear scan' problem.

Minimizing the Weakness of a Sequence (real-valued ternary search)

Problem

You are given n real numbers a[1..n]. For a chosen real number x, define the 'poorness' of a segment [l, r] as the absolute value of the sum (a[l]-x) + ... + (a[r]-x), and the 'weakness' of x as the maximum poorness over all non-empty contiguous segments. Find the value of x that minimizes the weakness, and print that minimum weakness.

Input: n, then n numbers a[1..n] (given as integers or decimals).
Output: the minimum possible weakness, printed with 6 digits after the decimal point.

Approach

For a fixed x, the weakness is max(maximum subarray sum of (a_i - x), -(minimum subarray sum of (a_i - x))), both computed with a standard O(n) Kadane pass. As a function of x, the weakness is a maximum of two functions, each of which is convex in x (a maximum/minimum subarray sum, viewed as a max/min over a finite set of LINEAR functions of x -- one per subarray -- is itself convex, since a pointwise maximum of linear functions is always convex, and negating a concave minimum keeps it convex too); a maximum of convex functions is convex, so weakness(x) is convex, hence unimodal, and ternary search applies directly on the real line. Run ternary search with a fixed number of iterations (200, far more than needed for 1e-6 precision) over a sufficiently wide range, evaluating weakness(x) via Kadane at each of the two candidate points per iteration, and narrow toward the minimum. Verified by brute-force scanning weakness(x) on a fine grid (step 0.0001) for the sample input, confirming the ternary search converges to the same minimum (x=2, weakness=1.0 for input [1,2,3]).

Solution
#include <bits/stdc++.h>
using namespace std;
int n;
vector<double> a;

double weakness(double x) {
    // compute max subarray sum and min subarray sum of (a[i]-x) via Kadane
    double curMax = 0, maxSum = -1e18;
    double curMin = 0, minSum = 1e18;
    for (int i = 0; i < n; i++) {
        double v = a[i] - x;
        curMax = max(v, curMax + v);
        maxSum = max(maxSum, curMax);
        curMin = min(v, curMin + v);
        minSum = min(minSum, curMin);
    }
    return max(maxSum, -minSum);
}

int main(){
    cin >> n;
    a.assign(n, 0);
    for (auto &x : a) cin >> x;
    double lo = -1e6, hi = 1e6;
    for (int it = 0; it < 200; it++) {
        double m1 = lo + (hi - lo) / 3;
        double m2 = hi - (hi - lo) / 3;
        if (weakness(m1) <= weakness(m2)) hi = m2; else lo = m1;
    }
    double ans = weakness((lo + hi) / 2);
    cout << fixed << setprecision(6) << ans << endl;
}

Equalize Pillar Heights at Minimum Total Cost (integer ternary search)

Problem

You are given n pillars, where pillar i currently has height h[i]. You want to choose a single target height T (an integer) and adjust every pillar to have height T, where the cost of adjusting pillar i to height T is |h[i] - T| (moving each unit of height costs 1). Find the target height T that minimizes the total cost, and print T together with the minimum total cost. (If multiple T achieve the same minimum cost, print the smallest such T.)

Input: n, then n integers h[1..n].
Output: two integers: the optimal T, and the minimum total cost.

Approach

cost(T) = sum of |h[i] - T| is a sum of convex (absolute-value) functions of T, hence convex, hence unimodal (minimized, with possibly a flat plateau at the median when n is even) -- a textbook target for integer ternary search. Because integer ternary search can behave incorrectly right at the boundary of a very small range or on a plateau, use the robust pattern: shrink the range [lo, hi] only while hi - lo > 2, using two interior points m1, m2 at roughly the 1/3 and 2/3 marks, and comparing cost(m1) <= cost(m2) to decide which side to discard (convexity guarantees the true minimum is never discarded by this rule, even on a plateau, because it never discards past the point where cost stops being provably worse). Once the range has shrunk to at most 3 candidates, brute-force evaluate cost at each remaining integer and take the best (and, for tie-breaking to the smallest T, scan candidates in increasing order and only replace the best on a STRICT improvement). This correctly reproduces the well-known fact that the optimum is the median of h[].

Solution
#include <bits/stdc++.h>
using namespace std;
int n;
vector<long long> h;

long long cost(long long target) {
    long long c = 0;
    for (int i = 0; i < n; i++) c += llabs(h[i] - target);
    return c;
}

int main(){
    cin >> n;
    h.assign(n, 0);
    for (auto &x : h) cin >> x;
    long long lo = *min_element(h.begin(), h.end());
    long long hi = *max_element(h.begin(), h.end());
    while (hi - lo > 2) {
        long long m1 = lo + (hi - lo) / 3;
        long long m2 = hi - (hi - lo) / 3;
        if (cost(m1) <= cost(m2)) hi = m2; else lo = m1 + 1;
    }
    long long best = LLONG_MAX, bestH = lo;
    for (long long height = lo; height <= hi; height++) {
        long long c = cost(height);
        if (c < best) { best = c; bestH = height; }
    }
    cout << bestH << " " << best << endl;
}

Custom Comparators & Multi-Key Sorting

2 worked examples

Many greedy algorithms are only correct once the input is sorted by exactly the right key -- often a DERIVED key (a ratio, a sum, or a comparison rule between two fields) rather than any single raw field, and sometimes a different sort order for different subsets of the input entirely. Getting this key right is usually justified by an EXCHANGE ARGUMENT: suppose an optimal solution processes two adjacent elements i then j in some order; show that swapping their order never makes the solution worse (and sometimes strictly better) exactly when a certain inequality between their fields holds; that inequality between i's and j's fields is then used to define the comparator, guaranteeing that no adjacent swap can improve on the sorted order, which (by a standard argument extending adjacent transpositions to arbitrary permutations) means the sorted order is optimal among all orderings.

A canonical two-group example: processing 'projects' that each require a minimum resource level to start and then change the resource level by some signed delta. Projects with a non-negative delta (net gainers) should be processed sorted ascending by their requirement -- do the 'cheapest to unlock' ones first to build up resources as fast as possible. Projects with a negative delta (net spenders) should be processed sorted DESCENDING by (requirement + delta), i.e. by their value AFTER completion -- counter-intuitively not by their requirement directly, because what matters for a spender is how much of a safety margin it leaves behind for the remaining spenders, and an exchange argument shows that ordering by post-completion value descending never causes an avoidable failure.

A second common shape: a greedy that needs 'the k best items where quality is judged by a MINIMUM over the selected group, multiplied or combined with a SUM over the group' (e.g. maximize sum(speed) * min(efficiency), or minimize a cost keyed by the max ratio in a hired group). The trick is to sort by the field that appears as a min/max in the objective (efficiency, or wage-to-quality ratio) descending, then scan while maintaining the SUM field (speed, or quality) in a heap of bounded size -- because sorting by the min/max field first guarantees that, at the moment each element is considered, every element seen so far (including the current one) has a min/max-field value at least as large as the current one, so the current element's field value is safely usable as 'the min (or the threshold ratio) of the group so far' without having to re-check every previously chosen element.

Recognize it by

A greedy or heap-based approach seems natural, but sorting by the obvious raw field gives wrong answers on small counterexamples; the objective mixes two fields (a per-element requirement/cost and a per-element gain/effect, or a sum together with a min/max), and you suspect the right order is by a DERIVED key (a sum of two fields, a ratio, or 'value after applying the effect') rather than either raw field alone.

Complexity

O(n log n) for the sort, plus O(n) or O(n log n) for the subsequent greedy/heap scan, so O(n log n) total.

Feasibility of Ordering Rating-Changing Projects (two-key exchange-argument sort)

Problem

You start with rating R. You are given n projects; project i requires your CURRENT rating to be at least a[i] to start it, and completing it changes your rating by b[i] (which may be positive or negative). Your rating must never become negative at any point (including immediately after completing a project). Determine whether there exists an order to complete ALL n projects without ever violating these constraints.

Input: n and R, then n pairs a[i] b[i].
Output: "YES" if some valid order exists, otherwise "NO".

Approach

Split the projects into two groups: 'gainers' with b[i] >= 0, and 'spenders' with b[i] < 0. Do all gainers first, sorted ascending by a[i] -- an exchange argument shows that if two gainers could be swapped to violate this order and still be feasible, swapping them back to ascending-a order is also feasible (a gainer only helps future rating, so unlocking the cheapest requirement first is never worse). Then do all spenders, sorted DESCENDING by (a[i] + b[i]) -- the rating immediately after completing the project -- again by an exchange argument: for two adjacent spenders i, j, doing i before j requires rating >= max(a[i], a[j] - b[i]) at that point, while doing j before i requires rating >= max(a[j], a[i] - b[j]); algebraic manipulation shows that ordering by descending post-completion value (a[i]+b[i]) never requires a strictly higher minimum starting rating than any other order, so it's always safe to prefer it. Simulate both groups in this fixed order, tracking the running rating and failing immediately if any project's requirement isn't met or if the rating would go negative afterward. This crafted test demonstrates the necessity of the (a+b)-descending rule: sorting spenders by requirement 'a' ascending instead would process a=4 before a=5, whose simulation fails, even though the correct (a+b)-descending order (a=5 before a=4) succeeds from the same starting rating.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; long long R;
    cin >> n >> R;
    vector<pair<long long,long long>> pos, neg; // (a, b)
    for (int i = 0; i < n; i++) {
        long long a, b; cin >> a >> b;
        if (b >= 0) pos.push_back({a, b});
        else neg.push_back({a, b});
    }
    sort(pos.begin(), pos.end(), [](auto &p, auto &q){ return p.first < q.first; });
    sort(neg.begin(), neg.end(), [](auto &p, auto &q){
        return (p.first + p.second) > (q.first + q.second);
    });
    long long rating = R;
    bool ok = true;
    for (auto &pr : pos) {
        if (rating < pr.first) { ok = false; break; }
        rating += pr.second;
    }
    if (ok) {
        for (auto &pr : neg) {
            if (rating < pr.first) { ok = false; break; }
            rating += pr.second;
            if (rating < 0) { ok = false; break; }
        }
    }
    cout << (ok ? "YES" : "NO") << endl;
}

Course Schedule III (deadline sort + retroactive max-heap swap)

Problem

You are given n courses, course i taking duration[i] days and having a deadline lastDay[i] (you must FINISH it on or before lastDay[i]). You may take the courses in any order, one at a time with no gaps, starting at day 0. Find the maximum number of courses you can take without missing any deadline of a course you commit to finishing.

Input: n, then n pairs duration[i] lastDay[i].
Output: the maximum number of courses that can be taken.

Approach

Sort courses ascending by deadline -- this is the key comparator choice, because it lets you consider courses in an order where, once you decide to 'tentatively take' a course, every course considered afterward has an equal or later deadline, so there is never a reason to prefer a not-yet-seen course over one already tentatively scheduled except on duration. Greedily try to take every course in this deadline order, maintaining a running total time and a max-heap of the durations of courses currently scheduled. After tentatively adding a course (adding its duration to the running time and pushing it to the heap), check if the running time now exceeds this course's deadline; if so, the schedule is currently infeasible, so retroactively REMOVE the single longest-duration course scheduled so far (found instantly via the max-heap) -- this is always at least as good as removing the just-added course, since it frees up the most possible time while keeping the same count of courses scheduled, and it cannot violate any earlier deadline (all remaining courses have equal-or-later, already-satisfied deadlines). The final answer is the number of courses remaining in the heap.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin >> n;
    vector<pair<long long,long long>> courses(n); // duration, lastDay
    for (auto &c : courses) cin >> c.first >> c.second;
    sort(courses.begin(), courses.end(), [](auto &a, auto &b){
        return a.second < b.second; // sort by deadline ascending
    });
    priority_queue<long long> maxHeap; // durations taken so far
    long long curTime = 0;
    for (auto &c : courses) {
        long long dur = c.first, deadline = c.second;
        curTime += dur;
        maxHeap.push(dur);
        if (curTime > deadline) {
            curTime -= maxHeap.top();
            maxHeap.pop();
        }
    }
    cout << maxHeap.size() << endl;
}

Order Statistics / Quickselect

2 worked examples

The k-th order statistic of a collection is simply the k-th smallest (or largest) element. Sorting the whole collection to find it costs O(n log n), but quickselect -- reusing quicksort's partition step without recursing into both sides -- finds it in expected O(n) time. Partition the array around a pivot (ideally chosen randomly to avoid adversarial worst-case inputs) exactly as in quicksort: rearrange so all elements less than the pivot come first, then the pivot itself lands at its final sorted position 'store', then all elements greater than or equal to the pivot follow. If store equals the target index k, the pivot IS the answer; otherwise, recurse into only the half of the array that must contain the k-th element (the left part if k < store, the right part if k > store) -- discarding the other half entirely, which is what turns the expected O(n log n) of full quicksort into an expected O(n) (each recursive call operates on a geometrically shrinking array, summing to O(n) total work in expectation with random pivots).

A second, entirely different family of order-statistics problems asks for the k-th smallest value in an implicitly defined, exponentially large combinatorial set -- e.g. the k-th smallest pairwise distance among all C(n,2) pairs, the k-th smallest pairwise product between two arrays, or the k-th smallest sum choosing one element from each of several sorted lists. Enumerating the whole set is infeasible, but if you can efficiently COUNT how many elements of the set are <= a candidate value v (often via a two-pointer sweep over sorted data, or a per-row binary search), you can binary search on the answer value v itself: search for the smallest v such that count(<=v) >= k. This 'binary search on the answer, count with a cheaper structure' pattern is itself a generalization of order-statistics selection -- instead of partitioning the actual elements (quickselect), you partition the space of POSSIBLE ANSWER VALUES using a monotonic counting function, which is valid whenever count(<=v) is monotonically non-decreasing in v (always true, since a bigger threshold can only include more elements).

Which of the two techniques applies depends on whether you can cheaply materialize or partition the actual elements (use quickselect) versus only cheaply COUNT how many elements satisfy a threshold (use binary-search-on-the-answer with a counting subroutine).

Recognize it by

You need the k-th smallest/largest element (or a k-th order statistic of some derived quantity like a difference, product, or sum) without needing the collection fully sorted; if the k-th value comes from an explicit array, quickselect applies; if it comes from an implicitly huge set of combinations, look for a monotonic 'count elements <= v' function and binary search on v.

Complexity

Expected O(n) time, O(1) extra space for randomized quickselect on an explicit array of n elements; O(n log n) time (sort) plus O(log(range) * (cost of one count)) for binary-search-on-the-answer over an implicit combinatorial set.

K-th Smallest Element via Randomized Quickselect

Problem

Given an unsorted array of n distinct integers, find the k-th smallest element (1-indexed: k=1 means the minimum) without fully sorting the array.

Input: n, then n integers, then k.
Output: the k-th smallest element.

Approach

Use Hoare-style partitioning with a RANDOMLY chosen pivot (to make worst-case O(n^2) behavior astronomically unlikely regardless of input order): pick a random index in the current subrange, swap that pivot value to the end, then scan the rest of the subrange moving every element smaller than the pivot to the front (tracked by a 'store' index), and finally swap the pivot into position 'store' -- its final sorted position within this subrange. If store equals the 0-indexed target k-1, return the pivot immediately. Otherwise, recurse (via a loop, not actual recursion, to keep it iterative) into only the side of the partition that must contain the target: the left part if the target index is less than store, the right part otherwise. This discards, on average, half the remaining array at each step, giving expected O(n) total work despite each partition step itself costing O(current subrange size). A fixed random seed is used here only so the output is reproducible for testing; a real submission could seed from time or use std::random_device.

Solution
#include <bits/stdc++.h>
using namespace std;
mt19937 rng(12345); // fixed seed for reproducible output

int quickselect(vector<long long>& a, int lo, int hi, int k) {
    // returns the k-th smallest (0-indexed) element of a[lo..hi]
    while (true) {
        if (lo == hi) return a[lo];
        int pivotIdx = lo + rng() % (hi - lo + 1);
        long long pivot = a[pivotIdx];
        swap(a[pivotIdx], a[hi]);
        int store = lo;
        for (int i = lo; i < hi; i++) {
            if (a[i] < pivot) { swap(a[i], a[store]); store++; }
        }
        swap(a[store], a[hi]);
        if (store == k) return a[store];
        else if (k < store) hi = store - 1;
        else lo = store + 1;
    }
}

int main(){
    int n; cin >> n;
    vector<long long> a(n);
    for (auto &x : a) cin >> x;
    int k; cin >> k; // 1-indexed k-th smallest
    cout << quickselect(a, 0, n-1, k-1) << endl;
}

K-th Smallest Pairwise Distance (binary search on the answer + two pointers)

Problem

Given an array of n integers, consider the multiset of all C(n,2) pairwise absolute differences |nums[i] - nums[j]| for i < j. Find the k-th smallest value in this multiset (1-indexed).

Input: n, then n integers, then k.
Output: the k-th smallest pairwise distance.

Approach

Enumerating all C(n,2) distances directly is too slow for large n, but the number of pairs with distance <= v is easy to COUNT for a fixed v: sort the array, then for each right pointer, advance a left pointer forward while nums[right] - nums[left] > v, and add (right - left) to the count (every index from left to right-1 pairs with right to form a distance <= v) -- this two-pointer count runs in O(n) since both pointers only move forward, for a total of O(n) per candidate v. Since count(<=v) is monotonically non-decreasing in v, binary search on v over the range [0, max-min] for the smallest v with count(<=v) >= k; that v is guaranteed to actually be an achievable pairwise distance (not just a threshold), because count(<=v) only changes at values that are themselves actual pairwise distances. Total time is O(n log n) for the sort plus O(n log(max-min)) for the binary search with its O(n) counting step.

Solution
#include <bits/stdc++.h>
using namespace std;
int main(){
    int n; cin >> n;
    vector<long long> a(n);
    for (auto &x : a) cin >> x;
    long long k; cin >> k;
    sort(a.begin(), a.end());
    long long lo = 0, hi = a[n-1] - a[0];
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        // count pairs with distance <= mid using two pointers
        long long cnt = 0;
        int left = 0;
        for (int right = 0; right < n; right++) {
            while (a[right] - a[left] > mid) left++;
            cnt += right - left;
        }
        if (cnt >= k) hi = mid; else lo = mid + 1;
    }
    cout << lo << endl;
}
