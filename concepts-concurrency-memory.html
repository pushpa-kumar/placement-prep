This is exactly the territory HFT interviews probe hardest, because it's where correctness and performance are both on the line simultaneously.

Alignment & padding

Every type has an ALIGNMENT requirement: an object of that type may only be placed at a memory address that's a multiple of its alignment (commonly, a type's alignment equals its size for primitives, up to some platform maximum). To satisfy every member's alignment requirement inside a struct, the compiler silently inserts PADDING bytes between members as needed — which means a struct's total size, and even its layout, depends on the DECLARATION ORDER of its members, not just which members it has.

Reordering members to eliminate padding
struct Bad {
    char a;    // 1 byte, needs 3 bytes padding so 'b' below can start 4-byte-aligned
    int b;     // 4 bytes
    char c;    // 1 byte, needs 3 bytes padding at the end so the struct's total size
};             // is itself a multiple of its largest member's alignment (4)
// sizeof(Bad) == 12 on a typical platform (1 + 3 pad + 4 + 1 + 3 pad)

struct Good {
    int b;     // 4 bytes, no padding needed before it
    char a;    // 1 byte
    char c;    // 1 byte -- a and c pack together into the same 4-byte block
};             // only 2 bytes of trailing padding needed to reach a multiple of 4
// sizeof(Good) == 8 on the same platform -- a third smaller, same data, just reordered

Both structs hold exactly the same three fields — the only difference is declaration order, and that alone changes the total size by 33% here. The general heuristic: declare members from LARGEST alignment requirement to smallest to minimize padding.

Checking layout directly
#include <iostream>
struct Bad  { char a; int b; char c; };
struct Good { int b; char a; char c; };
int main() {
    std::cout << sizeof(Bad) << " " << sizeof(Good);  // typically prints "12 8"
}

This is directly checkable and is a common quick warm-up interview question: "reorder this struct to make it smaller, without removing or changing any field."

Pitfalls

  • Assuming struct size is just the sum of its members' sizes — padding means it very often isn't, and the gap can be significant for structs mixing small (char, bool) and large (int, double, pointer) members without deliberate ordering.

  • Forgetting that padding also matters for ARRAYS of structs — a small per-element size increase from bad ordering multiplies across every element, directly hurting cache-line utilization when scanning the array (see False Sharing for the related-but-distinct cross-thread version of this concern).

A common warm-up systems question at HFT firms — packing structs tightly (message formats, order-book entries) is routine, practical work, not academic trivia.

False sharing & alignas

False sharing is a PERFORMANCE problem, not a correctness one: two threads write to two DIFFERENT, logically-unrelated variables that happen to land on the same CPU cache line (commonly 64 bytes). Because cache-coherence protocols track ownership at the granularity of a whole cache line, every write by either thread invalidates the OTHER core's cached copy of that entire line — even though the two threads never actually touch each other's data. The threads end up fighting over cache-line ownership as if they were racing on the same variable, when logically they aren't. The fix is to pad/align each independently-hot variable to its own cache line, commonly via alignas(64).

The problem: two "independent" atomics sharing a cache line
struct Counters {
    std::atomic<long> producerCount;  // written by thread A
    std::atomic<long> consumerCount;  // written by thread B
};
// producerCount and consumerCount are only 8 bytes apart -- almost certainly on
// the SAME 64-byte cache line. Every increment by thread A invalidates thread B's
// cached copy of the line (and vice versa), even though the two counters are
// logically completely independent -- this looks like contention in a profiler,
// but there is NO actual data race or shared logical state here at all

Both threads are correct (each only touches its own atomic), but performance suffers as if they were contending on a single shared variable, purely because of physical cache-line proximity.

The fix: force each hot variable onto its own cache line
struct Counters {
    alignas(64) std::atomic<long> producerCount;
    alignas(64) std::atomic<long> consumerCount;  // now guaranteed a different cache line
};
// sizeof(Counters) grows from 16 bytes to 128 bytes -- a real memory cost,
// traded deliberately for eliminating the cross-core cache-coherence traffic

alignas(64) forces each field to start at a 64-byte-aligned address, and the compiler pads the struct so the SECOND field can't share a line with the first — the increased memory footprint is the explicit price for removing the false-sharing bottleneck entirely.

Pitfalls

  • Diagnosing this as a "race condition" because a profiler shows contention-like symptoms — false sharing produces performance symptoms that superficially resemble lock contention, but there's no actual shared logical state; the fix (cache-line separation) is completely different from the fix for a real race (synchronization).

  • Over-applying alignas(64) everywhere defensively — it's a real memory-footprint cost, worth paying specifically for variables that are BOTH hot (frequently written) AND touched by different threads; padding cold or single-threaded data this way is pure waste.

One of THE most frequently asked HFT-specific interview questions, almost always phrased exactly as: "two threads write to adjacent memory locations — what happens, and how would you fix it?"

The C++ memory model & happens-before

The C++11 memory model formally defines, for multithreaded programs, WHEN a write by one thread is guaranteed to be visible to a read by another thread. Absent any synchronization at all, concurrently accessing the same memory location from multiple threads — with at least one of those accesses a write — is a **data race**, which the standard defines as undefined behavior, not merely "you might read a stale value." Synchronization operations (atomics with appropriate ordering, mutexes) establish a **happens-before** relationship between specific operations in different threads, and it's ONLY through such an established happens-before edge that one thread's writes are guaranteed visible to another's subsequent reads.

A data race: undefined behavior, not just "maybe stale"
int data = 0;         // a plain, non-atomic int
bool ready = false;   // a plain, non-atomic bool

// Thread 1:
data = 42;
ready = true;          // no synchronization at all

// Thread 2:
while (!ready) {}      // spinning on a plain bool with no synchronization
use(data);              // UNDEFINED BEHAVIOR: this is a data race on BOTH `ready` and `data` --
                        // the standard makes NO guarantee `data` is even visible as 42 here,
                        // and the compiler is technically permitted to assume this loop
                        // never observes `ready` changing at all (and optimize accordingly)

This isn't merely "probably works but might occasionally see a stale value" — it's genuine undefined behavior per the standard, because there's no happens-before relationship connecting Thread 1's writes to Thread 2's reads at all.

The fix: establishing happens-before via release/acquire atomics
int data = 0;
std::atomic<bool> ready{false};

// Thread 1:
data = 42;
ready.store(true, std::memory_order_release);   // RELEASE: everything written before this
                                                   // store becomes visible to any thread that
                                                   // subsequently ACQUIRE-loads and sees `true`
// Thread 2:
while (!ready.load(std::memory_order_acquire)) {} // ACQUIRE
use(data); // now WELL-DEFINED: the release/acquire pairing establishes happens-before,
           // guaranteeing data==42 is visible here

The release store and the acquire load that observes it form a synchronization point: everything sequenced-before the release in Thread 1 is guaranteed visible after the acquire in Thread 2 — this release/acquire handoff pattern is the fundamental building block of essentially all lock-free code.

Pitfalls

  • Assuming volatile provides thread-safety or ordering guarantees in the way atomics do — it does not; volatile in C++ only prevents certain compiler optimizations (relevant for memory-mapped hardware registers) and has NOTHING to do with the multithreaded memory model or cross-thread visibility.

  • Believing a data race just means you occasionally get a slightly wrong/stale value — the standard defines it as full undefined behavior, which in practice can also mean the compiler optimizes based on the (false) assumption that the race never happens, producing results far stranger than "stale data."

std::atomic & memory_order basics

std::atomic<T> operations are indivisible (no other thread can observe a "half-finished" read or write), and each operation can specify an ordering constraint controlling how it interacts with OTHER memory operations around it. memory_order_relaxed gives you ONLY atomicity — no ordering guarantee relative to anything else — useful when you genuinely just need a value to update atomically (an independent counter) with no cross-thread visibility requirement on anything else. memory_order_acquire (on a load) and memory_order_release (on a store) together form the classic handoff pattern described in the memory-model concept above. memory_order_seq_cst (the default if you don't specify one) is the strongest and simplest to reason about: it additionally guarantees a single, globally-agreed total order across ALL seq_cst operations from every thread — at a real, measurable synchronization cost compared to relaxed/acquire-release.

Relaxed: atomicity without ordering, for an independent counter
std::atomic<long> requestsHandled{0};

void onRequest() {
    requestsHandled.fetch_add(1, std::memory_order_relaxed);
    // we only need the INCREMENT itself to be atomic (no lost updates) --
    // we don't need this operation to be ordered relative to any other
    // memory access in the program, so relaxed is the cheapest correct choice
}

Using memory_order_seq_cst here (the default) would still be CORRECT, just needlessly expensive — relaxed is exactly sufficient because nothing else in the program depends on this counter's update being ordered relative to anything else.

Why the ordering choice is a real, measurable engineering decision
// On some architectures (notably ARM, but even on x86 for certain patterns),
// seq_cst operations require additional memory fence instructions that
// relaxed/acquire-release do not -- a hot-path counter incremented millions
// of times per second genuinely benefits from being relaxed rather than
// seq_cst, if (and only if) no other code depends on its ordering relative
// to other memory operations. Getting this wrong in the other direction
// (using relaxed where acquire/release was actually needed) is a correctness
// bug, not just a missed optimization -- so this is a decision to make
// deliberately, not default to the weakest option everywhere.

This is exactly the kind of judgment call an HFT interviewer wants to see you reason through explicitly: relaxed is cheaper, but only correct when NOTHING else depends on ordering — defaulting to relaxed everywhere "for speed" without checking that is a real bug risk, not a free win.

Pitfalls

  • Defaulting to memory_order_relaxed everywhere to "go fast" without verifying that no other code depends on ordering relative to that atomic — this converts a performance optimization into a correctness bug.

  • Confusing is_lock_free() with a promise about ordering — is_lock_free() only tells you whether the atomic avoids an internal mutex on this platform; it says nothing about which memory_order semantics you've chosen or need.

Undefined Behavior vs Unspecified vs Implementation-defined

Three distinct levels of "the standard doesn't fully pin this down," and confusing them is a common mistake. **Undefined behavior (UB)** means the standard imposes NO requirements whatsoever — literally anything is a conforming outcome, including something that looks like it "worked" on your machine today and breaks on a different compiler, optimization level, or even a later run of the same binary. **Unspecified behavior** means the standard allows multiple valid outcomes and does not require an implementation to document which one it picked (classic pre-C++17 example: the order function-call arguments are evaluated in). **Implementation-defined behavior** is unspecified behavior with one extra requirement: each implementation MUST document, consistently, which choice it makes (e.g. the exact size of int, or how right-shift behaves on negative signed integers pre-C++20).

All three, side by side
int x = INT_MAX;
x = x + 1;                 // UNDEFINED BEHAVIOR: signed overflow. The standard gives
                            // NO guarantee at all -- not even "it wraps around"

void f(int a, int b);
f(g(), h());                // UNSPECIFIED (pre-C++17): could evaluate g() then h(), or
                            // h() then g() -- either is conforming, and the compiler
                            // need not document or commit to either consistently

std::cout << sizeof(int);   // IMPLEMENTATION-DEFINED: varies by platform (commonly 4),
                            // but whatever it is, that compiler must document and honor it
                            // consistently -- it's not free to change behavior arbitrarily

The key distinguishing question for each: does the standard require ANY specific behavior at all (no -> UB), and if there IS a required documented choice, is it required to be consistent per-implementation (yes -> implementation-defined) or not (unspecified)?

Why "but it worked when I ran it" is not evidence of correctness
int arr[5];
arr[10] = 1;   // UB: out-of-bounds write. This might silently "work" (corrupt some
               // unrelated memory that happens not to matter yet), crash immediately,
               // or be "optimized away" in a surprising way by a compiler that assumes
               // (correctly, per the standard) that well-formed programs never do this

This is exactly why recognizing UB matters practically, not just for interview trivia: a program exhibiting UB can pass every test you throw at it today and still be genuinely broken, because the compiler is entitled to assume UB never happens and optimize on that assumption — sometimes in ways that make the bug appear or worsen only under a different build configuration.

Pitfalls

  • Treating "it produced the expected output when I ran it" as proof that a piece of UB-containing code is fine — UB's defining property is precisely that conforming behavior includes "happens to look right today."

  • Assuming unspecified behavior is as dangerous as UB — it isn't: unspecified behavior guarantees the program still does something well-defined-per-that-execution, it just doesn't tell you in advance WHICH well-defined thing; UB provides no such floor at all.

Recognizing that a piece of code's "expected" output is actually built on UB is frequently the ENTIRE point of a tricky output-prediction interview question — the best answer is often "this is undefined behavior, so asking for THE output is the wrong question."
