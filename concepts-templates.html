Templates & instantiation

A template is a blueprint, not code that runs directly — the compiler generates ("instantiates") a genuinely separate, concrete function or class for every DISTINCT combination of template arguments actually used in the program. This gives you fully generic source code that compiles down to specialized, non-generic machine code for each instantiation — no runtime type checks, no boxing, no dispatch overhead — at the cost of longer compile times and larger binaries ("code bloat") if many distinct instantiations get generated.

Two calls, two entirely separate instantiations
template <class T>
T max_of(T a, T b) { return a > b ? a : b; }

max_of(3, 5);       // instantiates a fresh max_of<int>(int, int)
max_of(3.0, 5.0);   // instantiates a COMPLETELY SEPARATE max_of<double>(double, double)
// each is compiled independently, as if you'd hand-written both overloads yourself

There's no single "max_of" function at the machine-code level — the compiler has generated two distinct functions, each fully specialized to its type, with no runtime branching on "what type am I" anywhere in either one.

Class templates instantiate their MEMBERS lazily
template <class T>
class Box {
public:
    T value;
    void onlyCalledSometimes() { value.methodThatOnlyExistsOnSomeTypes(); }
};

Box<int> b;
b.value = 5;
// b.onlyCalledSometimes(); // if you NEVER call this, it's never instantiated,
                            // and int not having methodThatOnlyExistsOnSomeTypes()
                            // is never even checked -- templates only instantiate
                            // member functions that are actually USED

This lazy, per-member instantiation is a real, practical property: a class template can have member functions that would fail to compile for certain T, and that's completely fine as long as those specific members are never called for that T.

Pitfalls

  • Underestimating compile-time/binary-size cost — a heavily templated codebase with many distinct instantiations (e.g. a container template used with dozens of different element types) can meaningfully slow builds and bloat the binary; this is a real engineering tradeoff, not just theory.

  • Writing template code and only testing it with one type, then being surprised when it fails to compile for a different type — since each instantiation is checked independently, correctness for T=int says nothing about correctness for T=std::string.

SFINAE (Substitution Failure Is Not An Error)

During overload resolution for a template function, the compiler substitutes candidate template arguments into each overload's signature to see if it's viable. SFINAE is the rule that if that substitution produces something ill-formed — but ONLY if the ill-formedness is in the "immediate context" (typically the return type or a parameter type, not deep inside the function body) — the compiler quietly REMOVES that candidate from the overload set instead of raising a hard compile error. This lets you write multiple template overloads that each only "participate" for certain types, effectively doing compile-time dispatch based on type properties.

Two overloads, each SFINAE'd to opt in for exactly one category of type
template <class T>
typename std::enable_if<std::is_integral<T>::value, void>::type
foo(T t) { std::cout << "integral overload: " << t; }

template <class T>
typename std::enable_if<std::is_floating_point<T>::value, void>::type
foo(T t) { std::cout << "floating-point overload: " << t; }

foo(3);    // std::enable_if<is_integral<int>> succeeds -> only the first overload survives substitution
foo(3.5);  // std::enable_if<is_floating_point<double>> succeeds -> only the second survives
// foo("str"); // BOTH enable_if conditions are false -> both substitutions fail ->
               // both overloads silently vanish from the candidate set -> genuine compile error
               // ("no matching function"), NOT a confusing enable_if-internal error

For foo(3), substituting T=int makes the SECOND overload's enable_if<is_floating_point<int>::value, void>::type ill-formed (enable_if with a false condition has no ::type member) — SFINAE means this is silently dropped from consideration rather than causing a hard error, leaving exactly the first overload as the only viable candidate.

Detecting whether a type has a member function, a classic SFINAE idiom
template <class T>
class has_toString {
    template <class U> static auto test(int) -> decltype(std::declval<U>().toString(), std::true_type{});
    template <class U> static std::false_type test(...);
public:
    static constexpr bool value = decltype(test<T>(0))::value;
};

// has_toString<SomeClassWithToString>::value  -> true
// has_toString<int>::value                    -> false (int has no .toString(), substitution fails,
                                                //          falls through to the ... overload)

This pattern — an overload whose return type only compiles if the expression U().toString() is valid — is the classic pre-Concepts way to ask "does this type support this operation?" at compile time. It's clever but genuinely hard to read, which is exactly the readability problem C++20 Concepts were designed to fix.

Pitfalls

  • Confusing SFINAE with a hard compile error — SFINAE ONLY applies to substitution failures in the immediate context (the declaration itself); a failure deep inside a function BODY that happens to compile-instantiate is a real, hard error, not silently ignored.

  • Writing dense, hard-to-read enable_if-based template metaprogramming when C++20 Concepts are available — Concepts express the same intent far more readably and with much clearer compiler errors on failure; prefer them in new code.

Interviewers who ask about SFINAE are usually checking whether you can explain WHY it's needed (compile-time type-based dispatch) and whether you know it's been largely superseded by Concepts — not whether you can write it from memory.

Concepts (C++20)

Concepts let you name and directly enforce a compile-time constraint on a template parameter — "T must support addition," "T must be a forward iterator" — replacing much of what SFINAE was historically used for, with dramatically more readable code and, crucially, far clearer compiler error messages when a constraint isn't satisfied (compare to the wall of enable_if-substitution-failure noise SFINAE typically produces).

A named, reusable concept
template <class T>
concept Numeric = std::is_arithmetic_v<T>;

template <Numeric T>
T square(T x) { return x * x; }

square(5);       // OK: int satisfies Numeric
// square("hi"); // clear, direct error: "constraint 'Numeric' was not satisfied"
                 // (compare to the multi-page SFINAE error you'd get from an
                 //  equivalent enable_if-based overload set for the same mistake)

The concept Numeric is defined once and can be reused across any number of templates — and critically, when a call violates it, the compiler tells you exactly which named constraint failed, rather than dumping the internals of a failed template substitution.

Constraining based on required operations, not just type traits
template <class T>
concept Addable = requires(T a, T b) {
    { a + b } -> std::same_as<T>;   // T must support a+b, and the result must be T itself
};

template <Addable T>
T sum(T a, T b) { return a + b; }

This requires expression directly states "whatever operations I actually need" rather than relying on an indirect type trait — this is closer to how you naturally think about what a generic function requires, and it's exactly the kind of constraint that was awkward to express with SFINAE alone.

Pitfalls

  • Treating concepts as purely a documentation/readability improvement with no functional difference from SFINAE — they also change overload resolution rules (a more-constrained overload is preferred over a less-constrained one when both are viable), which SFINAE-based enable_if tricks handle much more awkwardly.

  • Assuming Concepts are available in codebases that haven't moved to C++20 yet — many production/interview contexts still target C++17 or earlier, where SFINAE remains the only tool for this.

CRTP (Curiously Recurring Template Pattern)

A class Derived inherits from a template Base<Derived> — passing ITSELF as the template argument to its own base class. This lets Base call methods on the actual derived type via static_cast<Derived*>(this), entirely at compile time — no vtable, no virtual dispatch, no indirect call. The result is "static polymorphism": Base-defined code that behaves differently per Derived type, fully inlinable, at the direct cost of losing genuine RUNTIME polymorphism (you can no longer hold a std::vector<Base*> of mixed concrete types and call through it uniformly, because each Base<X> is actually a distinct type for each X).

CRTP giving polymorphism-like reuse with zero virtual-call overhead
template <class Derived>
struct Shape {
    double area() const {
        // static_cast is safe here BY CONVENTION: Derived is required to inherit from Shape<Derived>
        return static_cast<const Derived*>(this)->areaImpl();
    }
};
struct Circle : Shape<Circle> {
    double r;
    explicit Circle(double r) : r(r) {}   // needed: Circle inherits Shape<Circle>,
    double areaImpl() const { return 3.14159 * r * r; }
};
struct Square : Shape<Square> {
    double s;
    explicit Square(double s) : s(s) {}    // so neither is a plain aggregate anymore
    double areaImpl() const { return s * s; }
};

Circle c(5);
c.area(); // Shape<Circle>::area() calls Circle::areaImpl() -- resolved AT COMPILE TIME,
          // fully inlinable, no vtable lookup anywhere in this call chain

Compare this to the virtual-function version in the OOP group: there, area() requires an indirect call through a vtable that the compiler cannot resolve until runtime. Here, the compiler knows the concrete type of this at compile time (because Shape<Circle> is a distinct, fully-specialized type), so areaImpl() can be inlined directly into the caller. (Circle/Square need an explicit constructor rather than plain brace-init like Circle{5}, since inheriting from Shape<Circle> means they're no longer aggregates.)

The tradeoff: no more uniform runtime collection
// This does NOT work with CRTP, because Shape<Circle> and Shape<Square> are
// genuinely different, unrelated types (no common non-template base):
// std::vector<Shape<???>*> shapes; // there's no single type to put in this vector

// The virtual-dispatch version from the OOP group DOES support this naturally:
std::vector<std::unique_ptr<Shape>> shapes; // Shape is a real common (non-template) base
shapes.push_back(std::make_unique<Circle>());
shapes.push_back(std::make_unique<Square>());
for (auto& s : shapes) total += s->area(); // works because it's genuine runtime polymorphism

This is the fundamental tradeoff CRTP makes: you gain compile-time-resolved, zero-overhead "polymorphism" for code that KNOWS its concrete types at compile time, but you lose the ability to treat a heterogeneous, runtime-determined collection uniformly — for that, you still need real virtual dispatch.

Pitfalls

  • Reaching for CRTP when you actually need runtime polymorphism (a collection of mixed concrete types processed uniformly) — CRTP fundamentally cannot do this; check which kind of "varies per type" you actually have before picking a mechanism.

  • The static_cast<Derived*>(this) inside Base is NOT checked by the compiler to be safe — it's a convention enforced only by the fact that Base<Derived> is meant to only ever be inherited by exactly that Derived. Nothing stops (accidental) misuse like struct Oops : Shape<SomeOtherType> {};, which compiles but is nonsensical.

A favorite HFT interview topic specifically because it's the direct, concrete answer to "how do you get polymorphism-like code reuse without paying the virtual-call cost on a hot path?"
