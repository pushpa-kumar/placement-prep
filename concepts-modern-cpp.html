Lambda captures

A lambda's capture clause controls exactly how it accesses variables from its enclosing scope. [x] captures x BY VALUE — a copy taken at the moment the lambda is created, independent of x's later lifetime. [&x] captures x BY REFERENCE — no copy, but x must genuinely outlive every use of the lambda, or you have a dangling reference. [=] and [&] capture everything the lambda body actually uses, by value or reference respectively (implicit, less explicit about intent). Since C++14, generalized ("init") captures like [y = std::move(someValue)] let you capture a MOVED or freshly-COMPUTED value under a new name, rather than being limited to copying/referencing an existing variable verbatim.

By-value capture making a returned lambda safe
auto makeAdder(int base) {
    return [base](int x) { return base + x; };  // base copied INTO the lambda at creation
}

auto add5 = makeAdder(5);
add5(10); // 15 -- base's copy inside the lambda is completely independent of the
          // original parameter `base`, which no longer exists once makeAdder returns

If this had captured [&base] instead, the returned lambda would hold a reference to a parameter that ceases to exist the instant makeAdder returns — calling add5 later would read a dangling reference, undefined behavior.

Generalized capture: moving an expensive resource into a lambda
std::vector<int> bigData = loadHugeDataset();

auto processor = [data = std::move(bigData)]() {
    // `data` here is a NEW lambda-member variable, initialized by moving bigData's
    // contents in at lambda-creation time -- no copy of the (potentially huge) vector
    return std::accumulate(data.begin(), data.end(), 0);
};
// bigData is now valid-but-unspecified (moved-from) -- ownership genuinely transferred
// into the lambda, not merely referenced or copied

Without generalized captures, you'd either have to copy bigData into the lambda (expensive) or capture it by reference (dangerous if the lambda outlives bigData) — moving it in via [data = std::move(bigData)] gets you a cheap, safe, fully-owned copy inside the lambda's own closure.

Pitfalls

  • Capturing [&] (implicit by-reference) in a lambda that OUTLIVES its creating scope (stored, returned, or scheduled to run asynchronously later) — this is one of the most common sources of dangling-reference bugs in modern C++; if the lambda's lifetime isn't strictly nested inside the captured variables' lifetimes, prefer explicit by-value or generalized-move captures.

  • Assuming [=] is always "safe" because it copies — it copies whatever is captured, but this is captured as a raw pointer even under [=] (pre-C++20; C++20 deprecated implicit this capture via [=] for exactly this reason), so member-variable access inside a [=]-capturing lambda can still dangle if the object itself is destroyed.

Iterator invalidation

Modifying a container can invalidate existing iterators, references, and pointers into it — and the exact rule is DIFFERENT per container, which is exactly why this shows up so often as a debugging/gotcha question. std::vector invalidates ALL iterators on any reallocation (and invalidates end() on essentially any insert/erase, even without reallocation). std::deque invalidates iterators on insert/erase almost everywhere except sometimes at the very ends. Node-based containers — std::list, std::map, std::set, std::unordered_map — only invalidate iterators/references to the SPECIFIC element that was erased; everything else remains valid (unordered_map additionally invalidates ALL iterators, but not references/pointers, on a rehash). Using an invalidated iterator is undefined behavior.

The classic erase-while-iterating bug on a vector
std::vector<int> v = {1, 2, 3, 4, 5};
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it == 3) {
        v.erase(it);   // erase() invalidates `it` (and everything after it)
    }
}   // the loop's `++it` on the NEXT iteration uses the now-invalidated `it` --
    // undefined behavior, even though this often "appears to work" in practice

v.erase(it) returns a new, valid iterator to what's now at that position, but the loop's own ++it runs on the OLD, invalidated iterator instead of that returned value — the bug is subtle exactly because it frequently doesn't crash, it just silently skips elements or reads garbage.

The correct pattern
for (auto it = v.begin(); it != v.end(); ) {
    if (*it == 3) {
        it = v.erase(it);   // reassign `it` to erase()'s return value -- guaranteed valid
    } else {
        ++it;                // only advance manually when we DIDN'T just erase
    }
}

erase() itself returns an iterator to the element that now occupies the erased position (or end() if the last element was erased), which is exactly the iterator you should continue the loop with — this pattern correctly avoids ever touching an invalidated iterator.

Pitfalls

  • Assuming ALL containers behave like std::vector regarding invalidation — a perfectly safe erase-while-iterating pattern for std::list (which only invalidates the specific erased element's iterator) becomes a real bug if the container is later changed to std::vector.

  • Holding onto a reference/pointer into a std::vector across a push_back/insert call and assuming it's still valid — even if the SPECIFIC iterator you're tracking wasn't the one erased, a vector's own growth (reallocation) can invalidate every reference into it, not just ones near the modification point.

Small String Optimization (SSO)

Most std::string implementations avoid a heap allocation entirely for SHORT strings — typically up to somewhere around 15-22 bytes, depending on the standard library implementation — by storing the character data directly INLINE inside the string object's own storage (using space that would otherwise hold a pointer/capacity/size for the heap-allocated case). Only strings longer than that threshold actually allocate a separate heap buffer.

Short strings never touch the heap
std::string s = "hello";       // 5 chars -- comfortably within SSO's inline buffer on
                                // essentially every major standard library implementation;
                                // NO heap allocation happens for this at all

std::string big(100, 'x');     // 100 chars -- exceeds SSO's inline capacity;
                                // this DOES heap-allocate a buffer to hold the data

You can observe this indirectly: constructing, copying, and destroying many short strings in a tight loop is dramatically cheaper than the same operations on strings just past the SSO threshold, precisely because the short case involves no allocator calls at all.

Why this changes a common intuition about hot-path string use
// The old C++03-era instinct: "never use std::string on a hot path, it always heap-allocates"
// is now only PARTIALLY true. For short, fixed-size identifiers (e.g. a 6-character ticker
// symbol), std::string operations frequently incur NO allocation at all thanks to SSO.
// It's still generally true that the hottest, most latency-sensitive paths in HFT code
// prefer fixed-size char buffers or std::string_view over std::string regardless --
// SSO reduces, but doesn't eliminate, the argument against std::string in the hottest loops
// (copying a short string is still a real memcpy of its inline bytes, and comparisons/hashing
// still cost something, even with zero heap traffic).

This is a good example of an interview answer that shows nuance: SSO is a real, important optimization to know about, but knowing its LIMITS (still not literally free, still generally avoided in the absolute hottest paths) is what separates a surface-level answer from a deeper one.

Pitfalls

  • Assuming SSO means std::string is always as cheap as a fixed-size buffer — even an SSO'd string still involves a memcpy of its bytes on copy and real comparison/hashing cost; it's "no heap allocation," not "free."

  • Assuming the SSO threshold is standardized — it is an IMPLEMENTATION detail; different standard libraries (libstdc++, libc++, MSVC's STL) use different inline-buffer sizes, so code should never depend on the exact cutoff.

std::string_view (C++17)

A std::string_view is a lightweight, NON-OWNING view over a contiguous sequence of characters — just a pointer and a length, no allocation, no copy, no ownership. It's ideal for read-only string parameters that don't need to outlive the call (avoiding a copy of the caller's data), but that convenience comes with a real lifetime obligation: the underlying character data must outlive the string_view, and a string_view is NOT guaranteed to be null-terminated (unlike a const char* or std::string::c_str()).

Avoiding copies on a read-only parameter
void log(std::string_view msg) {   // no copy of the caller's string, whatever form it's in
    std::cout << msg;
}

log("a string literal");            // no allocation
log(someExistingStdString);          // no copy of someExistingStdString's buffer either
log(someExistingStdString.substr(0, 5)); // careful: substr() itself still allocates a
                                          // temporary std::string here, which is then
                                          // viewed -- string_view didn't avoid THAT copy

string_view eliminates the copy that would otherwise happen converting between string-like types at a function boundary — but it can't retroactively make an already-copying operation (like substr on a std::string) free.

The classic dangling string_view bug
std::string_view getGreeting() {
    std::string temp = "hello, " + std::string("world");  // a temporary std::string
    return temp;   // returns a string_view into `temp`'s buffer...
}                   // ...but `temp` is destroyed HERE, at the end of the function --
                    // the returned string_view is immediately dangling

std::string_view bad = getGreeting();
std::cout << bad;   // undefined behavior: reading through a dangling string_view

This is the single most important thing to internalize about string_view: it never extends anyone's lifetime, and the compiler will not warn you when you view something whose lifetime is about to end — the analogous mistake with a std::string return value would be perfectly safe (the string itself is returned, not just a view into one).

Pitfalls

  • Assuming a string_view is null-terminated — passing .data() from a string_view to a C API expecting a null-terminated const char* is a real, silent bug unless you specifically know the underlying data happens to be null-terminated (e.g., it came from a std::string via .c_str()-compatible construction).

  • Returning or storing a string_view that views a temporary (as shown above) — this is by far the most common real-world string_view bug, and the compiler generally does not catch it.

Structured bindings (C++17)

Structured bindings let you unpack a tuple, pair, array, or any struct with all-public members into individually-named variables in a single declaration — auto [a, b] = someExpr; — which is a substantial readability improvement over repeatedly writing .first/.second or std::get<N>(...).

Unpacking a map's key/value pairs in a range-based for loop
std::map<std::string, int> scores = {{"alice", 90}, {"bob", 85}};
for (const auto& [name, score] : scores) {
    std::cout << name << " = " << score << "\n";
}
// compare to the pre-C++17 idiom:
// for (const auto& pair : scores) { std::cout << pair.first << " = " << pair.second; }

name and score are genuinely meaningful names bound directly to the pair's .first/.second, rather than forcing every reader to remember which of .first/.second corresponds to the key vs. the value.

Structured bindings also work on your own structs
struct Point { double x, y; };
Point p{3.0, 4.0};
auto [x, y] = p;               // x=3.0, y=4.0, bound by DECLARATION ORDER of the members
double dist = std::sqrt(x*x + y*y);

This works on any struct whose members are all public and non-static, binding names to members strictly in the order they're declared in the struct — no special support needs to be written into Point itself.

Pitfalls

  • Assuming auto [a, b] = pair always makes independent copies — whether a/b are copies, references, or const references depends on whether you wrote auto, auto&, or const auto& before the brackets, exactly analogous to ordinary auto-deduction rules.

std::optional, std::variant, std::any (C++17)

Three tools for expressing "this value might not be a simple, always-present T," each solving a different flavor of that problem. std::optional<T> represents a value that may or may not be present — a much safer, more expressive alternative to a sentinel value (like returning -1 for "not found") or an owning pointer used purely to signal absence. std::variant<A, B, ...> is a TYPE-SAFE tagged union: it holds exactly one value from a fixed, closed set of alternative types, and the compiler (via std::visit or std::get) enforces that you handle it correctly — no risk of reading the wrong union member. std::any holds a value of essentially ANY copyable type, fully type-erased, retrieved only via a checked any_cast — the most flexible of the three, but also the least type-safe and generally the least performant (it commonly involves a heap allocation and always involves a runtime type check on extraction).

std::optional replacing a sentinel-value anti-pattern
std::optional<int> findFirst(const std::vector<int>& v, int target) {
    for (int x : v) if (x == target) return x;
    return std::nullopt;    // explicit, type-safe "not found" -- no magic sentinel needed
}

if (auto result = findFirst(data, 42)) {
    use(*result);            // safely dereference -- we know it's present here
} else {
    handleNotFound();
}

Compare this to the old idiom of returning -1 (or some other magic value) to mean "not found" — that approach silently breaks if -1 is ever a legitimate value in your actual data; optional makes "absent" a distinct, impossible-to-confuse-with-a-real-value state.

std::variant enforcing exhaustive, type-safe handling
std::variant<int, std::string, double> value = 42;

std::visit([](auto&& v) {
    std::cout << v;   // the compiler generates the correct call for whichever
}, value);            // alternative is ACTUALLY active -- no manual tag-checking,
                      // no risk of reading the union as the wrong type

Compare this to a raw C-style union with a manually-maintained "which member is active" tag — variant makes the tag-tracking and dispatch part of the type system itself, eliminating an entire class of "read the wrong union member" bugs.

Pitfalls

  • Reaching for std::any when std::variant would work — if the SET of possible types is known and fixed, variant gives you compile-time exhaustiveness checking (via std::visit) that any's fully-erased, runtime-checked nature cannot; any should be reserved for genuinely open-ended "any copyable type" scenarios.

  • Dereferencing a std::optional without checking it has a value first (*opt when opt is empty) — this is undefined behavior, exactly analogous to dereferencing a null pointer; always check (if (opt)) or use .value() (which throws instead of UB on empty) when you're not certain.

noexcept specifier

Declaring a function noexcept is a promise that it will NEVER let an exception propagate out of it. If one somehow does anyway, the runtime doesn't convert it into a normal catchable exception at the call site — it calls std::terminate() immediately, ending the program. Beyond being documentation, noexcept has a genuine functional consequence for the standard library: containers like std::vector only use a type's MOVE constructor during reallocation if that move constructor is marked noexcept; if it isn't, the container conservatively falls back to COPYING during reallocation instead, specifically to preserve its own strong exception-safety guarantee (see Exception safety guarantees).

The functional impact of noexcept on vector reallocation
class Buffer {
public:
    Buffer(Buffer&& other) noexcept { /* steal other's resources, cannot throw */ }
};

std::vector<Buffer> v;
// when v reallocates: since Buffer's move constructor is noexcept, vector moves
// each existing Buffer into the new allocation -- O(1) per element, no copies

class RiskyBuffer {
public:
    RiskyBuffer(const RiskyBuffer&) { /* explicit copy ctor -- gives vector a fallback to use */ }
    RiskyBuffer(RiskyBuffer&& other) { /* NOT marked noexcept, even if it never actually throws */ }
};

std::vector<RiskyBuffer> v2;
// when v2 reallocates: vector cannot be SURE this move won't throw partway through
// (the type system gives it no such promise), so it falls back to COPYING every
// element instead -- silently, with no compile error, just worse performance

This is a real, easy-to-miss performance bug: forgetting noexcept on a move constructor that genuinely never throws still causes std::vector to copy instead of move during reallocation, and nothing about this is flagged by the compiler — it just silently performs worse. (RiskyBuffer needs an explicit copy constructor here -- declaring only a move constructor would suppress the implicit copy constructor entirely, leaving vector nothing to fall back to but the move it already has.)

noexcept as a conditional expression
template <class T>
void swap(T& a, T& b) noexcept(std::is_nothrow_move_constructible_v<T>) {
    T tmp = std::move(a);
    a = std::move(b);
    b = std::move(tmp);
}

noexcept can itself take a boolean expression, letting generic code propagate the noexcept-ness of the type it's parameterized over — this swap is noexcept exactly when T's own move construction is, rather than making a blanket claim that might be false for some T.

Pitfalls

  • Marking a function noexcept when it genuinely CAN throw (e.g., it allocates memory, calls code you don't fully control) — if it ever does throw, the program terminates immediately rather than the exception being catchable anywhere, which is a much worse outcome than an uncaught exception normally is.

  • Forgetting noexcept on move constructors/assignment operators that could easily be written to never throw — this is the single most common noexcept-related missed optimization, silently costing you vector's move-instead-of-copy behavior.
