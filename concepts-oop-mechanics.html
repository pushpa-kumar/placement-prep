Virtual functions & vtables

A class with at least one virtual function gets a hidden **vtable**: a per-CLASS static array of function pointers, one slot per virtual function. Every instance of that class then carries a hidden **vptr** (usually the first bytes of the object) pointing to its class's vtable. When you call a virtual function through a pointer or reference, the compiler doesn't emit a direct call — it emits code that follows the vptr, indexes into the vtable at that function's fixed slot, and calls whatever function pointer is sitting there. Which function that turns out to be depends on the object's ACTUAL (dynamic) type, not the static type of the pointer/reference you're calling through — that's the whole mechanism behind runtime polymorphism.

The cost is real and measurable: an indirect call through a pointer that the CPU can't always predict well, plus it blocks the compiler from inlining the call (it doesn't statically know which function it is), which cascades into losing other optimizations that inlining would have enabled.

Tracing exactly what happens at a virtual call site
struct Shape {
    virtual double area() const = 0;
    virtual ~Shape() = default;
};
struct Circle : Shape {
    double r;
    explicit Circle(double r) : r(r) {}   // an explicit constructor is needed:
    double area() const override { return 3.14159 * r * r; }
};                                          // Circle has virtual functions (inherited),
struct Square : Shape {                    // so it isn't an aggregate and can't use
    double s;                              // plain brace-init like Circle{5} directly
    explicit Square(double s) : s(s) {}
    double area() const override { return s * s; }
};

void printArea(const Shape& shape) {
    std::cout << shape.area(); // indirect call: follow shape's vptr, jump to slot 0
}

Circle c(5); Square sq(4);
printArea(c);  // shape's vptr points at Circle's vtable  -> calls Circle::area
printArea(sq); // shape's vptr points at Square's vtable  -> calls Square::area

printArea is compiled ONCE, with no idea at compile time whether it will be handed a Circle or a Square — the correct area() is found purely by following the vptr at runtime, which is exactly what makes this polymorphic. (Note: Circle/Square need explicit constructors here, not plain aggregate brace-init, precisely because inheriting from a class with virtual functions disqualifies them from being aggregates.)

Why this shows up in low-latency interview discussions
// A tight loop calling a virtual function through a base pointer:
for (auto& order : orders) {           // orders: vector<Order*>, mixed dynamic types
    total += order->computeValue();     // virtual call: cannot be inlined,
}                                        // branch predictor must guess the target each time

// vs. a non-virtual, CRTP-based, or template-based design where the concrete
// type is known at compile time and the call can be fully inlined into the loop

In a loop processing many heterogeneous orders through a common virtual interface, every iteration pays the indirect-call cost. This is precisely why HFT codebases often reach for CRTP or templates instead of virtual dispatch on the hottest paths — see the Templates & Generic Programming group.

Pitfalls

  • Calling a virtual function from inside a constructor or destructor and expecting the DERIVED override to run — it won't; see the C++ Q&A output-prediction question on this exact topic. During Base's own constructor, the object's dynamic type is still Base.

  • Forgetting that a non-virtual function called through a base pointer is resolved STATICALLY (at compile time, based on the pointer's declared type), not dynamically — mixing virtual and non-virtual functions of the same name across a hierarchy is a common source of confusion (see Function overloading vs overriding vs hiding).

Understanding the vptr/vtable mechanism (not just "virtual enables polymorphism") is what separates a surface-level answer from one that shows you understand the actual performance cost — which is exactly what a low-latency interviewer is listening for.

Pure virtual functions & abstract classes

A pure virtual function — declared with = 0 instead of a body — has no implementation in that class, and its presence makes the whole class **abstract**: you cannot instantiate it directly, only through a derived class that provides an override for every pure virtual function it declares. This is C++'s mechanism for expressing an interface: "any concrete type used this way MUST supply these operations."

A subtlety worth knowing: a pure virtual function CAN still have a body (definition) in the base class, which a derived class can explicitly call via qualified name (Base::f()) even though it must still override it to become concrete — useful for providing a default/shared partial implementation that derived classes build on.

A clean interface via pure virtual functions
struct Serializable {
    virtual std::string toJson() const = 0;
    virtual ~Serializable() = default; // still needs a virtual destructor, see below
};

// Serializable x;  // ERROR: cannot instantiate an abstract class

struct Order : Serializable {
    std::string toJson() const override { return "{...order fields...}"; }
};
Order o; // OK: Order is concrete, it overrides the one pure virtual function

Serializable can never exist on its own — it exists purely to force every concrete subclass to provide a toJson() implementation, which is exactly the contract an interface is supposed to enforce at compile time.

A pure virtual function that still has a callable body
struct Logger {
    virtual void log(const std::string& msg) = 0;   // pure virtual: declared here only
};
void Logger::log(const std::string& msg) {          // defined OUT-OF-LINE -- a pure virtual
    std::cout << "[base] " << msg;                  // function's body cannot be given inline
}                                                     // with "= 0 { ... }"; that's a compile error
struct FileLogger : Logger {
    void log(const std::string& msg) override {
        Logger::log(msg);          // explicitly invoke the base's shared behavior
        writeToFile(msg);
    }
};

Logger::log is pure virtual (Logger itself is still abstract, still can't be instantiated) but its body is real code that FileLogger's override chooses to reuse — a lesser-known pattern for sharing common logic while still forcing every subclass to explicitly opt in. Note the syntax: a pure virtual function's definition cannot be written inline as = 0 { ... } — the = 0; declaration and the body must be separated, with the body defined out-of-line (here, immediately after, using the qualified name Logger::log).

Pitfalls

  • Forgetting that an abstract class still needs constructors/member initialization for any data it holds — "abstract" only blocks instantiation of THAT class directly, it doesn't mean the class can't have real state.

  • Not marking the destructor virtual on an abstract base — see Virtual destructors below; this is such a common oversight that many style guides mandate it any time a class has any virtual function at all.

Virtual destructors

If an object might ever be deleted through a pointer to one of its BASE classes, that base's destructor must be declared virtual. Without it, delete basePtr; resolves the destructor call statically based on the pointer's declared type — it calls ONLY the base class's destructor, never the derived class's, even if the pointer actually points at a fully-constructed derived object. Any resources the derived part owns (heap memory, file handles, anything with a non-trivial destructor) never get cleaned up. This is undefined behavior per the standard, and in practice manifests as a straightforward resource leak.

The bug: a non-virtual base destructor
struct Base {
    ~Base() { std::cout << "~Base "; }   // NOT virtual
};
struct Derived : Base {
    int* buffer = new int[1000];
    ~Derived() { delete[] buffer; std::cout << "~Derived "; }
};

Base* p = new Derived();
delete p;   // prints ONLY "~Base " -- ~Derived() never runs, buffer leaks!

The compiler resolves delete p using p's STATIC type (Base*), and since ~Base isn't virtual, there's no vtable lookup involved at all — it's a direct, non-polymorphic call to ~Base only.

The fix: one keyword
struct Base {
    virtual ~Base() { std::cout << "~Base "; }   // now virtual
};
struct Derived : Base {
    int* buffer = new int[1000];
    ~Derived() override { delete[] buffer; std::cout << "~Derived "; }
};

Base* p = new Derived();
delete p;   // now correctly prints "~Derived ~Base " -- ~Derived runs first,
            // then implicitly chains to ~Base, exactly like normal inheritance

With virtual added, delete p becomes a polymorphic call resolved through the vtable at runtime: it finds Derived's destructor (because that's the object's actual dynamic type), runs it, and that automatically chains up to ~Base afterward.

Pitfalls

  • Assuming this only matters if you personally write delete basePtr — it also silently affects std::unique_ptr<Base>/std::shared_ptr<Base> holding a Derived object; smart pointers don't magically fix a missing virtual destructor, they just call delete on your behalf at the same wrong destructor.

  • Adding virtual to EVERY destructor "just in case" even on classes never used polymorphically — this isn't free (it forces a vtable to exist, growing every instance by a pointer); the rule is specifically "if this class might be deleted through a base pointer," not "always."

One of THE most common "what's wrong with this code" C++ interview snippets — if you see a class hierarchy with a delete through a base pointer, checking for a virtual destructor is the first thing to look at.

The diamond problem & multiple inheritance

When a class D inherits from two classes B and C that both inherit from a common base A, D ends up — by default — with TWO separate, independent A subobjects (one via B, one via C). Any attempt to access a member of A through D is ambiguous, because the compiler can't tell which copy you mean. C++'s answer is **virtual inheritance**: if B and C each inherit from A *virtually*, then D ends up with exactly ONE shared A subobject instead of two, resolving the ambiguity — at the cost of a more complex (and slightly slower) object layout, since the location of the shared virtual base now has to be looked up indirectly rather than at a fixed offset.

The problem: two independent A subobjects
struct A { int x = 1; };
struct B : A {};
struct C : A {};
struct D : B, C {};

D d;
// d.x;        // ERROR: ambiguous -- is this B's A::x or C's A::x?
d.B::x = 10;    // must explicitly disambiguate which A subobject you mean
d.C::x = 20;    // this is a SEPARATE x from d.B::x -- D genuinely has two of them

sizeof(D) here is large enough to hold two full, independent A subobjects — one that came through B, one that came through C — and they can hold different values simultaneously, which is exactly the confusing part.

The fix: virtual inheritance collapses it to one shared subobject
struct A { int x = 1; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {};

D d;
d.x = 5;   // unambiguous now: there is exactly ONE A subobject, shared by B and C

Because both B and C inherit from A virtually, the compiler guarantees D contains just one A — accessed through either path, it's the same object, so d.x is no longer ambiguous.

Pitfalls

  • Assuming virtual inheritance is "free" — it changes how the base subobject is located (typically via an extra indirection/offset table), so classes using it are slightly larger and slightly slower to access their virtual base than a plain inheritance hierarchy.

  • Not realizing that if only ONE of B or C inherits virtually and the other doesn't, D still ends up with two A subobjects — both paths need to agree on virtual inheritance for the sharing to happen.

Static vs dynamic binding

Static (compile-time) binding decides which function is called based purely on the STATIC type of the expression you're calling through — this is how every non-virtual function call and every overload-resolution decision works. Dynamic (runtime) binding decides based on the ACTUAL, runtime type of the object — this is exclusively how virtual function calls, invoked through a base pointer or reference, work. The two can coexist on the very same object in confusing ways, which is exactly what interview snippets exploit.

Both kinds of binding on the same object, in the same two lines
struct Base {
    void f()          { std::cout << "Base::f "; }         // NOT virtual
    virtual void g()  { std::cout << "Base::g "; }
};
struct Derived : Base {
    void f()          { std::cout << "Derived::f "; }        // hides Base::f, doesn't override it
    void g() override { std::cout << "Derived::g "; }
};

Base* p = new Derived();
p->f();   // "Base::f "    -- STATIC binding: f isn't virtual, resolved from p's declared type (Base*)
p->g();   // "Derived::g " -- DYNAMIC binding: g is virtual, resolved from p's actual type (Derived)

Both calls go through the exact same pointer p, but they're resolved completely differently — f never even looks at what p actually points to, while g looks at nothing else.

Why this surprises people used to other languages
Derived d;
Base& ref = d;
ref.f(); // still "Base::f" -- reference type is Base&, f is non-virtual, static binding applies
d.f();   // "Derived::f" -- calling directly on the Derived object itself uses Derived::f

In languages where every method is virtual by default (Java, Python), this distinction doesn't exist — C++'s default of non-virtual-unless-declared is a deliberate zero-overhead-by-default design choice, and it's exactly why you have to reason carefully about which type you're calling THROUGH, not just what the object actually is.

Pitfalls

  • Assuming that because a DERIVED class overrides-looking function, calling it through a base pointer will pick up the derived behavior — only true if the base declared that function virtual in the first place.

Object slicing

Assigning or passing a DERIVED object to a BASE object BY VALUE truncates — "slices" — it: only the Base subobject's data gets copied, and anything Derived-specific (extra data members, virtual overrides) is lost, because the destination's static type is Base, full stop. This is a copy-semantics problem, and the fix is always the same: pass/store by reference or pointer instead of by value whenever polymorphic behavior matters.

Slicing in action
struct Base {
    int x = 1;
    virtual void hi() const { std::cout << "Base"; }
};
struct Derived : Base {
    int y = 2;
    void hi() const override { std::cout << "Derived"; }
};

void printIt(Base b) { b.hi(); }  // parameter taken BY VALUE

Derived d;
printIt(d);   // prints "Base" -- d was SLICED into a plain Base when copied into the parameter

The moment d is copied into printIt's by-value parameter b, only the Base portion of d gets copied — y is discarded, and b's actual type really is Base (not Derived), so its vtable pointer points at Base's vtable too, meaning hi() calls Base's version even though it's declared virtual.

The fix
void printIt(const Base& b) { b.hi(); } // reference: no copy, no slicing

Derived d;
printIt(d); // now correctly prints "Derived" -- b refers to the actual Derived object

Taking the parameter by reference (or pointer) means no copy ever happens — b is just another name for the original Derived object, so virtual dispatch works exactly as expected.

Pitfalls

  • Storing polymorphic objects directly in a std::vector<Base> — every element is a Base, full stop; any Derived object pushed into it gets sliced on insertion. Polymorphic collections need std::vector<std::unique_ptr<Base>> (or raw/shared pointers) instead.

  • Slicing during exception handling: catch (Base e) (by value) slices the thrown exception object the same way — always catch exceptions by (const) reference: catch (const Base& e).

A frequent "spot the bug" question: showing a function taking a base-class parameter by value and asking why polymorphism "isn't working."

Function overloading vs overriding vs hiding

Three different things that all involve "two functions with the same name" but behave completely differently, and mixing them up is a rich source of real bugs, not just interview trivia. **Overloading**: multiple functions with the SAME name but DIFFERENT parameter lists, in the same scope — resolved entirely at compile time by argument types. **Overriding**: a derived class redefines a VIRTUAL function with an IDENTICAL signature to the base's — resolved at runtime via the vtable. **Hiding**: a derived class declares ANY function with the same name as something in the base (regardless of signature, regardless of virtual-ness) that is NOT a valid override — and this hides ALL base overloads of that name from ordinary lookup on the derived type, whether or not the derived version's signature looks related at all.

Hiding silently removes access to an entire overload set
struct Base {
    virtual void f(int x)   { std::cout << "Base::f(int) "; }
    void f(double x)        { std::cout << "Base::f(double) "; }
};
struct Derived : Base {
    void f(int x) override { std::cout << "Derived::f(int) "; } // a valid override
};

Derived d;
d.f(3.14);       // Surprise: prints "Derived::f(int) " (3.14 truncated to 3!)
                 // NOT "Base::f(double)" -- Derived::f(int) HIDES Base::f(double) entirely
d.Base::f(3.14); // must explicitly qualify to reach the hidden overload -> "Base::f(double) "

Declaring ANY function named f in Derived — even one that's a perfectly legitimate override of f(int) — removes Base's ENTIRE f overload set (including f(double), which has nothing to do with the override) from ordinary name lookup on a Derived object. This is called the "hiding rule," and it catches even experienced C++ developers off guard.

Fixing hiding with a using-declaration
struct Derived : Base {
    using Base::f;             // pull ALL of Base's f overloads back into scope
    void f(int x) override { std::cout << "Derived::f(int) "; }
};

Derived d;
d.f(3.14); // now correctly resolves to Base::f(double) via normal overload resolution

The using Base::f; declaration explicitly re-introduces Base's overloads into Derived's scope, so overload resolution across ALL of them (Base's f(double) and Derived's own f(int)) works the way you'd naively expect.

Pitfalls

  • Believing that a same-named function with a DIFFERENT signature in a derived class is automatically an overload that peacefully coexists with the base's version — it isn't; it hides the base's entire overload set unless you explicitly using Base::name;.

  • Marking a function override with a signature that doesn't EXACTLY match the base's virtual function (wrong parameter types, missing/extra const) — this is actually a compile ERROR when override is used (which is exactly why you should always write override: without it, a signature mismatch silently creates an unrelated new function — hiding — instead of failing to compile).

The hiding rule specifically is one of the more "gotcha" pieces of C++ trivia interviewers use to separate candidates who've only read tutorials from candidates who've actually been bitten by real code.
